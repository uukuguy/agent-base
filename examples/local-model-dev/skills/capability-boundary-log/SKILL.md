# 记录本地模型的能力边界

## 为什么必须记

本地小模型的边界与云端模型差别很大，而且**同一个模型换个量化就是另一条边界**。
不记录就会反复踩同一个坑，并把"模型不行"误判成"我的配置不对"。

记录的价值不在于好看，而在于**下一次能直接查到**：这件事它到底行不行、在什么条件下行。

## 三类边界，处置完全不同

| 类别 | 例子 | 判定方式 | 命中了怎么办 |
|---|---|---|---|
| **硬边界** | 不支持工具调用；上下文只有 8k；没有 JSON mode | 一次探测即可确认 | 一票否决：改模型，或换一条不依赖它的做法 |
| **性能边界** | 首 token 3s、生成 12 tok/s、显存吃满 | 记三次取范围 | 把它移出内循环：改成批量/异步/离线 |
| **质量边界** | 指令遵循、结构化输出稳定性、多步推理、拒答率 | **只能统计**（同一输入重复 N 次） | 先加约束（schema 校验、few-shot）再测；仍不过就降级 |

**硬边界不重试，质量边界才重试** —— 把两者混在一起，就会在"它根本不支持工具调用"上耗一整天。

## 怎么测（最小可复现实验）

每个能力项都要留下"输入 + 运行次数 + 结果"，否则结论无从复核：

```bash
# 硬边界：这个模型支持哪些能力（capabilities 里有 tools 就说明能发工具调用）
ollama show qwen2.5-coder:7b

# 性能边界：真实生成一次，看首 token 与总耗时（用固定的长输出 prompt）
time curl -s http://localhost:11434/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen2.5-coder:7b","messages":[{"role":"user","content":"写一个 200 字的产品说明"}]}'

# 质量边界：同一输入重复 3 次，用结构化输出这类**可机械判定**的任务
#   （约定：输出必须是合法 JSON；3 次里几次能 parse，就是这条边界的实测值）
```

质量边界的判定复用 `prompt-eval-offline` 的方法与脚本（`scripts/eval-check.mjs`），
不要另起一套口径 —— 同一件事两套口径，数字就不可比。

## 记录表

| 能力项 | 类别 | 结论 | 证据（命令 / 用例 / 次数） | 日期 | 备注（模型+量化） |
|---|---|---|---|---|---|
| 工具调用 | 硬 | 支持 | `ollama show` capabilities 含 `tools` | | qwen2.5-coder:7b |
| 结构化输出 | 质量 | 3 次里 2 次合法 JSON | `cases.json#json-only`，3 次 | | 同上 |
| 长链推理（≥5 步） | 质量 | **未测** | 缺多步用例集 | | |

## 三种结论的写法（一字都不能含糊）

- **测过通过**：写"在什么用例、什么参数下通过了几次"。不许写成"完全支持"。
- **测过不通过**：写**最小复现** + 失败原文（长就截断要点）。不许只写"不行"。
- **没测过**：明确写 `未测`，并写清"缺什么才能测"。
  不要把没测过写成"可能不行"，也不要写成"应该可以" —— 这两种都是编的。

## 边界怎么用（决策规则）

1. 命中**硬边界** → 不要再用同一做法重试；改模型，或改路径（例如把工具调用改成人来确认）。
2. 命中**性能边界** → 把它移出内循环：批量跑、放后台、或只在必要时调用。
3. 命中**质量边界** → 先加约束再测一轮；仍不通过就**降级为「提示人来做」**，
   并在输出里明说"这一步本地模型不可靠，请人工确认"。

## 不要做

- 不要用一次成功代表"稳定"。
- 不要把同一模型**另一个量化**的结论外推过来 —— 量化不同，边界就可能不同。
- 不要在超出边界时硬凑一个看起来完成的答案。
