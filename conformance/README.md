# conformance/ —— 新 harness 的准入门槛（统一设计 §5.6，N11）

> **C1–C10 全为阻断性门槛**（P3 已裁决）：任何一项不通过，该 harness 不予接入。
> 「部分项仅告警」被明确否决 —— 会被软化的正是 **C5（静默失败检测力）** 与 **C8（参数层隔离）**，
> 也就是最危险的两类退化。

```bash
make conformance            # 跑全部用例（人读输出走 stderr）
make conformance JSON=1     # 机器可读
node conformance/run.mjs --only C5,C8
```

**退出码**：`0` 全过 / `1` 有未通过**或有未实现** / `2` 用法错误。
注意 conformance 是**开发适配器时**跑的工具，不属 §6.7 那套"智能体验证"的退出码语义。

## 为什么"未实现"不等于"通过"

新 harness 接入是渐进的过程，但**门槛不能渐进**。如果某个用例还没写就让整体变绿，
"conformance 全绿"就成了一句空话，而且被跳过的往往正是最难写的那两项（C5/C8）。

所以 runner 把未实现的用例记为 `pending` 并**非零退出**。这不是把工具做难用，
而是让"能不能接入"这个判断**永远只有一个意思**。

## 与 `failures.md` 的关系（C5 的输入）

`adapters/<h>/failure-cases.yaml` 是**机器可读**的静默失败检测清单：
§5.5 要求"每条静默失败都配一个可执行用例"，C5 就是去执行它们。

```yaml
cases:
  - id: F1
    kind: leak-undeclared-skill     # 注入类型，由 conformance 解释
    failure: "隐式源混入未声明的技能"
    detectBy: doctor 硬断言 1
    expectExitCode: 20
```

支持的注入类型见 `cases/index.mjs` 的 C5 分支。新增静默失败时，**两张表都要改**：
`failures.md`（给人读）与 `failure-cases.yaml`（给机器跑）。

## 加一个新的 harness 要做什么

见 §5.7 的十步清单。本目录的职责是**判定它做够了没有** —— 而不是帮它做。
