# dsh 适配器已知静默失败表（统一设计 §5.5 强制交付物）

> **本表的每一行都必须配一个可执行的检测用例**（进 `conformance` C5，来源为 `failure-cases.yaml`）。
> 本 harness 的失败面比另一个大：**它的设计哲学是"失败也继续跑"**，因此"没生效"往往连警告都没有。

## 来自实测与文档的失败模式

| # | 现象 | 真实原因 | 检测方式 | 闸门 |
|---|---|---|---|---|
| **D1** | 改了配置没生效，且**退出码 0** | patch 的 target id 不存在时**只打警告、继续运行**【文档 §11.1 / dsh 实验 A】。这是本 harness 最危险的一条 | `doctor` 断言「patch 的每个 target id 都出现在组合树里」；**这条断言是在替 harness 补它自己不报的错** | 2 |
| **D2** | 业务级增强没加载 | profile 里 `insert:` 的 row 落空，或插件被跳过 | 断言组合树里的 row id 集合 ⊇ 声明集合（`set-equals`） | 2 |
| **D3** | 工具没出现，但智能体照常启动 | MCP `failOnStartupError` 默认 **false**，连不上也启动【文档 §11.1】 | 断网/错端点的连接器探针**必须让闸门 3 失败** | 3 |
| **D4** | 无人值守时"卡死" | 审批**无应答者时 fail closed**【文档 §11.1】—— 它不会失败退出，而是等 | 断言运行入口给出了显式放行策略；冒烟用例超时即判失败，且失败信息必须区分"卡在审批"与"真的慢" | 4 |
| **D5** | 技能比声明的多 | **六个 rank 根**（project-dsh / project-agents / custom / user-dsh / user-agents / bundled）关不掉【文档】 | 断言组合树里实际生效的技能目录集合 == 渲染声明的集合 | 2 |
| **D6** | 升级后行为漂移 | 上游 `config` 是**整体替换**而非深合并，重述的 row 会随上游结构变化而过期**且不报错**【文档 §11.1「重述腐化」】 | 渲染器产出**完整** config（不做增量假设）+ 产物 digest 可复算；升级时靠 `conformance` 回归 | 1 + 2 |
| **D7** | 交付镜像里跑着"调试过的行为" | `--patch` 是调试逃生舱 | 交付/验证入口遇到 `--patch` 必须失败（退出码 2） | 1 |
| **D8** | 交付态与调试态无法区分 | 调试态未标记 | 轨迹首行输出 `{"type":"run.meta","mode":"debug"}`，与交付态可区分（§8.5） | 1 |

## 与另一个 harness 的不对称（写下来，避免"假装两边一样"）

| 维度 | 本 harness | 说明 |
|---|---|---|
| MCP 客户端 | **原生支持**（`@deepseek-ai/dsh-mcp-client`） | 另一个是 `unsupported`，需基座补客户端扩展。跨 harness 等价性在带连接器的智能体上**不成立**，必须显式标注 |
| 审批与沙箱轨迹 | **有原生事件**（`approval/policy`、`sandbox/mode`、`permission/preset`） | 另一个没有 → 它能回答"谁放行了这次调用"，另一个目前只能记 `allow`。这是缺口 G3 在两边的不对称 |
| 会话轨迹格式 | zstd 压缩的 JSONL（v4），记录骨架 `{type, seq, time, data}` | 另一个是明文 JSONL 事件流，无 `seq`。**两者都必须映射进同一份统一 schema** |
| 默认失败姿态 | 失败也继续（静默面大） | 另一个多为"报错即停"。因此本适配器的 `doctor` 承担更多"替上游报错"的责任 |

## 尚未机器化的条目（诚实标注）

- D3 需要真实连接器探针（闸门 3，S3），当前只能靠 `doctor` 断言"声明的连接器都进了组合树"，**不能**断言"连得上"。
- D4 的"卡在审批"与"真的慢"目前没有可靠的区分手段，需要冒烟用例配合超时与轨迹判读（S3）。
- D6 的回归网依赖 `conformance` 全绿，而 C6/C9 尚未实现（S3）。
