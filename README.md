# agent-base

**一套企业智能体基座 + 多个 harness 运行时。**

基座提供与 harness 无关的底座（中性智能体定义、适配契约、四道验证闸门、基座镜像、模板、文档）；
同一个智能体定义可以被任意一个受支持的 harness 渲染并运行。
企业在它之上派生各自的智能体应用——**应用派生到基座之外，不回头修改基座**。

> 仓库目录当前仍叫 `dsh-agent-base`（会话根目录不能就地改名）；改名为 `agent-base` 是一次性运维动作，
> 步骤见统一设计 §12.6。

## 已裁决的四个骨架级决策

| # | 决策 | 结论 |
|---|---|---|
| J1 | pi 与 dsh 的关系 | 并列可选；基座对"可移植核心"上的跨 harness 等价性负责 |
| J2 | 配置注入与可复现 | **行为烤、参数下放**：改变行为的进制品并经构建期渲染；端点/凭据等部署参数运行期注入 |
| J3 | 智能体定义形态 | 中性核心 + 渲染器 + 逃生舱（单一真源） |

## 基座与应用的边界

- 基座**不含任何业务智能体**
- 应用派生到基座**之外**，且不回头修改基座
- harness 的差异只允许出现在 `adapters/` 与 `harness/` 逃生舱里
- 详见统一设计 §1.2

## 设计文档的阅读方式

统一设计全文按四类标记组织，**因为它们的老化速度不同**：

| 标记 | 含义 | 老化速度 |
|---|---|---|
| 【不变量】 | 跨 harness 长期成立的要求与设计 | 慢 |
| 【适配契约】 | 基座与 harness 之间的接口，双方共同负责 | 中 |
| 【harness 专有】 | 某个 harness 的机制与实测约束 | 快 —— 随上游版本变化 |
| 【本项目决策】 | 在上述三者之上做的取舍 | 中 |

两份上位文档用三层标记（【dsh 专有】/【基座通用】/【本项目决策】）。统一设计在此基础上多出【适配契约】一层——
**它正是"一套基座 + 多个 harness"能够成立的那一层。**
