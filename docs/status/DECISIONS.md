# Decisions

> 架构决策与理由（既不是「当前状态」也不是「进度」）。

## 2026-09-25 · 基座镜像的构建与分层

**决策**：镜像**按架构分开构建**（原生优先 + 模拟隔离），再用 `docker-container` 驱动的 builder 合并成多架构 manifest list（OCI 归档落盘）；**生成的构建输入不放在 `core/`**，落 `dist/image/context/`。

**理由**：
- 一次 `--platform a,b` 在 arm64 机器上模拟 amd64 装 11 个包 + 2 个 harness，慢且**一架构失败毁掉整个构建**，排查时分不清代码问题与模拟问题。
- 本机默认 `docker` 驱动**不支持 OCI 导出**（实测报错），多架构打包必须换 builder 驱动。
- 坐标表必须写出包名，而**包名本身含 harness 名**，放在 `core/` 会踩 `core/harness-name` 这条分层规则。正确解法是纠正分层（生成物不是源码），而不是放宽规则。

**代价/边界**：多架构归档约 1.7 GB，只落本地；推送路径待 I2（内网能否直连镜像仓库）确认。
## D-0011 模型名是环境属性，不是行为属性（判据修正）

**背景**：设计里「行为烤、参数下放」的判据是「这个字段改了，同一个输入会不会得到不同行为」。按这条，
`model.name` 被归入制品层，并进了 `params.yaml` 的禁止清单（出现在参数层即违规，闸门 1 与 C8 双双拦截）。

**问题**：容器里"配置 LLM"于是只剩端点与凭据 —— 而实际部署中**端点与模型名是绑在一起的**
（内网网关只服务它有的那几个模型；dev 与 prod 的模型名常常不同）。端点既然运行期给，
模型名就没有理由烤死。判据对"环境属性"这一类用粗了。

**决定**：判据改为 —— **这个值是不是随部署环境而变**？是 → 参数层（运行期注入，必须可校验、可追溯）；
否 → 制品层。据此：

| 字段 | 归属 | 理由 |
|---|---|---|
| `model.route` | 制品层 | 它决定端点/凭据/模型名三个引用名，是"这份制品跑在哪条路由上"的身份 |
| `model.name` | **参数层** | 环境属性；定义里的值退化为**默认值** |
| `model.reasoningEffort` | 制品层 | 行为属性未变 |

**配套**（防止"可配置"变成"随便配"）：路由目录声明它服务哪些模型；闸门 1 与启动期都按该名单校验；
模型名记进轨迹（`model.request.model`）。**改了行为就必须改说法**：C8 原来的"模型选择禁止注入"
用例换了靶子（`tools.deny` / `persona` 仍是禁止项）。

**可逆性**：若企业实践表明模型名应当烤死，回退只需把 `model-name` 从 allowed 移回 forbidden、
把 `model.name` 的层改回 artifact —— 三处改动，无隐性依赖。
