# Decisions

> 架构决策与理由（既不是「当前状态」也不是「进度」）。

## 2026-09-28 · 运行环境与开发环境是两套（不提供「会话内即时改代码」）

**决策**：不把「在会话里临时改代码并即时生效」做成基座能力。智能体的**运行环境**与**开发环境**互相独立：
运行环境跑的是**制品**（渲染产物，冻结）；开发在**正式研发环境**里做，改完走「重跑」回路（重启会话 / 重跑闸门）。

**理由**（用户原话的意思）：进容器做 AI Coding 只是为了"临时能改代码"，**但要求即时生效**；
如果做不到即时生效，那就不如回正式研发环境改、再重启测试。既然如此，基座不该为此造一套半即时机制 ——
它既会破坏"跑的是制品"这条口径（闸门 2 的"实际加载 == 声明"正是靠这条成立），
又会把"某个目录下行为不同却无人知"的隐式输入引进来（沿 cwd 祖先发现指令文件/技能）。

**代价/边界**：
- **会话的工作区仍是中立临时目录**（`run-local` 的 `cwd = mkdtemp`）。想在会话里碰仓库，只能显式
  `bash cd`，**基座不承诺**模型默认看得见你的代码（路线图 C7 据此关闭，不再是缺口）。
- **替代回路是现成的、且已实测**：改定义 → 重跑（`make local` / `run-local`）会**自动重渲染**
  （清单指纹变了就重渲染；实测：改一个技能文件后重跑，产物里出现新内容，日志两次都打「先渲染」）⇒
  "重启即生效"。验收仍走四道闸门与（需要时的）容器内自证。
- 由此**降级**：路线图的「开发容器」工作线（W1–W4）不再按"进去改代码"论证 ——
  容器侧的价值收敛为**环境一致性与交付自证**，已由 `verify-container` / `env-check` 覆盖。

## 2026-09-25 · 基座镜像的构建与分层

**决策**：镜像**按架构分开构建**（原生优先 + 模拟隔离），再用 `docker-container` 驱动的 builder 合并成多架构 manifest list（OCI 归档落盘）；**生成的构建输入不放在 `core/`**，落 `dist/image/context/`。

**理由**：
- 一次 `--platform a,b` 在 arm64 机器上模拟 amd64 装 11 个包 + 2 个 harness，慢且**一架构失败毁掉整个构建**，排查时分不清代码问题与模拟问题。
- 本机默认 `docker` 驱动**不支持 OCI 导出**（实测报错），多架构打包必须换 builder 驱动。
- 坐标表必须写出包名，而**包名本身含 harness 名**，放在 `core/` 会踩 `core/harness-name` 这条分层规则。正确解法是纠正分层（生成物不是源码），而不是放宽规则。

**代价/边界**：多架构归档约 1.7 GB，只落本地；推送路径待 I2（内网能否直连镜像仓库）确认。
## D-0011 模型名是环境属性，不是行为属性（判据修正）

**背景**：设计里「行为烤、参数下放」的判据是「这个字段改了，同一个输入会不会得到不同行为」。按这条，
`model.name` 被归入制品层，并进了 `params.yaml` 的禁止清单（出现在参数层即违规，闸门 1 与 C8 双双拦截）。

**问题**：容器里"配置 LLM"于是只剩端点与凭据 —— 而实际部署中**端点与模型名是绑在一起的**
（内网网关只服务它有的那几个模型；dev 与 prod 的模型名常常不同）。端点既然运行期给，
模型名就没有理由烤死。判据对"环境属性"这一类用粗了。

**决定**：判据改为 —— **这个值是不是随部署环境而变**？是 → 参数层（运行期注入，必须可校验、可追溯）；
否 → 制品层。据此：

| 字段 | 归属 | 理由 |
|---|---|---|
| `model.route` | 制品层 | 它决定端点/凭据/模型名三个引用名，是"这份制品跑在哪条路由上"的身份 |
| `model.name` | **参数层** | 环境属性；定义里的值退化为**默认值** |
| `model.reasoningEffort` | 制品层 | 行为属性未变 |

**配套**（防止"可配置"变成"随便配"）：路由目录声明它服务哪些模型；闸门 1 与启动期都按该名单校验；
模型名记进轨迹（`model.request.model`）。**改了行为就必须改说法**：C8 原来的"模型选择禁止注入"
用例换了靶子（`tools.deny` / `persona` 仍是禁止项）。

**可逆性**：若企业实践表明模型名应当烤死，回退只需把 `model-name` 从 allowed 移回 forbidden、
把 `model.name` 的层改回 artifact —— 三处改动，无隐性依赖。

## D-0012 共享业务逻辑必须支持多种语言（登记，未实现）

**背景**：`harness/shared/*.mjs` 由两侧接入件以 **ESM 模块**方式 import ⇒ "可共享"目前只在
JavaScript/Node 世界里成立。业务团队的语言未必是我们的运行时的语言（Python / Go / Java 都常见）。

**问题**：如果共享层只能是 JS 模块，那"业务代码可共享"就不是一条架构性质，而只是"恰好都用 JS"。

**方向**（未实现，先登记）：把"共享"从**模块**提升为两类产物：

| 产物 | 形态 | 作用 |
|---|---|---|
| **能力描述** | 语言无关（JSON/YAML）：name / description / 参数 schema / 结果 schema / 确定性要求 | 各运行时接入件的**唯一输入**；不再靠读代码了解能力 |
| **可执行体** | **任意语言**：以**进程边界**调用（argv / stdin stdin-JSON / stdout JSON） | 业务实现；语言自由 |
| （可选）进程内快路径 | JS/TS 模块（今天的形态） | 同语言时省掉进程开销；**语义必须与进程外一致** |

**判据**：一个用 Python 写的评分规则，**不加任何运行时胶水**就能被两侧接入件注册并在闸门 3/4 里跑通
（工具真的被调用），且带 `--selftest` 与"同输入同输出"的确定性自证。

**代价/边界**：进程边界有启动开销与序列化约束（结果须 JSON 可表达）；要定义错误语义（非零退出 → 工具错误）
与超时；**进程内与进程外语义必须一致**，否则同一业务会有两种行为。这属于"隔离靠进程/文件系统"（P-b）的延伸。

**可逆性**：描述文件是**新增**一层。若不采用，删掉该契约、共享目录退回纯模块即可 ——
接入件只依赖描述，不受影响。

## D-0013 接入件按运行时固定，不应按能力重复写（登记，未实现）

**背景**：今天每增加一个业务能力，都要手写两份接入件（示例里 pi 28 行 / dsh 64 行）。而同一运行时的接入件
**几乎是同一段样板**：读描述 → 翻译参数 DSL → 注册工具 → 转发执行 —— 业务不同，接入件几乎不变。

**问题**：样板按能力复制 ⇒ 必然漂移（本项目已经在"两份实现必漂移"上交过多次学费）；
而且"接入件里不许出现业务规则"这条只能**逐文件人工检查**，检查不了就只能靠自觉。

**方向（推荐）**：把接入样板**上收到基座** —— 每个运行时提供一个**通用桥**
（pi：一个基座扩展；dsh：一个 cordis 插件），按能力描述**通用地**注册并执行。
业务方**不写接入件**，只提供"描述 + 可执行体"。这与既有原则一致：**能力在基座、选择与内容在智能体**。

**备选与取舍**：

| 方案 | 好处 | 代价 |
|---|---|---|
| **通用桥**（推荐） | 新增能力**零胶水**；运行时怪癖集中一处；"接入件里不许有业务规则"不再需要检查（没有逐能力接入件） | 桥是基座代码，须声明为基座不变量增强并纳入闸门 2 集合断言；桥成为单点，需维护 |
| 脚手架模板 | 立刻可用 | 每个能力仍存一份样板 ⇒ 漂移只是被推迟 |
| 维持现状 | 最灵活 | 重复最多；定制越多越难统一 |

**逃生门**：需要高度定制接入的能力**仍允许**手写接入件（且必须在声明里显式标注"定制接入"），
避免通用桥变成"想绕开就得改基座"。

**判据**：新增一个业务能力**只新增描述与实现，不新增运行时胶水**；
`enhance/shared-agnostic` 之外不再需要逐文件检查接入件。

**可逆性**：桥是**新增**层，手写接入路径保留 ⇒ 回退只需不再使用桥。

## D-0014 产品形态是两层：基座镜像 + 上层业务镜像（定制分层与验收口径）

**背景**：评审意见 —— "智能体开发不只是 skills、MCP，重点是**定制 harness**（尤其钩子，更深是 agent loop）"；
以及"agent-base 现在基本是**当作一个进程在用**，挂上配置在跑，很多具体应用问题解决不了"。
同时定位被澄清：**agent-base 是底座；最终可用的智能体是它之上的一个更高级容器镜像**，业务开发在上层充分发挥。

**决定**：

1. **两层产品模型**。
   - **基座层**（本仓库）：不变量（轨迹 schema、参数分层、产物只读、不静默失败）+ 契约（定义/渲染/启动）+
     闸门（validate/doctor/probe/smoke + conformance）+ 基座镜像（运行时与依赖预装）。
   - **业务层**（`FROM agent-base:<ver>`）：业务代码（任意语言）、钩子/策略/审批、loop 定制、
     服务形态（RPC/SDK/API/ACP、多会话）、业务自己的依赖与验收。**自由度在上层**。
2. **定制按 L0–L4 分层，基座对每层明确"支持到哪、怎么验"**（见设计文档 §3）：
   L0 声明式配置 ✅ · L1 薄接入 ✅（两侧实测）· L2 钩子 ⚠️（**传输已通，契约与验收缺**）·
   L3 loop ❌ · L4 服务形态 ❌。
3. **配置 / 服务分界线对外明说**：启停与参数、工具 allow/deny/ask、沙箱模式、模型名单、技能与连接器
   → **配置**；审批通道、LLM/工具网关、集中审计与成本遥测、检索与记忆、多租户隔离
   → **代码/服务**。别让使用者以为"改 JSON 就能上生产"。
4. **上层镜像的最低门槛（两步，缺一不可）**：
   ① **能定制**：产物可烤进镜像（已具备：`AGENT_ARTIFACT_DIR` 默认路径 + 目录存在即可）；
   上层能在**镜像内**加钩子（今天不行 —— 扩展必须在渲染产物里，而镜像里没有渲染器）。
   ② **能自证**：镜像内能跑通"四闸门 + 钩子触发"的证据链（今天不行 —— 镜像里没有闸门工具）。
5. **验收口径**：上层的每种深度定制都必须留下**可验证证据**（钩子触发留痕、策略拒绝可断言、审批可追溯）。
   验不了的，在文档与产物里标"未验证"，不许写成"已支持"。

**代价/边界**：
- 深度定制**不可跨运行时等价**（pi 与 dsh 的事件名、返回语义、失败语义都不同；
  例：钩子失败时 pi 的 `tool_call` 阻断工具，dsh 的 CLI 钩子桥选择不阻断 —— **语义相反**）。
  跨运行时等价承诺只覆盖 L0/L1。
- 上层**必然要写代码**：dsh 的 patch row 只能覆盖 `config`/`disabled`，改不了 `name`、删不掉 row，
  "替换实现"必须"禁用 + 插入 + 插件"；pi 的深度定制要写扩展。
- 基座镜像要多带验证工具（体积增长），换来的是"上层镜像可自证"。

**可逆性**：两层模型是**文档与契约层的新增**（不改现有渲染/启动路径）。若回到"单层、只跑配置"，
撤掉"上层镜像接入缝"与 §23 的演进项即可；已验证的 L0/L1 不受影响。

**相关**：设计文档 [`docs/design/2026-09-26-harness-customization.md`](../design/2026-09-26-harness-customization.md)；
待办 §23；前序决策 D-0012（多语言共享）、D-0013（接入件固定）。

## D-0015 基座能力 = 可执行的验收 + 契约不变量 + 可扩展的缝；规范措辞改为「保证/允许/不管」三段式

**背景**：评审追问 —— "只做 skills/MCP 根本不需要 agent-base 这个多余的东西，直接做就行，那基座能力到底在哪里？"
以及"应该对完整的企业智能体应用开发提供充分支持，**而不是说我的规范不允许我这么做**"。

**先承认对的部分**：中性定义 + 技能 + MCP 配置 + 渲染这一层（今天的 L0/L1）**不构成基座能力** ——
用 pi/dsh 直接做更快。基座若只停在这里，它就是多余的。

**判据（用来判断"什么配叫基座能力"）**：
> 如果基座明天消失，一个团队做同一个智能体，会不会**多花好几天**、并且**做得更不一致**？
> 会 → 那项是基座能力；不会 → 那项是多余的东西，该删掉或降级成示例。

按这把尺子，**今天真正算数的是四项**：

| 资产 | 为什么算 |
|---|---|
| **可执行的验收**（四闸门 + 零凭据假网关 + C1–C10） | 离线、无密钥、跨运行时回答"可用/不可用"，且给出证据链；自己做只会"跑一下看看" |
| **跨运行时/跨环境的契约**（定义→渲染 · 统一轨迹 · 参数分层） | 同一份定义跨环境成立；差异必须声明，不许沉默 |
| **运行与交付不变量**（产物只读+暂存隔离 · 参数四法 · 显式失败 · 镜像内 LLM 配置） | 每个项目都会踩的坑，基座把它变成默认 |
| **公共回归资产**（harness 版本 pin · 镜像输入指纹 · 13 个自检） | 升级/换模型/改镜像时有回归网，随时间复利 |

**决定**：

1. **基座能力的一句话定义**：**把"可用"变成可执行、可复算、跨项目一致的判据**。
2. **"充分支持"的实现方式**：全生命周期每层都给【**契约 + 判据 + 逃生门**】
   （定义/渲染/本地运行/交付镜像/**派生镜像（业务层）**/服务形态/运维；表见设计文档 §3）。
   尤其：业务层深定制（钩子/loop/服务）**在上层镜像里做**，基座给缝、给判据、给样例。
3. **规范措辞原则**：从"**不许**"改为"**保证 / 允许 / 不管**"三段式：
   - ① **基座保证并验证的**（进 schema/契约，有判据，改动走闸门与 conformance）；
   - ② **基座允许但不保证的**：**开放命名空间**（如 `x-*` / `customizations:`）与可扩展的 `kind`；
     内容**原样透传**到产物与清单，并在报告里**标注"未验证"**；`additionalProperties:false` **保留**（拼写错误仍能拦住）；
   - ③ **基座明确不管的**：业务逻辑、策略内容、审批/网关/审计实现 —— 给缝，不给判据。
   **②与"不静默失败"不冲突**：不认识的**声明**要保留并标注；不认识的**内容**不许造成静默行为。
4. **不做**：不阻止保证范围外的做法（给缝、给样例、给标注，不设卡）；不假装支持（没判据的一律标"未验证"）。

**代价/边界**：开放命名空间会让产物里出现基座不理解的字段 ⇒ 清单与报告必须**如实列出**"未验证声明"，
否则会给人一种"基座验证过了"的错觉；`core/` 的层纪律仍然有效（基座代码不许出现运行时名）。

**可逆性**：措辞与开放命名空间是**新增**（不改现有必填字段语义）；若要收紧，删掉开放区即可。

**相关**：设计文档 [`docs/design/2026-09-26-base-value-and-openness.md`](../design/2026-09-26-base-value-and-openness.md)、
[`docs/design/2026-09-26-harness-customization.md`](../design/2026-09-26-harness-customization.md)；待办 §24。

## D-0016 开发者契约：起点与保证，而不是约束

**背景**：评审认可 D-0014 的三点（① 给上层镜像明确的接入缝 ② 让上层深定制仍可声明可验证 ③ 保住底座不变量），
并给出总原则：

> **"开发者如何深度开发是他的能力；从 agent-base 基座开始，能给他一个足够好的起点以及开发的保证，而不是约束他。"**

**决定**：把这条原则落成**对外可引用的开发者契约**（`docs/13-developer-contract.md`），三节：

1. **起点**：从零到一个跑起来的智能体，基座给什么（镜像 / 派生骨架 / 参考项目 / 一条命令跑通 / 本地真跑 / 演练），
   以及**还缺什么**（派生镜像骨架、镜像内自证、镜像内加钩子、钩子触发闸门、loop 与服务形态声明面）——
   缺口不藏，登记进路线图。
2. **保证**：逐条列出"你可以依赖什么"，**每条都指向一条真实判据**（闸门/自检/conformance 用例），
   并标注现状（✅ 已成立 / ⚠️ 口径不完整）。同时给出**稳定性承诺**：哪些接口跨版本不变
   （`apiVersion`/schema `$id`、轨迹 schema、入口环境变量、产物清单字段、镜像 LABEL），哪些可能变。
3. **不约束**：加自定义字段、手写接入件、在镜像里加钩子/loop/服务、绕过基座直接跑运行时 —— **都允许**；
   自定义内容**原样透传 + 标注"未验证"**（与 D-0015 的开放命名空间一致）。
   唯一硬边界：**不静默**（声明要保留标注；内容不许静默行为）。

**并明确基座自己的自我检验**：
> 凡是声称"已支持"的能力，必须能指向一条真实判据；**指不出来的，降级为"示例"或"未验证"**，不许留在"已支持"清单里。

**代价/边界**：契约一旦对外承诺就要守（尤其 §3 的稳定性清单）；
`docs/13` 表里的"✅"必须随实现变化更新（表里已经出现过期条目，见 D-0014 的 D7 教训）。

**可逆性**：契约是**文档层承诺**，不改行为；若某条承诺站不住，撤掉该行或降级标注即可。

## D-0017 harness 层契约（`enhancements.schema.json`）随**基座版本**演进，不进 `apiVersion`

**背景**：路线图 §23 E1 要给钩子声明立"事件名集合"的判据。落地时发现 schema 里的 `event: <字符串>`
**表达不了基座自己的轨迹扩展**（`adapters/pi/seed/extensions/trace.ts` 订阅 6 个事件），于是改成
`events: [...]`（数组）—— 这是**改字段名**，按 CHANGELOG §1.2 属于"定义契约破坏性变更"，字面上要求
`apiVersion` 升版。

**问题**：`apiVersion` 是 `agent.yaml` / `connectors.yaml` / `enhancements.yaml` **共用**的一个 token，
而 `harness/<h>/enhancements.yaml` 在 D-0014/D-0015 里已被明确划为**harness 层、本就不在可移植性承诺内**
（两套扩展机制根本不同）。为一个 harness 层字段改名去升中性定义的 `apiVersion`，会迫使**所有**定义连
`agent.yaml`、`connectors.yaml` 一起动 —— 代价与收益不相称，而且会把两个变化节奏不同的契约绑死。

**决定**：

1. **`apiVersion` 只承诺中性定义**（`agent.yaml` / `connectors.yaml` + `skills/`）——与 CHANGELOG §1.1 的原话一致，
   中性定义这次**一个字都没改**。
2. **`enhancements.schema.json` 随基座版本（`package.json` 的 `version`）演进**：改名/收窄/删字段必须
   ①写 CHANGELOG（含一句迁移写法）②**响亮失败**（旧写法在闸门 1 红，不许静默忽略/静默跳过）。
3. 本次改动按此办理：CHANGELOG 0.1.0 下立"破坏性：`event` → `events`"条目 + 迁移写法；
   仓内唯一的使用者（基座 seed）当场更新。

**被否的方案**：把 `apiVersion` 升到 `agent-base/v2` 并让基座同时支持两个版本。
代价：6 个示例 + 模板 + fixtures 全部要动；且要新增"按 apiVersion 分派 schema"的机制 ——
为一个尚未发布、且属于 harness 层的字段，不成比例。

**代价/边界**：`apiVersion` 的语义**窄化**为"中性定义契约版本"（此前含糊地覆盖所有带该字段的文件）——
这条要靠 CHANGELOG §1.1 与 `docs/13` §3 的表述保持；将来若 harness 层契约真要独立版本号，
应当**新立**一个字段（如 `enhancementsVersion`），而不是复用 `apiVersion`。

**可逆性**：高。若判定应当升 `apiVersion`，本次改动可在 CHANGELOG 补条目 + 批量改 `apiVersion` 完成，
schema 与判据不用动（判据只看字段形状，不看版本号）。

## D-0018 主运行时定 `pi`；多语言业务代码走"双通道 + 镜像预装 Python"；能力包延后

**背景**：三件事此前一直等用户拍板（决策材料见 `docs/plans/OPEN-DECISIONS.md`），2026-09-28 用户答复：**1 选 A、2 做、3 等**。

**决定 1 —— 主运行时 = `pi`（候选 `dsh` 继续维护，不占关键路径）**。
理由（实测事实见 `docs/design/2026-09-27-runtime-selection-facts.md`，机器生成）：
① 基座的差异化是"说过的话都有判据"，而 `dsh` 的**钩子事件集合未穷举** ⇒ 那一侧的钩子声明制度性地只能标「未验证」；
② `dsh` 无头模式**不派发斜杠命令**（`capabilities.commandsHeadless: unsupported`，实测）⇒ 会话内能力进不了自动化验证网，
而 L1 的 E5–E8（loop/服务形态）正好要靠会话内操作验证；
③ `pi` 是稳定版（`0.87.1`），主运行时不该是会被上游升级打断的那个。
**代价（明说）**：`pi` 没有原生 `hmr`、原生 MCP、原生权限预设 + 审批（这些在 `dsh` 上是原生的，在 `pi` 上靠基座种子扩展补）。
**可逆性**：翻转只需改默认 HARNESS 与示例默认 runtime，设计不动（两侧 conformance 与豁免都继续维护）。

**决定 2 —— 做多语言业务代码（D-0012/D-0013 落地）**，两个分叉按建议执行：
- **A2 双通道**：JS/TS 业务走**进程内**（保住 `make local` 的迭代速度）；其他语言走**进程边界**；
  "进程内/外语义一致"必须有自检（这是 D-0012 判据的一部分，不是可选项）。
- **B1 镜像预装 Node + Python**（先只加 Python）：不依赖能力包，L6 因此不被 L4 拖住。
  预装项进 `preinstall.yaml` + 双架构可得 + 离线可用（已有自检管预装集）。

**决定 3 —— 能力包（L4/bundles）延后**，排在决定 2 之后（语言运行时将来正好可由能力包按需提供，那样 B2 才成立）。

**边界**：本决定只定"选哪个/走哪条路"，不改任何已有公开契约；能力描述契约的形状仍以
`docs/design/2026-09-27-capability-description-contract.md` 为准，实现时若发现形状需要调整，改那份提案并记录理由。
