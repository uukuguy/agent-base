# Decisions

> 架构决策与理由（既不是「当前状态」也不是「进度」）。

## 2026-09-25 · 基座镜像的构建与分层

**决策**：镜像**按架构分开构建**（原生优先 + 模拟隔离），再用 `docker-container` 驱动的 builder 合并成多架构 manifest list（OCI 归档落盘）；**生成的构建输入不放在 `core/`**，落 `dist/image/context/`。

**理由**：
- 一次 `--platform a,b` 在 arm64 机器上模拟 amd64 装 11 个包 + 2 个 harness，慢且**一架构失败毁掉整个构建**，排查时分不清代码问题与模拟问题。
- 本机默认 `docker` 驱动**不支持 OCI 导出**（实测报错），多架构打包必须换 builder 驱动。
- 坐标表必须写出包名，而**包名本身含 harness 名**，放在 `core/` 会踩 `core/harness-name` 这条分层规则。正确解法是纠正分层（生成物不是源码），而不是放宽规则。

**代价/边界**：多架构归档约 1.7 GB，只落本地；推送路径待 I2（内网能否直连镜像仓库）确认。
## D-0011 模型名是环境属性，不是行为属性（判据修正）

**背景**：设计里「行为烤、参数下放」的判据是「这个字段改了，同一个输入会不会得到不同行为」。按这条，
`model.name` 被归入制品层，并进了 `params.yaml` 的禁止清单（出现在参数层即违规，闸门 1 与 C8 双双拦截）。

**问题**：容器里"配置 LLM"于是只剩端点与凭据 —— 而实际部署中**端点与模型名是绑在一起的**
（内网网关只服务它有的那几个模型；dev 与 prod 的模型名常常不同）。端点既然运行期给，
模型名就没有理由烤死。判据对"环境属性"这一类用粗了。

**决定**：判据改为 —— **这个值是不是随部署环境而变**？是 → 参数层（运行期注入，必须可校验、可追溯）；
否 → 制品层。据此：

| 字段 | 归属 | 理由 |
|---|---|---|
| `model.route` | 制品层 | 它决定端点/凭据/模型名三个引用名，是"这份制品跑在哪条路由上"的身份 |
| `model.name` | **参数层** | 环境属性；定义里的值退化为**默认值** |
| `model.reasoningEffort` | 制品层 | 行为属性未变 |

**配套**（防止"可配置"变成"随便配"）：路由目录声明它服务哪些模型；闸门 1 与启动期都按该名单校验；
模型名记进轨迹（`model.request.model`）。**改了行为就必须改说法**：C8 原来的"模型选择禁止注入"
用例换了靶子（`tools.deny` / `persona` 仍是禁止项）。

**可逆性**：若企业实践表明模型名应当烤死，回退只需把 `model-name` 从 allowed 移回 forbidden、
把 `model.name` 的层改回 artifact —— 三处改动，无隐性依赖。

## D-0012 共享业务逻辑必须支持多种语言（登记，未实现）

**背景**：`harness/shared/*.mjs` 由两侧接入件以 **ESM 模块**方式 import ⇒ "可共享"目前只在
JavaScript/Node 世界里成立。业务团队的语言未必是我们的运行时的语言（Python / Go / Java 都常见）。

**问题**：如果共享层只能是 JS 模块，那"业务代码可共享"就不是一条架构性质，而只是"恰好都用 JS"。

**方向**（未实现，先登记）：把"共享"从**模块**提升为两类产物：

| 产物 | 形态 | 作用 |
|---|---|---|
| **能力描述** | 语言无关（JSON/YAML）：name / description / 参数 schema / 结果 schema / 确定性要求 | 各运行时接入件的**唯一输入**；不再靠读代码了解能力 |
| **可执行体** | **任意语言**：以**进程边界**调用（argv / stdin stdin-JSON / stdout JSON） | 业务实现；语言自由 |
| （可选）进程内快路径 | JS/TS 模块（今天的形态） | 同语言时省掉进程开销；**语义必须与进程外一致** |

**判据**：一个用 Python 写的评分规则，**不加任何运行时胶水**就能被两侧接入件注册并在闸门 3/4 里跑通
（工具真的被调用），且带 `--selftest` 与"同输入同输出"的确定性自证。

**代价/边界**：进程边界有启动开销与序列化约束（结果须 JSON 可表达）；要定义错误语义（非零退出 → 工具错误）
与超时；**进程内与进程外语义必须一致**，否则同一业务会有两种行为。这属于"隔离靠进程/文件系统"（P-b）的延伸。

**可逆性**：描述文件是**新增**一层。若不采用，删掉该契约、共享目录退回纯模块即可 ——
接入件只依赖描述，不受影响。

## D-0013 接入件按运行时固定，不应按能力重复写（登记，未实现）

**背景**：今天每增加一个业务能力，都要手写两份接入件（示例里 pi 28 行 / dsh 64 行）。而同一运行时的接入件
**几乎是同一段样板**：读描述 → 翻译参数 DSL → 注册工具 → 转发执行 —— 业务不同，接入件几乎不变。

**问题**：样板按能力复制 ⇒ 必然漂移（本项目已经在"两份实现必漂移"上交过多次学费）；
而且"接入件里不许出现业务规则"这条只能**逐文件人工检查**，检查不了就只能靠自觉。

**方向（推荐）**：把接入样板**上收到基座** —— 每个运行时提供一个**通用桥**
（pi：一个基座扩展；dsh：一个 cordis 插件），按能力描述**通用地**注册并执行。
业务方**不写接入件**，只提供"描述 + 可执行体"。这与既有原则一致：**能力在基座、选择与内容在智能体**。

**备选与取舍**：

| 方案 | 好处 | 代价 |
|---|---|---|
| **通用桥**（推荐） | 新增能力**零胶水**；运行时怪癖集中一处；"接入件里不许有业务规则"不再需要检查（没有逐能力接入件） | 桥是基座代码，须声明为基座不变量增强并纳入闸门 2 集合断言；桥成为单点，需维护 |
| 脚手架模板 | 立刻可用 | 每个能力仍存一份样板 ⇒ 漂移只是被推迟 |
| 维持现状 | 最灵活 | 重复最多；定制越多越难统一 |

**逃生门**：需要高度定制接入的能力**仍允许**手写接入件（且必须在声明里显式标注"定制接入"），
避免通用桥变成"想绕开就得改基座"。

**判据**：新增一个业务能力**只新增描述与实现，不新增运行时胶水**；
`enhance/shared-agnostic` 之外不再需要逐文件检查接入件。

**可逆性**：桥是**新增**层，手写接入路径保留 ⇒ 回退只需不再使用桥。

## D-0014 产品形态是两层：基座镜像 + 上层业务镜像（定制分层与验收口径）

**背景**：评审意见 —— "智能体开发不只是 skills、MCP，重点是**定制 harness**（尤其钩子，更深是 agent loop）"；
以及"agent-base 现在基本是**当作一个进程在用**，挂上配置在跑，很多具体应用问题解决不了"。
同时定位被澄清：**agent-base 是底座；最终可用的智能体是它之上的一个更高级容器镜像**，业务开发在上层充分发挥。

**决定**：

1. **两层产品模型**。
   - **基座层**（本仓库）：不变量（轨迹 schema、参数分层、产物只读、不静默失败）+ 契约（定义/渲染/启动）+
     闸门（validate/doctor/probe/smoke + conformance）+ 基座镜像（运行时与依赖预装）。
   - **业务层**（`FROM agent-base:<ver>`）：业务代码（任意语言）、钩子/策略/审批、loop 定制、
     服务形态（RPC/SDK/API/ACP、多会话）、业务自己的依赖与验收。**自由度在上层**。
2. **定制按 L0–L4 分层，基座对每层明确"支持到哪、怎么验"**（见设计文档 §3）：
   L0 声明式配置 ✅ · L1 薄接入 ✅（两侧实测）· L2 钩子 ⚠️（**传输已通，契约与验收缺**）·
   L3 loop ❌ · L4 服务形态 ❌。
3. **配置 / 服务分界线对外明说**：启停与参数、工具 allow/deny/ask、沙箱模式、模型名单、技能与连接器
   → **配置**；审批通道、LLM/工具网关、集中审计与成本遥测、检索与记忆、多租户隔离
   → **代码/服务**。别让使用者以为"改 JSON 就能上生产"。
4. **上层镜像的最低门槛（两步，缺一不可）**：
   ① **能定制**：产物可烤进镜像（已具备：`AGENT_ARTIFACT_DIR` 默认路径 + 目录存在即可）；
   上层能在**镜像内**加钩子（今天不行 —— 扩展必须在渲染产物里，而镜像里没有渲染器）。
   ② **能自证**：镜像内能跑通"四闸门 + 钩子触发"的证据链（今天不行 —— 镜像里没有闸门工具）。
5. **验收口径**：上层的每种深度定制都必须留下**可验证证据**（钩子触发留痕、策略拒绝可断言、审批可追溯）。
   验不了的，在文档与产物里标"未验证"，不许写成"已支持"。

**代价/边界**：
- 深度定制**不可跨运行时等价**（pi 与 dsh 的事件名、返回语义、失败语义都不同；
  例：钩子失败时 pi 的 `tool_call` 阻断工具，dsh 的 CLI 钩子桥选择不阻断 —— **语义相反**）。
  跨运行时等价承诺只覆盖 L0/L1。
- 上层**必然要写代码**：dsh 的 patch row 只能覆盖 `config`/`disabled`，改不了 `name`、删不掉 row，
  "替换实现"必须"禁用 + 插入 + 插件"；pi 的深度定制要写扩展。
- 基座镜像要多带验证工具（体积增长），换来的是"上层镜像可自证"。

**可逆性**：两层模型是**文档与契约层的新增**（不改现有渲染/启动路径）。若回到"单层、只跑配置"，
撤掉"上层镜像接入缝"与 §23 的演进项即可；已验证的 L0/L1 不受影响。
