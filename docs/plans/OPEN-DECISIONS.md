## 决策 1：主运行时选谁（`pi` / `dsh` / 暂不定）

**拍板后解锁**：L1 的 E5–E8（loop/服务形态的声明面与判据）——那是 L1 唯一剩下的部分。

**事实材料**（机器生成，闸门 1 守同步）：[`docs/design/2026-09-27-runtime-selection-facts.md`](../design/2026-09-27-runtime-selection-facts.md)
复跑：`make gen-selection-facts`（生成）· `make validate` 里的 `docs/selection-facts-sync`（守同步）

| 维度 | `pi`（当前主运行时） | `dsh`（候选） |
|---|---|---|
| 版本形态 | `0.87.1` **稳定**，pin 在仓库里 | `0.1.7-rc.1` **预发布** |
| 声明面覆盖 | 20 supported / 22 verified / 1 unknown | **23 / 23 verified** |
| 钩子事件集合 | **已穷举**（39 个，逐行数过）⇒ 钩子声明**可校验** | **未穷举** ⇒ 钩子只能标「未验证」 |
| 原生能力 | 无 `hmr`（改配置要重启）· MCP 靠基座种子扩展 · 审批靠扩展 | 原生 `hmr` · 原生 MCP · 原生权限预设 + 审批（**fail-closed**） |
| 会话内能力能否自动化验证 | **能**：RPC 可驱动斜杠命令（`/project skills` 端到端自检在） | **不能**：无头模式把它当提示词（实测；`commandsHeadless: unsupported`） |
| 基座不变量落地 | `trace`/`project-info`/`verify-container` 都是产物内声明 | `project-info`/`verify-container` 产物内声明；`trace` 走**事后映射** |

**我的建议：选 `pi` 为主运行时，`dsh` 作为**持续维护的第二目标**（不急收敛到一个）。**

理由（与基座的核心承诺直接相关）：
1. 基座的差异化是"**说过的话都有判据**"。钩子事件集合在 `dsh` 上未穷举 ⇒ 那一侧的钩子声明永远只能标"未验证"，
   这是**制度性**的弱化，不是工程量问题。
2. 会话内能力（`/project`、`/verify-container`）在 `dsh` 上进不了自动化验证网（实测无头不派发命令）⇒ E5–E8 那些
   形态正好要靠会话内操作验证，选它当主运行时会让**新能力的验证成本翻倍**。
3. `pi` 是稳定版，`dsh` 是预发布：主运行时不该是会被上游升级打断的那个。

**若你认为"能力面更宽"更重要**（原生 HMR / MCP / 审批确实好用），那就反过来选 `dsh`——代价是上面的 1/2 两条要接受，
并且要给 `project-info` 之类的不变量补落地（V3 已完成 ✓，所以这条路已经比我上轮估计的更短）。

**不拍的代价**：E5–E8 一直做不了 ⇒ loop 预算、时长上限、并发上限、会话生命周期这些**生产形态的能力**没有声明面与判据；
其余两件事也会被拖（决策 2 的契约要"按两侧交集"设计，见下）。

## 决策 2：能力描述契约的两个分叉（A 与 B）

**拍板后解锁**：L6 全部（D-0012 多语言共享 + D-0013 接入件上收为通用桥）。

**事实材料**：[`docs/design/2026-09-27-capability-description-contract.md`](../design/2026-09-27-capability-description-contract.md)
（三件套：描述 / 可执行体 / 进程边界协议 / 各闸门判据 / 迁移三步 / 10 个待拍点）

| 分叉 | 选项 | 我的建议 |
|---|---|---|
| **A：JS 业务走哪条路** | A1 统一进程边界（语义一条，但每次工具调用起一个进程，**本地迭代变慢**）· **A2 双通道**（JS 走进程内保持快；其他语言走边界；需自检守"进程内/外一致"）· A3 先只做边界 | **A2** —— `make local` 的"快"是开发入口的卖点，不该为一致性牺牲；一致性用自检守 |
| **B：非 JS 语言运行时从哪来** | **B1 镜像预装 Node + Python**（不依赖别的线）· B2 靠 L4 能力包按需提供（**会依赖决策 3**）· B3 不做运行时 | **B1，先只加 Python** —— 覆盖绝大多数"评分/清洗/规则"场景；Go/Java 等出现真实需求再加 |

**拍完立刻能做什么**（3 步，估 1–2 个工作段）：
1. 描述契约 + schema + **一个非 JS 语言的"描述 + 实现 + 通用桥"**（含"零胶水注册"自检）
2. 迁移 `examples/change-risk-review`：删掉两份手写接入件，断言**工具数不变、两侧仍可用**
3. 回归口径：`make regression` 全绿 + 两侧 conformance

**不拍的代价**：业务团队用 Python/Go 写规则就必须自己写胶水 —— "业务代码可共享"这条架构性质**只在 JS 世界成立**。

## 决策 3：L4 能力包（bundles）现在启动吗

**你此前的决定是"择机、不占当前队列"**，这里只补一份"现在启动 vs 继续等"的对照。

**事实材料**：[`docs/design/2026-09-26-capability-bundles.md`](../design/2026-09-26-capability-bundles.md)（设计完成、未实现）

| 现在启动 | 继续等 |
|---|---|
| 交互式 AI Coding 的便利性上来（能力"打成一包、按需开关"）；这是你最初提的痛点 | 保持当前队列最短；但每次要在镜像里加编程能力仍需逐个选 |
| 与决策 2 有交叠：**语言运行时正好可以由能力包按需提供**（那样 B2 才成立） | 若先拍 B1（镜像预装 Python），L4 就不再是 L6 的前置 |

**我的建议：先拍决策 1 与 2；L4 放在决策 2 之后**——除非你要的是"交互式 AI Coding 的便利"本身（那就 L4 先做，
它与前两件互不阻塞，只是会让 B1/B2 的选择多一层考量）。
