# 10 · 运行时选型：pi 与 dsh

**先说结论的形式**：两个运行时**并列可选**，不是主从。当前默认 pi（更稳）。
**这份对比不构成绑定** —— 它描述差异，不规定你必须用哪个。定位可以按比较数据翻转，
翻转只改默认值，不改设计。

## 一、能力对比（数据来自各自 `adapter.yaml` 的声明，逐条标了依据）

| 能力 | **pi** | **dsh** | 实务含义 |
|---|---|---|---|
| 原生参数插值 | ❌ 不支持 | ✅ 支持 | pi 的 `models.json` **不对 `baseUrl` 做环境插值**（只对 apiKey/headers）⇒ 渲染器必须产出 `.tmpl`、启动期渲染。dsh 没这个约束 |
| 运行期写配置 | ✅ 支持 | ⚠️ 有限制 | pi 连 `--list-models` 都会写产物目录 ⇒ 必须暂存可写副本 |
| 隐式技能源 | ⚠️ 两个 | ⚠️ 多个 rank 根 | **两边都关不掉**，只能靠文件系统隔离 + 闸门 2 的集合断言 |
| 配置 include | ❌ 不支持 | ⚠️ 有限制 | pi 不能多文件拼接 ⇒ 构建期扁平化 |
| 热重载（hmr） | ❌ 不支持 | ✅ 支持 | pi 改配置要重启；本地迭代靠交互模式 |
| 子智能体 | ⚠️ 有限制 | ✅ 支持 | pi 有 subagent 扩展但未跑真实委派 |
| OS 级沙箱 | ❌ 不支持 | ⚠️ 有限制 | **两边都不能只靠运行时兜安全下限** ⇒ 容器层承担硬下限（只读根/非 root/丢能力/断网） |
| 权限模型 | 🧩 靠扩展 | ✅ 原生 | pi 靠扩展；dsh 原生有审批与权限预设 |
| 轨迹产出 | ✅ 支持 | ✅ 支持 | 但**来源不同**，见下节 |
| MCP 客户端 | ❌ **原生没有** | ✅ 原生支持 | 这是最大的一条差异，见下 |
| 运行模式 | interactive / oneshot / rpc / debug | 同左 | 一致 |
| 业务级增强形态 | `file`（产物里的扩展文件） | `package`（cordis 插件 npm 包） | 机制根本不同 ⇒ 必然不可移植 |

> 取值含义：✅ `supported` · ⚠️ `partial`（限制写在 `adapter.yaml` 的 note 里）·
> ❌ `unsupported` · 🧩 `extension`（靠扩展实现，不是缺陷）。
> 每条 note 都标了依据（【实测】/【文档】/【待实测】），有疑问去看那个文件。

## 二、四条真正会影响你选择的差异

### 1. MCP（连接器）

| | pi | dsh |
|---|---|---|
| 原生支持 | ❌ 没有 | ✅ 有 |
| 声明了连接器会怎样 | **渲染直接失败**（并说明原因） | 正常渲染，每服务器一条 row |

**pi 侧的"直接失败"是故意的**：如果渲染器选择跳过不支持的连接器，你会得到一个**没有连接器的
智能体**而你以为连上了。要用 MCP，先选一个第三方客户端扩展并做成基座种子。
**所以：以"连外部系统"为主的验证，现阶段 dsh 更省事。**

### 2. 轨迹来源

| | pi | dsh |
|---|---|---|
| 主来源 | **回调式**：订阅运行时 loop 回调 | **`--json` 的 run events** |
| 能拿到 | **实际发出去的请求体**（真实 `tools` 数组与 `stream` 标志）、原生 `toolCallId` | `callId`（可直接配对）、`status`/`text`/`final` |
| 拿不到 | 网关侧发生了什么 | **请求信息**（它不告诉你发了几个工具） |
| 兜底 | 事后映射原生事件流 | 会话文件（zstd 压缩 JSONL v4；`tool/result` **没有 callId**，只能按 step 顺序配对） |

**实务结论**：闸门 3 的"工具数/流式"断言，对 dsh 改从**端点侧**取证（零凭据假网关记录它收到了什么）。
从端点看两边一样 —— 这也是为什么那条判据现在是跨运行时中性的。

### 3. 工具边界的粒度

| | pi | dsh |
|---|---|---|
| 生效方式 | 运行参数 `--exclude-tools`（**手工直接启动会绕过**） | 禁用对应 tool row |
| 粒度 | 每个工具一个 | ⚠️ **更粗**：`read`/`write`/`edit` 是**同一个** `tool-fs` row |

**实务结论**：「禁 `write` 但保留 `read`」这种意图在 dsh 侧**做不到**（禁一个等于禁三个）。
要这种精度就用 pi，或者接受更宽的边界。差异已进 `exemptions.yaml`。

### 4. 技能可观测性

| | pi | dsh |
|---|---|---|
| 口径 | 能问运行时要到「**实际加载了哪些**」 | 只能看到「**配置了哪些目录**」+ 核对文件就位 |

**实务结论**：dsh 侧闸门 2 的技能断言**强度较弱**（口径是"已配置且就位"，不是"已被发现"）。
这不影响正确性，但影响结论的把握 —— 已在 `exemptions.yaml` 标注，比对时不许当作等价。

## 三、什么场景用哪个

| 你的场景 | 建议 | 理由 |
|---|---|---|
| 纯技能型验证（无外部系统） | **两个都行** | 两边都全绿；pi 更稳 |
| 要连 MCP / 外部系统 | **dsh** | pi 原生没有 MCP 客户端 |
| 要精细化工具边界（禁 write 留 read） | **pi** | dsh 的工具粒度是整行的 |
| 要轨迹里带上"实际发出的请求" | **pi** | 回调式能拿到请求体 |
| 要审批/权限的原生支持 | **dsh** | pi 靠扩展 |
| 要最大稳定性 | **pi** | dsh 是 `0.1.7-rc.1`（预发布，接口可能变） |
| 想比较两个运行时的差异 | 都跑一遍 | 同一份定义，`make verify HARNESS=pi` / `HARNESS=dsh` |

## 四、两个运行时"做不到等价"的地方（跨运行时比对时必须知道）

以下都写在各自的 `exemptions.yaml` 里，**比对时必须在报告里标注**，不许当作等价：

| 维度 | 差异 |
|---|---|
| 连接器 | pi 不支持 MCP（需外部客户端）；dsh 原生支持 |
| 工具边界粒度 | dsh 的 `read`/`write`/`edit` 是同一 row |
| 技能集合口径 | dsh 只能给"已配置且就位"，弱于 pi 的"实际加载" |
| 审批判定（`tool.call.decision`） | 两边目前都是 `unobserved`（观测不到就不写 `allow`） |
| 推理强度 | dsh 侧**尚未映射** `model.reasoningEffort` |
| 工具命名 | 两个运行时的工具名不同 —— 业务不应依赖工具名 |
| 提示词文本 | 人设最终拼装方式由运行时决定 |
| token 计数/延迟 | 运行时特性，不是可移植性承诺 |

## 五、这个对比会怎么演化

- 两个运行时都要**通过全部十项准入门槛**才算接入（当前：**两边都 10/10 全绿**）
- 定位可依比较数据翻转，**翻转只改默认值**（`HARNESS` 默认值与示例默认运行时），不改设计
- 双运行时的目的不只是可移植，更是**比较选型** —— 将来可能收敛到一个
- 新增第三条轨时，准入成本就是 `conformance` 那十项（用例本身就是契约的可执行形态）
