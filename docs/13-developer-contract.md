# 13 · 开发者契约：起点、保证、不约束

| | |
|---|---|
| 状态 | 契约定义（**待评审**）；落地缺口登记在路线图 §23/§24 |
| 日期 | 2026-09-26 |
| 原则 | **"开发者如何深度开发是他的能力；从 agent-base 开始，基座要给一个足够好的起点以及开发的保证，而不是约束他。"** |

**基座对开发者的三句承诺**：

1. **给你一条缝** —— 业务代码、钩子、loop 扩展、服务形态都有明确的放置点与加载方式（上层镜像里自由发挥）。
2. **让你声明的东西可验证** —— 声明即契约；触发留痕、边界可断言、失败响亮。
3. **不挡你** —— 保证范围外的做法**允许做**，基座给样例、给标注（"未验证"），不设卡。

## 3. 稳定性承诺：什么不会随基座升级而变

| 接口 | 承诺 |
|---|---|
| `agent.yaml` / `connectors.yaml` 的 `apiVersion` + schema `$id` | 同 `apiVersion` 内**不破坏**；破坏性变更必须升版并写 CHANGELOG |
| `enhancements.schema.json`（**harness 层**：`harness/<h>/enhancements.yaml`） | **不**在 `apiVersion` 承诺内（该层本就不可移植）：随**基座版本**演进；改名/收窄必须写 CHANGELOG 并给迁移写法（例：`event:` → `events: []`），且必须**响亮失败**而不是静默忽略 —— 见 D-0017 |
| 统一轨迹 schema（`$id`）与 10 类事件 | 只增不改；新增事件不改变既有字段语义 |
| 容器入口的环境变量合同（`AGENT_ARTIFACT_DIR`/`AGENT_RUN_DIR`/`HARNESS`/`AGENT_HARNESS_ARGS`/参数四法） | 名字与语义不变；新增走文档 |
| 产物清单字段（`runtimeParams`/`runtimePlan`/`modelProvider*`/`artifactsDigest`） | 只增不改；字段重命名必须一次到位并升版（本项目已因此吃过教训） |
| 镜像 LABEL（`agent-base.inputs-digest` / `agent-base.variant`） | 语义不变（用于同源校验） |
| **可能变**（不在承诺内） | 目录内部布局细节、`dist/` 结构、基座自身的实现文件划分 |

## 4. 缺口：起点还差什么（诚实清单）

> **纪律**：这份清单不许引用**已完成**的项 —— 做完就删，否则有人会去啃已经存在的东西。
> 闸门 1 的 `docs/gaps-not-done` 会拦：每行必须注明"记在哪"（待办 id），且该 id 在账本里必须存在、**没标 `done`**。
> （2026-09-27 复核：原清单 5 条里有 **4 条已经做完**却还挂着，正是这条纪律要消灭的情形。）

| # | 缺口 | 后果 | 记在哪（待办 id） |
|---|---|---|---|
| 1 | loop / 服务形态**没有声明面与判据**（最大轮次、时长预算、终止条件、委派深度、会话生命周期、并发上限、状态外置） | 长驻/并发/预算这些形态无法声明、无法断言，"上生产"缺判据 | E5–E8 |

| 4 | **主运行时尚未选型**（pi / dsh / 最终收敛）：两侧都跑得通，但默认与关键路径押在哪一侧没定 | 上面第 1 条的声明面要按两者的交集设计，没定就动不了 | E5–E8（前置是选型决策） |

## 5. 不约束：保证范围外，基座怎么对待

| 你的做法 | 基座的反应 |
|---|---|
| 在定义/增强里加**自己的字段**（`x-*` / `customizations:` / 自定义 `kind`） | **原样透传**进产物与清单，报告里标"未验证声明"；**不报错、不丢弃**（当前待实现：O1） |
| **手写接入件**而不走通用桥 | 允许（是显式逃生门）；需要时在声明里标注"定制接入" |
| 在**上层镜像**里加业务代码/钩子/loop 扩展/服务 | 允许；基座只要求不破坏 §6 的三条不变量 |
| 绕过基座直接跑 `pi`/`dsh` | 允许 —— 基座不拦，那是你的选择 |
| 不用基座的某些层（如不要容器、不要轨迹） | 允许，但**不在这份契约的保证范围内**（文档会写清） |

**一条硬边界**：**不静默**。
不认识的**声明**要保留并标注；不认识的**内容**不许造成静默行为（丢掉/降级/假通过）。

---

## 6. 你要守住的三条（不变量）

1. **产物只读**：运行期只改暂存副本；产物内的 digest 必须可复算。
2. **显式失败**：缺参数、缺凭据、配置不完整 —— 一律响亮失败，不许静默降级或占位兜底。
3. **轨迹完整**：发生的事要能进统一轨迹（含"未映射的原生事件"，必须带理由）；轨迹行必须过 schema。

守住这三条，其余随便你。

## 7. 自我检验（基座自己也要被量）

> **凡是声称"已支持"的能力，必须能指向一条真实判据（闸门 / 自检 / conformance 用例）。
> 指不出来的，降级为"示例"或"未验证"，不许留在"已支持"清单里。**

这条对基座自身同样生效；本页 §1（能力）与 §2（承诺）的每一行都按此标准给了判据，缺口在 §4 里明说。

**它是可执行的**（§24 O4）：`make selfcheck` 会把本页两表的「证据 / 判据」逐条解析到仓库里**真实存在**的
东西（`make <目标>` / `node <脚本>` / 路径 / 闸门检查 id）——
解析不到就是"**指不出的能力**"，要删除或降级为"示例/未验证"；显式写「未实测」的算**降级态**（单独计数）。
闸门 1 的 `docs/capability-judgements` 用的是同一份实现（`core/spec/capability-judgements.mjs`）。
