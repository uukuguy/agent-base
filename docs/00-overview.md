# 00 · 这是什么

## 一句话

**agent-base 是一套企业智能体基座**：你把一个业务智能体写成一份**中性定义**，它负责把这份定义
渲染到具体运行时、跑起来、并用四道闸门告诉你**「这个想法验证走通了吗」**。

它的目标不是生产上线，而是**验证**（E2E 四道闸门全绿 = 可用）。生产化（鉴权、审批流、多租户、
高可用、SBOM 签名、常驻服务编排）不在基座范围；基座里的安全基线、交付契约、镜像等机制，存在理由
都是**让验证环境足够接近生产，结论才可信**。

## 它封装了三件事

| 封装 | 你不必再操心 |
|---|---|
| **运行时差异** | 两个 harness（pi 与 dsh）并列可选，同一份定义两边都能跑。差异（做不到等价的部分）被**显式列出**，不会沉默地不一样 |
| **验证流程** | 四道闸门一条命令跑完，给出"可用 / 不可用"，而不是"好像能启动" |
| **交付契约** | 你的定义 → 渲染产物 → 双架构镜像（生产 + 调试变体），构建期烤行为、运行期注入参数 |

## 三层边界

```
平台层   提供镜像仓库、凭据、网络策略        ← 基座不碰
──────────────────────────────────────────────
应用层   my-agent/（你的智能体）              ← 你只改这里
           agent.yaml · connectors.yaml · skills/ · 可选 trace-labels.yaml
──────────────────────────────────────────────
基座层   core/ + adapters/<h>/                ← 平台开发者改这里
──────────────────────────────────────────────
```

**基座不含任何业务智能体。** 应用派生**到基座之外**，也不回头改基座。这条边界是本项目最硬的一条：
如果你发现"必须改基座才能做这个智能体"，那说明基座缺能力，是另一件事，不该顺手改。

## 你的智能体由四样东西组成（可移植核心）

| 概念 | 文件 | 说明 |
|---|---|---|
| **它是谁** | `agent.yaml` 的 `persona` | 人设与边界 |
| **它用哪个模型** | `agent.yaml` 的 `model` | **供应商名 + 模型名**（不是 URL、不是密钥；见「行为烤、参数下放」） |
| **它会什么** | `skills/<名字>/SKILL.md` | 技能；可带 `scripts/` 放业务代码 |
| **它能连什么** | `connectors.yaml` | MCP 连接器（按名引用基座预装条目，或写完整形态） |

这四样是**可移植核心**：两个 harness 都必须支持。做不到等价的部分，基座有义务写进
`adapters/<h>/exemptions.yaml` 并在报告里标注 —— **不允许沉默不等价**。

业务级增强（自定义工具、钩子、插件）放在 `harness/<运行时>/`：它**必然 harness 专有**、不计入可移植性
承诺（两个 harness 的扩展机制根本不同）。需要写增强时看 `11-harness-enhancements.md`。

## 两个原则（决定了大部分设计）

**行为烤、参数下放** —— 判据一句话：

> 这个字段改了，同一个输入会不会得到不同行为？
> **会** → 烤进制品（构建期渲染）；**不会** → 参数层（运行期注入）。

所以人设、技能、连接器、工具边界、模型**选择**进制品；端点与**凭据**只在运行期注入，
定义里只写**引用名**（例如 `CORP_GATEWAY_BASE_URL`）。

**隔离靠文件系统，不靠配置** —— 每个智能体各自的 HOME、各自的产物目录、各自的技能目录。
因为两个 harness 都有"隐式技能源"（会从 `$HOME` 或工作目录祖先里发现技能），配置关不掉，
只能靠隔离干净。

## 目录速览

```
core/          基座不变量：定义 schema · 能力/参数/供应商目录 · 四闸门框架 · 统一轨迹 · 镜像
adapters/pi/   适配器：渲染器 · 自证 · 轨迹映射 · 失败表 · 种子 · 豁免
adapters/dsh/  同上（第二个 harness）
conformance/   新 harness 的准入门槛 C1–C10（10 项阻断性检查）
template/      派生源：新智能体从这里开始
examples/      示例智能体（不是基座的一部分，可整体删除）
tools/         命令面实现：validate / probe / smoke / verify / new-agent / run-local …
docs/          本套文档 + 设计正文 + 调研
```

## 两个 harness 是什么关系

**并列可选，不是主从。** 当前默认 pi（更稳定），dsh 是候选（国内生态偏向它，但版本很新）。
两者都通过全部十项准入门槛 —— 也就是说，**同一份定义在两边都验证过**。

双 harness 的目的不只是可移植，更是**比较选型**：等拿到足够的比较数据，可能收敛到一个。
翻转只改默认值，不改设计。
