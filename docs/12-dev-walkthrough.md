# 12 · 开发场景演练（两个不同的东西，别混）

这篇要说清**两件不同的事**，混在一起会得出错误结论：

| | 是什么 | 用在哪 | 在哪 |
|---|---|---|---|
| **演练**（`make walkthrough`） | 一条命令把基座的各项功能**跑一遍**，给功能 × 证据清单 | 改完基座自检、交接时快速证明"功能没坏" | 本页 |
| **示例项目**（`examples/`） | **完整可跑的项目样本**，照着它做自己的智能体 | **真实开发**：在一个项目里持续改、持续验证 | `examples/README.md` |

**关键区别**：真实开发不是"跑一条命令"，而是在**一个项目下持续做**。所以现场验证的载体是
`examples/`（每个示例都有完整定义 + 技能 + 标签 + Makefile + README，README 讲清构建与验证过程），
不是这个演练脚本。演练脚本的价值是"基座功能冒烟" —— 快、全、离线可跑。

## 演练能证明什么、不能证明什么

**能**：派生、定义校验、技能发现、工具边界、渲染确定性、四道闸门、运行期参数四种给法、
运行期隔离（产物只读）、跨运行时等价、容器 `config-check` 与 fail-fast —— 一项一项都有证据。

**不能**：它不构成"你的场景能用"的证据。你的场景要用 `examples/` 的方式做：**建一个自己的项目**，
按示例的 README 走完整循环。演练里那个临时智能体用完就删了，它不是你的项目。

## 一条命令跑完

```bash
make walkthrough                    # 离线闭环（零凭据假网关，不花任何额度）
make walkthrough LIVE=1 ENDPOINT=https://… API_KEY=…    # 再打真实端点（真的调用模型）
```

它会真的**派生一个智能体**、真的改定义、真的跑闸门与容器，最后给出功能 × 证据的清单。
默认全部离线；`LIVE=1` 才打真实端点 —— 没验的项会明确标成"跳过"，不会伪装成通过。

## 它走的循环（也就是开发者实际会走的）

| # | 步骤 | 在验什么 |
|---|---|---|
| 1 | `new-agent` 派生 | 骨架可用、含 Makefile（派生者不必碰基座） |
| 2 | 改定义：加自己的技能 + 工具边界 | 技能是 `skills/<名>/SKILL.md` **目录发现**，不在定义里列清单；`tools.deny` 生效 |
| 3 | **故意写错**（模型名、技能引用） | 闸门 1 当场变红并列出可用取值 —— 闸门真的在管事，不是摆设 |
| 4 | 改对 → 闸门 1 全绿 | 错误修掉即可交付 |
| 5 | 渲染（两次） | 确定性（digest 相同）+ 产物自带运行期参数契约 |
| 6 | 渲染清单 | 自己的技能与工具边界**真的进了产物**（不看定义文件，看产物） |
| 7 | 闸门 2 / 3 / 4 | 解析自证 · 集成探针 · 端到端冒烟（离线、零凭据） |
| 8 | 运行期参数四种给法 | ① 环境变量 ② `_FILE` ③ `AGENT_SECRETS_DIR` ④ 定义默认值 —— 都能解析、优先级正确 |
| 9 | 本地真跑 + 产物只读 | 跑完之后**产物 digest 不变**（运行期隔离成立） |
| 10 | 跨运行时比对 | 同一份定义在 pi / dsh 上等价，差异必须有声明 |
| 11 | 容器 `config-check` | 镜像里能配好 LLM 并离线自检；**缺凭据 fail-fast** |
| 12 | （可选）`LIVE=1` | 对真实端点跑四道闸门 —— "真的能用"的最终证据 |

## 什么时候用 `examples/`

| 你想要 | 用什么 |
|---|---|
| 看"这东西长什么样"、抄一份写法 | `examples/`（`idea-to-proof` 纯技能型 · `contract-review` 带 MCP 连接器） |
| 验证基座自身是否健康 | `make validate` / `make conformance` / 各 `*-selftest` |
| **验证"我的场景能不能用"** | `make walkthrough`，然后把工作区里的定义换成你自己的 |

`examples/` 的价值在**对照**：同一份定义在两个运行时上等价、连接器怎么声明、技能怎么组织。
它不是你的项目的起点 —— 起点是 `make new-agent`。

## 在会话里问"这个项目现在是什么样"：`/project`

真实开发里最费时间的往往不是改一行，而是**确认这个项目现在到底声明了什么**。为此基座带了一条
**常驻命令**（基座不变量，每个智能体都有）：

```bash
cd examples/idea-to-proof && make local     # 进交互会话
> /project              # 分类目录（只列出可查询的子命令）
> /project overview     # 显示项目根目录 PROJECT.md（Markdown 原样交给运行时渲染）
> /project all          # 显式查看完整报告
> /project skills       # 只看一类：skills | connectors | enhancements | hooks | model | trace | portability
> /project <Tab>        # 补全列出分类；再 <Tab> 补**这个项目里真实存在的值**
```

它说的话**全部来自产物**（渲染清单 + 产物配置目录），不是文档抄来的：

```
── hooks ──
· trace → session_start, before_provider_request, after_provider_response, tool_call, tool_result, session_shutdown
运行时可订阅集合  39 个（0.87.1；来源 dist/core/extensions/types.d.ts:979-1017 …）
✅ 订阅的 6 个事件都在集合内
```

判据（`make pi-project-info-selftest`）：定义里加一个技能/删一个技能 ⇒ 输出与补全项跟着变；
钩子事件名写错 ⇒ 当场标 ❌；读不到产物 ⇒ 响亮失败而不是给半份清单；可移植性结论与闸门 1 **同源**。

**补全本身就是"一个项目应该有哪些信息"的目录** —— 这是这条命令最容易被低估的用途：
想不起该有什么时，敲 `/project ` 按 Tab。

### 给项目写一份可执行的入口说明

在智能体定义根目录放一个 `PROJECT.md` 即可约定项目入口，不限制 Markdown 内容格式。渲染时文件会随产物进入 Pi/DSH，
会话内用 `/project overview` 查看。示例项目都带有这份文件；可以从 `examples/idea-to-proof/PROJECT.md` 开始改写，放入
本项目的验证命令、验收标准和几个真实输入例子。Pi 的交互消息会渲染 Markdown；DSH 的 Web UI 会渲染 Markdown，
无头输出则保留 Markdown 文本。

## 没验的部分（诚实清单）

- **真实模型质量**：演练只验"调用成功、工具字段没被吞、流式没被降级"，不评价回答好不好。
- **LIVE**：需要你自己给端点与凭据；订阅读（如 `openai-codex`）请先登录，见 `01-quickstart`。
- **镜像**：容器那两步要求本机已构建镜像（`make image-all`），没构建会标成"跳过"。
- **推送与编排**：`image-push` 未对真实 registry 验证；本项目不假定统一 K8s。
