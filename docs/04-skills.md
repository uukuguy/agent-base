# 04 · 技能怎么写

技能是智能体"会什么"。一个技能 = 一个目录 + 一份 `SKILL.md`，可以带业务代码。

## 最小技能

```
skills/
  clause-scan/
    SKILL.md
```

```markdown
---
name: clause-scan
description: 扫描合同条款，标出高风险表述
whenToUse: 用户给出合同文本或条款清单时
---

# 扫描条款风险

## 何时用
（写给模型看：什么情况下该用这个技能）

## 怎么做
1. …（步骤要具体到可执行，别写"仔细分析"这种空话）
2. …

## 不要做
- …（把这条写清楚，比写十条"要做什么"更省事）
```

## 三个必填/常用字段

| 字段 | 必填 | 约束 |
|---|---|---|
| `name` | 是 | **必须与目录名一致**（`skills/clause-scan/` ↔ `name: clause-scan`）。`make validate` 会拦 |
| `description` | 是 | 一句话。模型靠它决定"要不要翻这份技能" |
| `whenToUse` | 否 | 更明确的触发场景。写得好能显著减少误用 |

## 带业务代码

技能可以带脚本，**放在技能目录下的 `scripts/`**：

```
skills/
  clause-scan/
    SKILL.md
    scripts/
      scan.sh          ← 你的业务代码
```

在 `SKILL.md` 里用**相对路径**引用它（`scripts/scan.sh`），不要写绝对路径 ——
渲染器会把整包原样搬进产物，绝对路径会当场失效。

**落点纪律**：技能携带的业务代码**只进智能体镜像的薄层**，绝不进基座镜像。
所以你可以放心往里放只属于这个智能体的东西。

## 技能是怎么被加载的（两个运行时不同，但这不关你的事）

| | pi | dsh |
|---|---|---|
| 机制 | `agent-dir/skills/` + 运行参数 `--skill <目录>` | `skill-filesystem.customSkillDirs` 指向**镜像内固定路径** + 启用 `tool-skill` |

**你不用管这些。** 你只要把技能放进 `skills/` 目录，两侧的渲染器各自处理。

## 两条容易踩的坑

**① 隐式技能源 —— 技能可能"多出来一个"。**
两个运行时都会从**你没指定的地方**发现技能（pi 会看 `$HOME/.agents/skills` 和沿工作目录祖先发现的
`.agents/skills`；dsh 有多个 rank 根），而且**配置关不掉**。基座用**文件系统隔离**
（独立的 HOME、中立的 cwd）把这条路堵上，并在闸门 2 做集合断言：

> 实际加载的技能集合 **必须等于** 声明的集合 —— **多一个也不行**。

所以：技能一律放 `skills/` 下，别指望放在别处会被"顺便"加载。

**② 技能声明了但没落盘。**
`make validate` 会检查 `skills/<name>/SKILL.md` 是否存在、frontmatter 是否合法。
闸门 3 还会确认它**在产物里就位**。两道都过了才说明这个技能真的可用。

## 怎么确认它生效了

```bash
make validate            # 闸门 1：frontmatter 合法、name 与目录名一致
make render && make doctor RENDER_DIR=.render/pi
#   → doctor 会报告"实际加载了哪些技能"，并与声明集合做断言
make verify              # 四道闸门一起看
```

如果 doctor 报「实际加载集合 ≠ 声明集合」，先看是不是**隐式源**混进来了（见上面的坑 ①）。

## 写技能的几条经验（来自本仓库的示例）

- **把"不要做"写清楚**：模型最常犯的错是越界（顺手给建议、顺手改文件）。一条明确的禁令比三条鼓励有用。
- **输出格式写死**（例如"用表格，列为 …"）：格式稳定了，下游才好接。
- **不可验证的东西要单独成列**：例如"当前不可验证，缺什么才能验证" —— 把它混进结论里是最坏的输出，
  看起来有结论、实际无从检验。
- 具体示例见 `examples/idea-to-proof/skills/`（三个技能串成一条完整工作流，其中一个带脚本与自检）。
