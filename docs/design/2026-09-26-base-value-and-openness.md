# 基座能力在哪里：保证、允许、不管（三段式）

| | |
|---|---|

| 日期 | 2026-09-26 |
| 触发 | 评审追问：**"只做 skills/MCP 根本不需要 agent-base 这个多余的东西，直接做就行 —— 那基座能力到底在哪里？"** 以及 **"应该对完整的企业智能体应用开发提供充分支持，而不是说我的规范不允许我这么做"** |

---

## 1. 先把话说清：skills/MCP 那一层，确实不构成基座能力

**评审说得对**：中性定义 + 技能目录 + 连接器配置 + 渲染出一份产物 —— 这一层用 pi/dsh 直接做更快。
基座如果只停在这里（**今天基本如此**），它就是多余的。

所以问题不是"基座要不要包揽一切"（不可能），而是：**哪些东西每个项目都会自己重做一遍、而且做得更差？**
只有那些才配叫基座能力。用这把尺子量：

| 候选 | 自己做会变成什么 | 算不算基座能力 |
|---|---|---|
| 中性定义 + 技能 + MCP 配置 | 直接写 pi/dsh 配置，更快 | ❌ **不算**（评审说得对） |
| **可执行的验收**（四闸门 + 零凭据假网关 + C1–C10） | 手动"跑一下看看"；各项目各写一套脚本，且大多只测 happy path | ✅ **算**（最硬的一项） |
| **跨运行时/跨环境的契约**（定义→渲染 · 统一轨迹 · 参数分层） | 直接绑死某个 CLI 的参数与目录布局，换运行时重写 | ✅ 算 |
| **运行与交付不变量**（产物只读+暂存隔离 · 参数四法 · 显式失败 · 镜像内 LLM 配置） | 各自踩一遍：密钥进镜像、运行期改写产物、缺凭据静默降级 | ✅ 算 |
| **公共回归资产**（harness 版本 pin · 镜像输入指纹 · 13 个自检） | 每次升级运行时靠人肉回归 | ✅ 算（随时间复利） |
| **L2 钩子 / L3 loop / L4 服务** | 今天只能各写各的，且**无法验证是否生效** | ⚠️ **今天不算**（只有传输、没有判据）→ **这正是必须补的** |

**结论 1**：基座今天的价值集中在"验收 + 契约 + 不变量 + 回归"，**不在"配置管理"**。
凡是我们拿不出判据的东西，都不算基座能力 —— 不管它写在文档里多漂亮。

---

## 2. 基座能力的一句话定义

> **基座能力 = 把"可用"变成可执行、可复算、跨项目一致的判据。**

拆成三件套：

1. **可执行的验收**：离线、无密钥、跨运行时地回答"这个智能体可用/不可用"，并给出**证据链**
   （端点侧真的收到工具、流式没被降级、被禁工具真的没被调、产物真的没被改、缺凭据真的 fail-fast）。
2. **契约与不变量**：同一份定义在不同运行时/环境成立；差异**必须声明**，不许沉默；轨迹、参数、隔离、交付纪律是**默认**而不是"记得做"。
3. **可扩展的缝 + 诚实的支持声明**：业务深定制在**上层镜像**里做，基座给缝、给判据、**并如实标注"未验证"**。

**自我检验（随时可跑）**：
> 如果基座明天消失，一个团队做同一个智能体，会不会**多花好几天**、并且**做得更不一致**？
> 会 → 那项是基座能力；不会 → 那项是多余的东西，该删掉或降级成示例。

## 3. "充分支持完整企业应用开发" = 全生命周期每一层都有【契约 + 判据 + 逃生门】

| 阶段 | 契约（能声明什么） | 判据（怎么算成立） | 逃生门（不在保证范围但**允许**） |
|---|---|---|---|
| 定义 | schema + 参数层 + provider 目录 | 闸门 1（含参数层与层纪律） | 自定义字段 → §4 的开放命名空间 |
| 渲染 | 确定性渲染 + 清单契约 | digest 复算一致 + 声明即契约 | 自定义渲染补丁（标注未验证） |
| 本地运行 | 参数四法 + 暂存隔离 | 闸门 2/3/4 | 直接跑二进制（基座不拦） |
| 交付镜像 | 基座镜像 + 启动器 + `runtimePlan` | C9 容器下限 + `config-check` | 派生镜像自由加层 |
| **派生镜像（业务层）** | **接入缝**：业务代码 / 钩子 / loop 扩展 | **可声明 + 触发留痕**（E2/E3 待建） | **完全自由**，只要不破坏不变量 |
| 服务形态（L4） | 会话生命周期 / 并发上限 / 状态外置 / 审批通道 | 对应闸门（E5 待建） | 自建服务（基座给接口约定） |
| 运维 | 版本 pin + 输入指纹 + 轨迹 | C1–C10 + 回归网 | 自己的灰度/审计/成本实现 |

**判据的底线**（不可退化）：
1. 四道闸门与 conformance **不许降级成软告警** —— 新能力要**新判据**，不是放宽旧判据。
2. **验不了的必须标注"未验证"**，不许写成"已支持"。
3. **不静默失败**：不认识的声明要**保留并标注**，不认识的内容不许悄悄丢掉。

## 4. 规范措辞原则：**保证 + 判据**，不是**禁止**

**旧口径**（`core/spec/agent.schema.json` 当时的原文，2026-09-26 之前）：

> "刻意保持小：中性格式只表达两个 harness 的可移植核心（交集）……**因此本 schema 不预留任何未来字段**"
> 且 `additionalProperties: false`

**它读起来是"基座不允许你做"。** 这正是评审反对的那种姿态。已改成三段式（**2026-09-27 落地**）：

| 段 | 含义 | 工程做法 | 落地处 |
|---|---|---|---|
| **① 基座保证并验证的** | 进了 schema / 契约，有判据 | 改动要走闸门与 conformance | `core/spec/*.schema.json` 的 `properties` + 能力目录的 `harnesses.*.verified` |
| **② 基座允许但不保证的** | 厂商/业务自加的东西：**原样透传**到产物与清单 | **开放命名空间**：`x-*` 与 `customizations:`（任意层级）、增强的 `kind: x-*`；`additionalProperties:false` **保留**（拼写错误仍能拦住），开放区**原样保留**并标注「未验证声明」 | schema 的 `patternProperties` · `core/spec/open-namespace.mjs`（闸门 1 与两个渲染器**共用同一份实现**）· 闸门 1 的 `open/unverified-declarations` · 清单字段 `unverifiedDeclarations` |
| **③ 基座明确不管的** | 业务内容、策略内容、审批/网关/审计的实现 | 给缝，不给判据；文档写清"这是你的活" | `docs/14` 的"边界"与各 `exemptions.yaml` |

**关键**：②与"不静默失败"不冲突 ——
**不认识的声明要保留并显式标注**；不认识的**内容**不许造成静默行为。二者要分开处理。

**验证这条口径的证据**（都在仓库里，可重跑）：
- `make validate-selftest` → 正例 `positive/open-namespace`：这份定义**必须全绿**，且 `open/unverified-declarations` 里点到 `x-team-owner` / `customizations` / `x-widget`；
- 负例 `negative/01-unknown-field`：`temperature` 这种**越界/拼错的已知字段**仍然硬错误（区分"显式扩展"与"写错了"）；
- 两个渲染器都把 `unverifiedDeclarations` 写进产物清单（`make render` 后看 `render-manifest.json`）。

---

## 5. 不做的事（边界）

- **不做业务**：业务逻辑、策略内容、审批规则、网关计费 —— 这些是上层镜像与服务的活。
- **不假装支持**：没有判据的能力一律标"未验证"，不进"已支持"清单。
- **不阻止**：不在保证范围内的做法，基座**给缝、给样例、给标注**，不设卡。
