## 阅读指南

两份上位文档都用"老化速度"来解释自己的分节（【dsh 专有】/【基座通用】/【本项目决策】）。这个思路是对的，但**三层不够**：在"一套基座 + 多个运行时"的结构里，多出来一层最关键的——**基座与 harness 之间的契约**。它既不是基座不变量（它必须承认 harness 的差异），也不是 harness 专有（它对所有 harness 都成立）。

因此本文用**四类标记**：

| 标记 | 含义 | 老化速度 | 评审关注点 | 本文位置 |
|---|---|---|---|---|
| **【不变量】** | 跨 harness 长期成立的要求与设计 | 慢 | 是否有遗漏、是否过度设计 | §1–§3、§6–§9、§13 |
| **【适配契约】** | 基座与 harness 之间的接口，**双方共同**负责 | 中 | 是否足以接入第三个 harness | §4、§5 |
| **【harness 专有】** | 某个 harness 的机制与实测约束 | **快**，随上游版本变化 | 事实是否准确；升级时复核 | §10、§11 |
| **【本项目决策】** | 在上述三者之上做的取舍 | 中 | 是否符合业务需要 | §2.2、§12、§15 |

**约定**：

- "**harness**" = 智能体运行时（pi、dsh 都是）。"**基座**" = 所有智能体、所有 harness 共享的底座。"**适配器**" = `adapters/<harness>/`，把中性定义与基座不变量翻译成该 harness 的原生形态。
- 需求编号 **N1–N29** 是本文的规范条目，§3 定义，全文引用。附录 A 给出它们与两份上位文档的逐条对应。
- 关键机制均来自两份上位文档的**实测**记录（dsh 实验 A–E、pi 四层闸门与 smoke 实测）。本文不引入未经实测的新机制假设；凡属推断，均显式标注"**待实测**"。
- `-pi` 候选稿用三态标记（【基座通用】/【harness 适配】/【项目决策】）。本文保留四态并多出【适配契约】——因为"一套基座 + 多个 harness"成立的关键恰恰是那一层（§0.1）；其余三态与本表一一对应。

## 1. 目标与范围

### 1.1 目标

> **帮助某一个业务智能体把想法"验证走通"——E2E = 四道闸门全过 = 可用；同一份智能体定义可以被任意一个受支持的 harness 验证。**

**核心目标是"验证走通"，不是"生产上线"**（用户已明确）。基座的价值由两件事证明：**从它派生并验证一个智能体有多省事**，以及**换一个 harness 验证的代价有多小**。走通之后是一个**决策点**（继续投入 / 放弃 / 进入真正的生产化），生产化是另一个阶段、可能另一个团队，不回头改基座。

### 1.2 三层边界：基座 / 应用 / 平台

| 层 | 是什么 | 含什么 | 谁维护 | 本文是否设计 |
|---|---|---|---|---|
| **基座** | 可复用的启动底座 | 中性定义规范、适配器、闸门、模板、基座镜像、文档 | 平台团队 | ✅ 本文 |
| **应用（智能体）** | 某个业务场景的智能体 | `agent.yaml`、`connectors.yaml`、`skills/`、`harness/*` | 业务团队 | ✅ 只定义其形状（§4），不定义其内容 |
| **平台** | 编排、鉴权、多租户、调度、计费 | 会话归属、并发、RBAC、配额 | 平台团队 | ❌ 明确不做（§1.5） |

**判定标准（沿用 pi §1.1）**：一条需求若只对某一个智能体成立，就不属于基座。**本文追加一条**：一条需求若只对某一个 harness 成立，就不属于基座不变量，而属于适配器。

**核心不变量**：

> **基座不含任何业务智能体；应用派生到基座之外，且不回头修改基座；harness 的差异只允许出现在 `adapters/` 与 `harness/`（业务级增强，harness 专有）里。**

一旦业务开发者需要改 `core/` 或 `adapters/`，说明抽象没做对。

### 1.3 "便捷"的定义与可检查代理指标

沿用 dsh §1.3 的定义：便捷 **不是** 耗时短，而是**心智负担低**。合并两份上位文档的指标，并补上"换 harness"这一维：

| 指标 | 目标 | 判据（怎么量） |
|---|---|---|
| 新建一个智能体要写/改几个文件 | ≤ 3（`agent.yaml`、`connectors.yaml`、`skills/<n>/SKILL.md`） | `tools/new-agent.mjs` 生成的目录里非模板文件数 |
| 需要理解的业务概念数 | ≤ 4（人设与边界 / 模型 / 技能 / 连接器） | §4.6 能力目录的分组数（"智能体"是容器概念，不计入） |
| 需要理解的 harness 概念数 | 0 | `docs/` 中业务向文档不出现 harness 术语；`validate` 报错信息只给中性字段路径 |
| 新增一个智能体是否声明依赖 | 不需要 | 模板目录内无 `package.json`、无 lockfile |
| 复制模板后 | 开箱可跑，无 TODO | `template/` 内 `grep -rn TODO` 为空 |
| 配置错误时的反馈 | 显式失败 + 文件 + 字段路径；**harness 的静默失败必须被闸门 2 抓到** | §6.2/§6.3 的注入式测试用例 |
| 同一份定义换 harness | 改一个变量（`HARNESS=`）后重跑四闸门；业务级增强内容除外 | §6.6 等价性检查 |
| 新增一个 harness 需要改基座核心的文件数 | 0（只新增 `adapters/<h>/` 并通过 `conformance`） | §5.6 合规套通过 + `core/` 无 diff |

**明确不用工期指标**（"分钟数"）度量便捷性：它会诱导砍掉该有的文档与校验，做出没人敢用的东西。

### 1.4 "并列双运行时"的确切含义

并列 **不等于** 两个 harness 行为一致。它承诺的是下面这条边界内的等价：

| | 承诺 | 不承诺 |
|---|---|---|
| **可移植核心**（§4.1–§4.4 的中性定义：身份/人设/边界、技能集合、连接器集合、模型路由名与模型名） | 两个 harness 渲染后，§6.3 解析自证输出必须满足同一组断言；§6.5 冒烟断言集相同且都通过 | 提示词文本逐字相同；工具调用顺序相同；token 级输出相同；工具命名相同（工具名由 harness 决定） |
| **业务级 harness 增强**（§4.5） | 只有"声明即契约、进入制品、进入 digest"这几条约束 | **任何跨 harness 保证——且这是预期常态而非例外**：pi 扩展与 dsh 插件是两套完全不同的机制（§4.5）。使用增强的智能体，其"可移植"结论是**部分**的，由 `validate` 显式标注 |

**等价性豁免**：确实做不到的等价，必须写进 `adapters/<h>/exemptions.yaml`，每条带理由与复核期限；`validate` 检查豁免是否过期（§6.6）。**不允许"沉默地不等价"**——这是两份上位文档都缺的那一环。

**并列的第二个目的：比较，而不是长期双持。** 同时挂两个 harness 不只是为了"可移植"，更是一次**有实证的选型比较**——同一份定义跑两边，差异会被 §6.6 的断言集与 §10.4/§11.6 的 H 轴自证如实暴露。**最终可能收敛到其中一个**：收敛判据不是偏好，而是"哪一边在可移植核心上通过得更干净、增强开发更省事"，数据来自 `verify` 报告与 H 轴自评。

### 1.5 明确不做（本阶段）

**生产上线本身不在基座范围**（§1.1）：基座交付的是"验证走通的证据与可复现制品"，不是可长期运行、高可用、需鉴权审计的生产服务。下列各项皆由此导出，沿用并合并两份上位文档的"不做"清单：

- 平台能力：权限体系、审批流、多租户、调度与编排、计费（pi D1；基座只提供被调用的接口）
- 私有 npm registry、bundle 版本矩阵治理、SBOM/镜像签名（dsh §1.5 + pi D5；列为 §14 风险而非本期交付）
- 多层 bundle 拆分（`corp-base` + `corp-domain`）
- 常驻服务的会话归属、并发、鉴权（pi D3；需要单独一张设计）
- 推理结果的跨 harness 逐字一致（§1.4 已明确不承诺）

### 1.6 主力与候选：当下用 pi，押注在 dsh

两个 harness **不是等权的**。本项目决策：

| harness | 定位 | 依据 |
|---|---|---|
| **pi** | **当前主力**：关键路径（首个走通、示例、模板默认 harness）都先跑 pi | 稳定（`0.87.1` 正式版）；dsh 基线还是 RC |
| **dsh** | **比较对象 + 未来候选**：适配器同步维护、参与选型比较，但不压关键路径 | 国内生态明显偏向 dsh（DeepSeek 系），但 `0.1.7-rc.1` 太新、接口会变（§14 风险 1） |

**这条定位是可翻转的**，翻转依据就是 §1.4 的比较数据：dsh 一旦进入稳定版且比较结果占优，主力与候选互换。**互换不需要改任何设计**——只需改默认 `HARNESS=` 与示例的默认 harness，这正是"并列 + 中性定义"的价值兑现。

## 2. 统一架构

### 2.1 五层模型

```
【应用层】 my-agent/          中性定义：agent.yaml + connectors.yaml + skills/     ← 业务团队只碰这里
                │
                │  render（构建期，确定性）
                ▼
【制品层】 my-agent:<ver>  =  base:<ver>  +  渲染后的 harness 原生定义（行为在此冻结）
                │
                │  FROM
                ▼
【基座层】 base:<ver>      =  core（不变量）  +  adapters/<h>（harness 专有）
                │
                │  适配契约（§5）：能力声明 / 渲染 / 解析自证 / 探针 / 轨迹映射 / 失败表
                ▼
【适配层】 adapters/pi        adapters/dsh        conformance/（新 harness 准入门槛）
                ▲
                │
【参数层】 部署期只注入"不改变行为"的东西：端点、凭据、探针参数（env / secret）
```

**与 dsh 上位设计的差异**：dsh 原设计的"home 层"（`$DSH_HOME/cordis.patch.yml`）在新模型里**降级为基座不变量的一部分，烤进基座镜像**；"领域差异用 `--patch`"改为"领域差异是构建期渲染出的智能体 profile，烤进智能体镜像"（§11.3）。这是 J2 的直接结果。

### 2.2 裁决 C1：为什么必须是"行为烤、参数下放"

两份上位文档在这一点上直接冲突：

| | pi 的取法 | dsh 的取法 |
|---|---|---|
| 配置进入点 | 构建期扁平化，烘焙进镜像 | 运行期四层合成（bundle / profile / home / `--patch`） |
| 换来什么 | 同 digest = 同行为（R7） | 一镜像多智能体，改配置不重建 |
| 代价 | 改配置必须重建 | 行为随配置漂移；配置失效**静默**（dsh 实验 A） |

**论证**：把内容按"变了会不会改变智能体的行为"切开，两边的诉求可以同时满足。

| 内容 | 变了吗 | 放哪 | 依据 |
|---|---|---|---|
| 人设、边界（工具白/黑名单） | 改变行为 | **制品（构建期）** | 行为必须可评审、可回滚、可签名 |
| 技能集合（清单与实现） | 改变行为 | **制品** | 同上；技能是可执行内容 |
| 业务代码（技能脚本、自研连接器、业务级 harness 增强） | 改变行为 | **制品** | 可执行内容，必须可评审、可签名、可复现（§4.1 的 `scripts/`、`mcp-servers/`，§4.5 的 `harness/<h>/`） |
| 连接器集合（有哪些服务器、传输方式） | 改变行为 | **制品** | "它能连哪些系统"是能力声明 |
| 连接器指向哪个环境的同名系统（URL） | **不**改变行为 | **参数层** | 同名系统的不同环境实例；换环境不该重建 |
| 模型路由名 + 模型名 | 改变行为 | **制品** | "它用哪个模型"是行为选择；会话级 `/model` 属调试，不属制品 |
| 路由名背后的端点（`baseURL`）与凭据 | **不**改变行为 | **参数层** | 上门 dsh/pi 上位设计的共同结论（R1） |
| 基座不变量（安全姿态、审计、校验、路由能力目录） | 不随智能体变 | **基座镜像** | 全企业统一 |

- **放运行期的可执行内容违反了制品签名边界**（pi 附录 A 已否决"瘦镜像 + 配置由卷下发"）——这一条在统一设计里对两个 harness 都成立。
- **把端点烤进制品违反 R1/N21**，企业网关一换就要重建全部智能体。
- 因此执法线是一句话：**"这个字段改了，同一个输入会不会得到不同行为？会 → 烤；不会 → 参数层。"**

**副作用一（好）**：dsh 的 `--patch` 从"领域差异的常态表达"降级为**只用于本地调试的临时手段**。交付镜像不接受 `--patch`（§11.3），这直接消灭了 dsh 上位设计 §6.2 决策 1 的两难。

**副作用二（好）**：dsh 的"home 层钉住的 row 领域层改不动、且失败静默"（实验 A）在新模型下不再是陷阱——因为**不存在运行期覆盖的层级竞争**，每层只有一个来源。

**副作用三（需接受）**：改行为要重建智能体镜像。代价是**一个薄层**（`COPY` 渲染产物），不重建基座层。

### 2.3 参数层允许/禁止清单（可执法）

`core/catalog/params.yaml` 是这份清单的机器可读真源，`validate` 与 `conformance` 都读它。

| 允许（参数层） | 禁止（参数层，必须进制品） |
|---|---|
| `AGENT_<NAME>_ENDPOINT_*`（连接器端点覆盖） | 任何 `*_INSTRUCTIONS` / 人设文本 |
| `<NAME>_(TOKEN\|SECRET\|KEY\|PASSWORD)`（连接器凭据，见下） | 技能清单或技能内容 |
| `<ROUTE>_API_KEY` / `<ROUTE>_BASE_URL`（模型路由） | 连接器的启用/停用（"有哪些连接器"） |
| `AGENT_PROBE_*`（探针参数：超时、目标） | 模型名与路由名的选择 |
| `AGENT_LOG_LEVEL` / `AGENT_TRACE_DEST` | 工具白/黑名单 |
| `AGENT_RUN_MODE`（`interactive` / `oneshot` / `rpc` / `debug`） | 业务级增强内容（§4.5） |
| `AGENT_SECRETS_DIR` | |

**连接器凭据的命名约定（实现期补记，2026-09-25）**：本表原先没有逐项列出连接器凭据（`connectors.yaml` 的 `credentialRef`），但 §4.3 的示例用了 `JIRA_TOKEN` / `GITLAB_TOKEN`，且闸门 1 必须能判定"某个 `credentialRef` 是否落在允许清单内"。因此把它显式列为上表第 2 行，约定为后缀式命名：`<NAME>_(TOKEN|SECRET|KEY|PASSWORD)`。

> 这是本清单里**唯一由 §4.3 示例归纳、而非本表原文列出**的条目。若企业既有凭据命名习惯与此不符（如统一前缀式），改 `core/catalog/params.yaml` 的一条 `pattern` 即可，不影响其他任何设计。

**执法方式**：`conformance` 会用一个"把禁止项当参数注入"的负向测试用例验证——注入了必须**无效或直接报错**，不允许静默生效。这是把 §2.2 的纪律从文档变成测试。

### 2.5 一个智能体的完整生命周期

```
① new-agent   tools/new-agent.mjs 从 template/ 派生到基座之外      → my-agent/（3 个文件 + README）
② 写业务      $EDITOR agent.yaml / connectors.yaml / skills/*/SKILL.md
③ validate    闸门 1：schema + 引用 + 凭据引用 + 纪律（§6.2）        → 无 harness 概念暴露
④ render      HARNESS=pi|dsh → adapters/<h>/render.mjs               → 确定性产物 + 产物 digest
⑤ doctor      闸门 2：harness 报告"实际生效物"（§6.3）               → 技能数/连接器数/路由名/生效 digest
⑥ probe       闸门 3：模型（假网关，0 凭据）/技能/连接器（§6.4）
⑦ smoke       闸门 4：冒烟任务 + 退出码 + 输出断言 + 轨迹校验（§6.5）
⑧ 等价性      HARNESS=pi,dsh 双跑 ⑤⑦，比对断言集（§6.6）
⑨ image       产出 my-agent:<ver>（FROM base:<ver>，只 COPY 渲染产物）
⑩ 部署        只注入参数层（§2.3）；stdout/stderr/退出码按 §8.2 契约
```

**本地迭代（③–⑦）在 harness 的交互入口上做**（dsh 用 tui：HMR 启用，改完即生效；pi 用交互模式：改技能目录即重读）；**交付验证（⑦⑧⑨）在容器里做**。理由见 §9.2 的本地/容器差异表。

### 2.6 三条贯穿原则

三条原则在正文多处被引用，在此命名，作为所有后续取舍的判据（P-a/P-b 采自 `-pi` 候选稿 §2.2，P-c 来自本项目实践策略）：

| 原则 | 内容 | 直接推论 |
|---|---|---|
| **P-a 能力/选择分离** | **能力是基座不变量，选择是应用可变**：有哪些 provider、安全姿态、通用技能属于基座（构建期烤入）；这次用哪个 model、哪个端点、哪把密钥属于应用或部署（运行期注入） | 模型层"能力在基座、选择在智能体"（§2.2/§11.4）；参数层清单（§2.3） |
| **P-b 文件系统隔离** | **隔离靠文件系统，不靠配置**：harness 普遍存在"无法用配置关闭的隐式加载源"（pi 的 `~/.agents/skills`、dsh 的六根 rank 扫描），逐项关闭配置不可靠 | 固定并隔离 `HOME`/`DSH_HOME`；闸门 2 硬断言"实际集合 == 声明集合"（§6.3） |
| **P-c 后验统一** | **先分别写、各用原生接口；两份实现都出现了才摘取公共语义**。不做先验抽象——预判出来的"公共"往往是猜的，实证出来的才是真的 | 业务级增强先按 harness 各写一份（§4.5）；`harness/shared/` 只在两个外壳出现同一纯算法时才抽取；"统一基础 harness"是**收敛产物，不是设计起点** |

## 4. 【适配契约】智能体定义单元（中性格式）

### 4.1 目录

```
my-agent/                        # 派生到基座之外，独立仓库或独立目录
├── agent.yaml                   # 必填：身份、人设、边界、模型选择
├── connectors.yaml              # 可选：连接器（不写 = 无连接器）
├── skills/                      # 可选：技能
│   └── <skill-name>/
│       ├── SKILL.md             #   指令（必填）
│       └── scripts/             #   业务代码（可选）：SKILL.md 里调用的脚本/工具
├── mcp-servers/                 # 可选：自研连接器代码（内部系统无现成 MCP server 时）
│   └── <server-name>/
├── harness/                     # 可选：业务级增强（shared/ 纯算法 + pi/ + dsh/ 薄外壳，§4.5）
│   ├── pi/                      #   pi 独有内容
│   └── dsh/                     #   dsh 独有内容
├── Makefile                     # 由模板生成，转发到基座工具（业务开发者不改它）
└── README.md                    # 由模板生成，说明怎么改
```

**业务开发者只需要认识前三个 + README。** `harness/` 是**业务级增强**（§4.5）——它不是"高级用户才碰的逃生舱"，而是**企业智能体的常态需求**（pi/dsh 的基础能力不足以支撑业务）；模板默认不生成它，但一旦需要做增强，它是正面的一等公民。`Makefile` 是薄转发层（`AGENT_DIR=. `，把 `validate/render/doctor/verify` 转发到基座工具），由模板生成、由基座升级时重新生成，**不属于业务开发者要写的增量**（因此不计入 §1.3 的 ≤3 文件指标）。

  route: corp-gateway              #   引用 §11.4 / §10.2 的适配器路由目录，不是 URL

### 4.3 `connectors.yaml`

```yaml
apiVersion: agent-base/v1
mcpServers:
  - name: jira                     # 必填，^[A-Za-z0-9_-]{1,32}$（对齐 dsh serverName 约束）
    transport: streamable-http     # 必填，stdio | streamable-http
    urlRef: JIRA_MCP_URL           # endpoint 是参数层：只写引用名
    credentialRef: JIRA_TOKEN      # 凭据是参数层：只写引用名
    enabled: true
    description: 工单系统            # 进能力目录与系统提示词
  - name: gitlab
    transport: stdio
    command: npx                   # stdio 传输：command/args 进制品（属"能连什么"）
    args: ["-y", "@corp/gitlab-mcp@1.2.3"]
    credentialRef: GITLAB_TOKEN
```

**四个设计点**：

1. **`urlRef` / `credentialRef` 只写引用名**（N18）。取值来自参数层（§2.3）。适配器负责把它解析成 harness 原生字段——dsh 用 `!!js process.env.X`（原生支持），pi 需要在启动期渲染（§10.2 约束 1）。这个差异由适配器的"参数化能力"声明吸收，业务定义不变。
2. **`stdio` 的 `command`/`args` 属于制品**：它决定"能连什么"，且是可执行内容，必须可评审、可 pin 版本。
3. **自研连接器**：当内部系统没有现成 MCP server 时，业务把 server 代码放进 `mcp-servers/<name>/`，`stdio.command` 用相对路径引用它（如 `command: node`、`args: ["mcp-servers/corp-internal/index.js"]`）。渲染器把相对引用解析成镜像内固定路径（§8.1）；这套代码是**业务代码**，随制品一起烤、一起 digest（N19），不是外部依赖。

4. **按名引用基座预装条目（`ref` 形态）**——**这是「开发智能体便捷」的关键一条**。上例是完整形态，要求业务方写全 `transport` + `command`/`args` + 包名版本；对非专家这等于要求先懂 MCP。因此定义单元支持第二种形态：

```yaml
apiVersion: agent-base/v1
mcpServers:
  - ref: filesystem        # 基座预装条目名（core/image/preinstall.yaml 的 namedReferences）
    enabled: true          # 可省略，默认 true
    description: 工作区文件  # 可选，覆盖预装条目的说明
  - ref: playwright
    name: web-tasks        # 可选：服务器名（默认 = ref 名）；同一 ref 用多次时必须给
```

| 规则 | 说明 |
|---|---|
| 解析来源 | `core/image/preinstall.yaml`（**独立可升级产物**）：`ref` → 条目的 `install`（包 + 精确 pin + transport + args）与 `credentialRef` |
| **不提供实现细节覆写** | `ref` 形态**不允许**覆写 `transport` / `command` / `args` / 包名版本。这不是限制而是纪律：一旦允许，每个智能体又会各自 pin 版本，「升级局部化」失效（P-a：能力=基座持有的包与版本，选择=智能体写不写这个 ref） |
| 需要定制时 | 用上面的完整形态写全；两者在 schema 里互斥（`oneOf`） |
| 未知 `ref` | **显式失败**（不是警告）——否则开发者会以为连接器生效了 |
| 服务器名 | 默认 = `ref` 名；`name` 可覆盖 |

**为什么这不算"多一个真源"**：`ref` 只表达**选择**（用不用它），不表达实现；实现只存在于基座清单一处。完整形态与 `ref` 形态表达的是同一件事的不同详细程度——若允许 `ref` 覆写实现细节，才会变成两个真源。

### 4.4 `skills/`

形式对齐两个 harness 的交集：**目录 bundle `<name>/SKILL.md`**。技能可以携带**业务代码**——`scripts/` 子目录放 SKILL.md 里调用的脚本/工具，SKILL.md 用相对路径引用（如「运行 `scripts/parse.py 输入文件`」）；脚本随技能一起进渲染产物、烤进镜像，同样受"同一 digest = 同一行为"约束（N19）。

```markdown
---
name: clause-risk-scan
description: 扫描合同条款中的风险点并分级
whenToUse: 用户给出合同文本要求审阅时
---

（技能正文）
```

**约束（来自 pi 约束 3/4 的通用化）**：中性定义**只声明本目录下的技能**。harness 的隐式加载源（如 pi 的 `$HOME/.agents/skills`、dsh 的六个 rank 根）必须由适配器**用文件系统而非配置**隔离开，并在 `doctor` 中自证"实际技能集合 == 定义声明的集合"（§6.3：这是闸门 2 的一条硬断言，直接对治"配置关不掉的隐式加载源"）。

### 4.5 业务级 harness 增强 `harness/<name>/`（一等公民，harness 专有）

**先承认一件事**：pi 与 dsh 的**基础能力不足以支撑企业智能体**。真实的业务智能体必然要做 **harness 业务级增强**——自定义工具、钩子、中间件、插件、子智能体、命令。这不是边缘情况，是常态；把它当成"逃生舱"是低估了它。

**但它必然 harness 专有、不可移植**——两套扩展机制根本不同：

| harness | 业务级增强机制 | 增强产物形态 |
|---|---|---|
| pi | TypeScript 扩展（事件钩子 / 自定义工具）+ `agents/` 子智能体 + `prompts/` 命令 + `packages` 引 npm 扩展 | `extensions/<id>.ts` 等文件 |
| dsh | **cordis 插件**（一切皆插件）+ profile 里 `insert:` 的新 row（工具 / 服务 / 钩子） | 自定义 npm 插件包 + row 片段 |

因此 `harness/<name>/` 是**一等公民**（不是逃生舱），落点与规则如下：

```
harness/
├── shared/                # 共享层：只放纯业务算法逻辑（无 harness 依赖；两个外壳都 import）
├── pi/                    # pi 外壳（薄）：TypeScript 扩展，import shared
│   ├── enhancements.yaml  #   声明清单（闸门 2 用它断言"真的加载了"）
│   ├── extensions/        #   外壳代码
│   └── prompts/           #   命令 / 提示词（可选）
└── dsh/                   # dsh 外壳（薄）：cordis 插件，import shared
    ├── enhancements.yaml
    └── extensions/
```

**三层分工**（P-c 后验统一的落点）：

| 层 | 放什么 | 纪律 |
|---|---|---|
| `harness/shared/` | **纯业务算法逻辑**（评分、解析、规则、转换…） | 无 harness import、无 I/O 副作用、可纯函数单测；**初期可以是空的** |
| `harness/<h>/` | 外壳：协议适配 + 注册（把 shared 的算法接进该 harness 的扩展/插件机制） | 保持薄——外壳越薄，换 harness 时重写的越少 |
| 基座不变量 | 审计、写保护、轨迹、参数层隔离… | 由基座提供，业务只声明（见下方"晋升通道"） |

```yaml
# harness/pi/enhancements.yaml
apiVersion: agent-base/v1
harness: pi
enhancements:
  - kind: tool                # tool | hook | middleware | plugin | subagent | command
    id: corp-risk-score       # 唯一 id；闸门 2 用集合断言"真的加载了"
    entry: extensions/corp-risk-score.ts
    description: 企业风险评分工具
  - kind: hook
    id: audit-enrich
    event: tool_call
    entry: extensions/audit-enrich.ts
```

| 规则 | 说明 |
|---|---|
| **一等公民** | 业务级增强是**预期常态**；模板与文档必须正面教它——`docs/11-harness-enhancements.md` 是业务开发者要读的第 5 篇文档（§13） |
| **声明即契约** | 每个增强必须在 `enhancements.yaml` 声明 `id`；**闸门 2 的第三条硬断言**比对"已加载扩展 id 集合 == 声明集合"（§6.3）——直接对治"扩展静默没加载"（pi 扩展加载抛错、dsh `skipping profile bundle`） |
| **进入制品** | 增强代码是**行为**，构建期烤进智能体镜像薄层（§8.1），随 digest 可复现（N19） |
| **不承诺跨 harness** | 一份 `harness/pi/` 的增强对 dsh 无意义，反之亦然；等价性只覆盖可移植核心（§1.4）；`validate` 输出"本智能体可移植性：核心 + pi 增强（不可移植）" |
| **禁止** | 用增强去覆盖中性定义已表达的字段（两个真源）；`validate` 拒绝同一字段在两处出现 |
| **外壳保持薄** | 每个 harness 外壳只做"协议适配 + 注册"，业务算法一律下沉到 `harness/shared/`（即使初期只有一份实现，也按"将来会被两边复用"的结构放） |
| **晋升通道** | 同一个增强在多个智能体里重复出现时（`validate` 统计各 `enhancements.yaml` 的重复 `id`/`kind`），它应**晋升为基座不变量**——由基座提供实现、业务侧只留声明（像审计 / 写保护 / 轨迹那样）。**这是让"重复劳动被吸收"的唯一机制，缺了它每个团队都会重写一遍且各自不一致** |

### 4.6 能力目录（N26）

`core/catalog/capabilities.yaml` 是机器可读真源，`docs/03-capability-catalog.md` 由它生成（保证文档与实现不漂移）。结构：

```yaml
groups:                       # 即业务概念的四个分组（N2）
  - id: identity              # 「它是谁、边界在哪」
    fields: [persona.instructions, persona.instructionsFile, tools.deny]
  - id: model                 # 「它用哪个模型」
    fields: [model.route, model.name, model.reasoningEffort]
  - id: skills                # 「它会哪些技能」
    fields: [skillsDir, skills[].name, skills[].description, skills[].whenToUse]
  - id: connectors            # 「它能连哪些系统」
    fields: [mcpServers[].ref, mcpServers[].name, mcpServers[].transport, mcpServers[].urlRef, …]
```

每个字段记录：类型、默认值、取值范围、所属层（制品/参数）、支持该字段的 harness 及降级行为。**"所属层"字段是 §2.3 纪律的第二个执法点**：目录说某字段属参数层，但它在 `agent.yaml` 里，`validate` 就报错。

**连接器字段的两套形态**（§4.3）：`mcpServers[].ref` 是「按名引用基座预装条目」形态；其余字段是完整形态。两者互斥，`validate` 与能力目录都要覆盖：`ref` 必须能在 `core/image/preinstall.yaml` 的 `namedReferences` 里查到，否则**显式失败**。

### 4.7 定义版本与兼容

- `apiVersion: agent-base/v1` 出现在每个定义文件里；渲染器只接受自己支持的版本，不支持的版本**显式失败**（不是警告）。
- 破坏性变更时升 `v2`，基座同时支持 v1/v2 渲染并给出迁移提示（`render --migrate`）。
- 中性定义的 schema 变更走 `CHANGELOG.md`（N28）。

## 5. 【适配契约】harness 适配层

### 5.1 职责边界与十个轴（H1–H10）

| 适配器负责 | 适配器**不**负责 |
|---|---|
| 把中性定义确定性渲染成 harness 原生形态 | 中性定义的语义（那是 `core/spec`） |
| 报告 harness 实际加载了什么（解析自证） | 判断"配置是否正确"（那是闸门 1） |
| 把原生事件映射成统一轨迹 | 轨迹的消费（审计系统） |
| 声明自身能力与降级行为 | 承诺能力（能力由 N 基线要求） |
| 声明已知静默失败并实现检测 | 修 harness 的 bug |
| 提供探针实现 | 编排闸门顺序（那是 `core/gates`） |

**一句话**：适配器是**翻译层 + 自证层**，不是决策层。

**基座对 harness 运行时提出的契约共十个轴**（采自 `-pi` 候选稿 §3，本文把它们与 §5.2 能力声明、§5.5 失败表连成一条线）：

| 轴 | 基座要什么 | 换 harness 必查（实测项） |
|---|---|---|
| **H1 配置合成模型** | 层与优先级、能否 include/拼接 | 有没有多文件拼接机制；配置目录是否必须可写 |
| **H2 端点/模型注入** | 端点能否容器外配置、密钥能否引用变量 | `baseUrl` 是否环境插值 |
| **H3 技能发现与隔离** | 技能从哪加载、有没有隐式加载源 | 隐式路径是否跟随 `HOME` |
| **H4 连接器/MCP** | 外部系统连接、凭据治理、失败时降级还是失败 | 连不上是否静默降级 |
| **H5 安全/沙箱/权限** | 不信任工作区、写入保护、审批、沙箱 | 沙箱是否 Linux-only |
| **H6 可观测钩子** | 每次工具调用可否留痕、轨迹可否导出 | 有无工具调用事件 |
| **H7 委派/子智能体** | 上下文隔离、并行探索 | 有无 subagent 机制 |
| **H8 交付入口/协议** | 交互 / 批处理 / 常驻，同一能力源 | 退出码与 stdout 契约 |
| **H9 静默失败模式** | 所有"改了没生效"的情形 | 逐项实测 |
| **H10 业务级扩展点** | 自定义工具 / 钩子 / 中间件 / 插件 / 子智能体 / 命令如何注册、如何声明、加载失败如何被检出 | 扩展机制的形态；加载失败是报错还是静默；能否枚举"实际加载了哪些扩展" |

**每轴三件事（强制交付）**：每个 harness 适配层必须对 H1–H10 **逐轴**交出 ① 实测约束（带可复现步骤，不是文档推断）② 适配决策（由此导出的"基座这一轴怎么做"）③ 静默失败清单（该轴所有"悄悄没生效"的情形）。缺任何一轴或任何一件事，`conformance/C1` 不通过。§10.4 / §11.6 是 pi / dsh 的逐轴自评。

### 5.2 能力声明 `adapters/<h>/adapter.yaml`

```yaml
harness: pi
version: "0.87.1"                     # 精确 pin
adapterVersion: "1.0.0"
renders:
  output: agent-dir                   # 渲染产物形态
  deterministic: true                 # 同输入同输出（conformance 会验证）
capabilities:                         # 每项：supported | partial | unsupported
  nativeParamInterpolation: unsupported   # → 需启动期渲染（pi 约束 1）
  runtimeWritableConfig: supported        # pi 会写配置目录（约束 2）→ 启动暂存模式
  implicitSkillSources: partial           # $HOME/.agents/skills 关不掉（约束 3）→ 文件系统隔离
  configInclude: unsupported              # 无 include/extends（约束 5）→ 构建期扁平化
  hmr: unsupported
  childAgents: partial                    # subagent 扩展已加载，未跑真实委派
  osSandbox: unsupported                  # macOS 无 OS 级沙箱；容器内由编排承担
  permissionModel: extension              # protected-paths 扩展
  traceEmit: extension                    # audit-log 扩展
  runModes: [interactive, oneshot, rpc, debug]
failures: failures.md                 # §5.5 强制交付物
exemptions: exemptions.yaml           # §1.4 等价性豁免
```

### 5.3 SPI 接口清单

| 接口 | 输入 | 输出（必含） | 由谁消费 |
|---|---|---|---|
| `render` | 定义目录 + 基座种子 | 渲染产物 + `artifactsDigest`（确定性） | `tools/image.mjs` |
| `doctor` | 渲染产物 + 参数层 | harness 版本、定义路径、技能清单、连接器清单、**扩展清单**、模型路由名、`effectiveConfigDigest`、诊断条目 | 闸门 2 |
| `probe/model` | 路由名 + 探针参数 | 一次最小推理的结果与耗时 | 闸门 3 |
| `probe/skills` | 技能清单 | 每个技能是否进入会话目录 | 闸门 3 |
| `probe/connectors` | 连接器清单 | 每个服务器连通性与工具名列表 | 闸门 3 |
| `smoke` | 冒烟任务 | 退出码、输出、轨迹文件 | 闸门 4 |
| `trace` | harness 原生事件 | 符合 `core/trace/schema.json` 的 JSONL | 审计/调试 |
| `entrypoint` | `AGENT_RUN_MODE` + 参数层 | 进程行为（§8.2 契约） | 部署 |

### 5.4 降级与豁免语义

能力声明里 `partial` / `unsupported` 的**后果必须显式**，只有三种合法处置：

| 处置 | 何时用 | 记录位置 |
|---|---|---|
| **等效替代** | 能用别的机制达到同一效果（如 pi 无 include → 构建期扁平化） | 声明里写实现方式 |
| **豁免** | 做不到，但影响可接受 | `exemptions.yaml`，含理由 + 复核期限 |
| **拒绝** | 做不到且影响不可接受（如某 harness 无法隔离隐式技能源） | 该 harness 不能通过 `conformance`，不予支持 |

**禁止第四种：静默降级。** 这是两份上位文档里 dsh 最痛的教训（实验 A：patch target 不存在，只打警告、exit 0、继续运行）。

### 5.5 已知静默失败表（强制交付物 `failures.md`）

每个适配器必须交付一张表，每行必须配一个**可执行的检测用例**（进 `conformance`）。dsh 的示例：

| 现象 | 真实原因 | 检测方式 | 检测归哪个闸门 |
|---|---|---|---|
| 改了配置没生效 | patch target id 不存在，**exit 0 继续运行** | 注入一个不存在的 target，要求报错 | 闸门 1 |
| 插件没加载 | `peerDependencies` 与 dsh 版本不符被跳过 | 比对 `doctor` 的技能/插件清单与声明集合 | 闸门 2 |
| **业务级增强没加载** | profile 里 `insert:` 的 row 落空 / 插件被跳过 | 比对 `doctor` 的扩展 id 集合与 `enhancements.yaml` 声明集合 | 闸门 2 |
| 工具没出现 | MCP 连接失败，`failOnStartupError: false` 静默降级 | 断网探针必须让闸门 3 失败 | 闸门 3 |
| 行为与本地不一致 | macOS 无 landlock；容器内有 | 安全断言只在容器内跑（§7.2） | 闸门 4 |

pi 的示例（来自 pi 约束 1/3）：

| 现象 | 真实原因 | 检测方式 | 闸门 |
|---|---|---|---|
| 端点配了没生效 | `models.json` 的 `baseUrl` 不做环境插值 | 断言渲染产物里的端点来自参数层 | 闸门 2 |
| 出现未声明的技能 | `$HOME/.agents/skills` 无法用配置排除 | 断言实际技能集合 == 声明集合 | 闸门 2 |
| **增强没生效** | 扩展加载抛错被忽略（约束 7：扩展入参未校验） | 比对 `doctor` 扩展 id 集合与 `enhancements.yaml` 声明集合 | 闸门 2 |

### 5.6 合规测试套 `conformance/`（N11）

新 harness 的准入门槛。每个 harness 必须全过，且**不需要修改 `core/`**。**C1–C10 全部为阻断性门槛**（P3 已定）：任何一项告警即视为不通过——会被软化的往往正是 C5/C8 这两类最危险的退化。

| 用例组 | 验证什么 |
|---|---|
| C1 声明完整性 | `adapter.yaml` 含全部必填能力项；无未知项 |
| C2 渲染确定性 | 同定义渲染两次，产物与 digest 完全一致 |
| C3 渲染完整性 | 定义里每个非空字段在产物中有对应表达（或有声明豁免） |
| C4 解析自证不变量 | `doctor` 输出必含 §5.3 的七个字段，且技能 / 连接器 / **扩展**集合 == 声明集合 |
| C5 静默失败检测力 | 注入 §5.5 的每条失效场景，**必须报错**；任何一条静默通过即判失败 |
| C6 零凭据闸门 3/4 | 假网关下探针与冒烟通过（N14） |
| C7 轨迹合规 | 原生事件映射后符合 `core/trace/schema.json` |
| C8 参数层隔离 | 把 §2.3 禁止项当参数注入 → 无效或报错（**不得静默生效**） |
| C9 安全下限声明一致 | 声明的安全能力与容器内实测一致（不许夸大） |
| C10 退出码契约 | §8.2 退出码语义逐条验证 |

**C5 与 C8 是这套测试的灵魂**：它们把"文档里写的纪律"变成"不通过就不能接入"。

### 5.7 新增一个 harness 的完整清单

```
1. mkdir adapters/<h>/；写 adapter.yaml（§5.2 全部字段，unsupported 也要写）
2. 写 render.mjs（确定性，输入中性定义 + 基座种子）
3. 写 doctor.mjs（必须报告 §5.3 七个字段，含扩展清单）
4. 写 probes/{model,skills,connectors} 与 smoke
5. 写 trace.mjs（原生事件 → 统一 schema）
6. 写 failures.md（每条配 conformance 用例）
7. 写 seed/ 与 image/Dockerfile.partial；基座镜像按 BASE_HARNESS 组合
8. 逐条实跑 §10/§11 同类的"实测约束"清单（隐式加载源、端点可否外置、配置目录可写性）
9. conformance 全绿；core/ 无 diff
10. 更新能力目录里"支持该字段的 harness"一列
```

步骤 8 是关键：**两份上位文档的最大价值不是结论，而是"换 harness 必须逐项重测什么"这张清单**（pi §2.1 八条 + dsh 实验 A–E）。

## 6. 【不变量】验证体系：四道闸门

### 6.1 总览与映射

两份上位文档各自有一套验证口径，形状相同、粒度不同：

| 闸门 | 回答的问题 | dsh 六关对应 | pi 四层对应 | 凭据 |
|---|---|---|---|---|
| **1 静态** | 定义合法吗？引用都存在吗？ | 关 1 配置合法 | `make typecheck` | 否 |
| **2 解析自证** | harness **实际**加载了什么？ | 关 2 能启动 | `make doctor` | 否 |
| **3 集成探针** | 组成部件真的可达吗？ | 关 3 模型 / 关 4 技能 / 关 5 连接器 | `make verify` | 模型可用假网关替代 |
| **4 端到端** | 它能干活吗？ | 关 6 能完成任务 | `make smoke` | 是 |

**与 `-pi` 候选稿的五层（L0–L4）是一一映射**：`L0 静态 → 闸门 1`、`L1 解析 → 闸门 2`、`L2 装配 + L3 运行时六关 + L4 零凭据自证 → 闸门 3/4`。两者是同一条阶梯的不同粒度——本文把"装配 / 运行时六关 / 零凭据冒烟"并进"集成探针 + 端到端"两道，因为闸门 3 的假网关已经把"零凭据"内建进去了（§6.4）。

**关键升级**：pi 的 `doctor`（解析自证）在统一设计里从"一个好用的命令"升格为**所有适配器的强制接口**（N13）。理由：**dsh 的失败是静默的，而"让 harness 报告它实际加载了什么"是对治静默失败最有效的手段**——它不依赖我们枚举所有失败模式，而是让 harness 自己暴露状态。这是综合分析两份文档得到的最有价值的一条结论。

### 6.2 闸门 1：静态校验

| 检查 | 说明 | 失败信息要求 |
|---|---|---|
| schema 校验 | `core/spec/*.schema.json` | 文件 + JSON Pointer |
| 引用完整性 | `model.route` 必须是适配器路由目录里的名字；`connectorsFile`/`skillsDir` 必须存在 | 文件 + 字段 + **可选值列表** |
| 凭据引用 | 每个 `credentialRef`/`urlRef` 必须在参数层清单里有对应项 | 引用名 + 应写进哪个文件 |
| 命名约束 | `name` 正则；MCP `serverName` 命名空间规则 | 值 + 正则 |
| 层纪律 | §2.3：字段所在层与能力目录声明是否一致 | 字段 + 违反的纪律 + 正确位置 |
| 增强纪律 | §4.5：业务级增强不得与中性定义重复表达同一字段 | 两处位置 |
| harness 静默失败补洞 | 适配器声明的"闸门 1 级"检测用例 | 见 §5.5 |

**必须做到"注入式负向全绿"**：`conformance/C5` 的每个注入场景都要在这里被抓到，且**不能只打警告**（这是对 dsh 静默通过的直接修补）。

### 6.3 闸门 2：解析自证（强制接口）

`doctor` 必须输出的七个字段（缺一即 `conformance` 失败）：

| 字段 | 为什么必须有 |
|---|---|
| `harness` + `version` | 行为随上游版本变（dsh 基线是 RC）；轨迹与排障需要它 |
| `definitionPath` | 确认加载的是**这一份**定义，不是宿主或缓存里的别的 |
| `skills[]` | 对治"隐式加载源关不掉"（pi 约束 3/4）与"技能没加载" |
| `connectors[]` | 对治"工具没出现但静默降级"（dsh `failOnStartupError: false`） |
| `enhancements[]` | 对治"业务级增强静默没加载"（§4.5）——这是企业智能体的**常态**需求，不是边缘情况 |
| `modelRoutes[]` | 对治"路由名写错只在请求时暴露"（dsh `MISSING_CREDENTIAL`） |
| `effectiveConfigDigest` | 可复现性的载体（§6.7） |

**三条硬断言**（所有 harness 相同）：

1. **技能**：`skills` 集合 == **基座不变量技能集合 ∪ 智能体定义技能集合**。两个集合都必须来自声明（不变量技能声明在 `core/catalog/`，智能体技能声明在定义里）；**多一个也不行**——多出来的说明隐式加载源没隔离干净（pi 约束 3/4、dsh 的六个 rank 根）。
2. **连接器**：`connectors` 中 `enabled: true` 的集合 == 定义声明的启用集合。少一个就是静默降级（dsh `failOnStartupError: false`）；基座若注入了通用连接器，必须在基座能力目录里声明，且默认 `enabled: false`（不进入断言集合）。
3. **扩展**：`enhancements` 的**已加载扩展 id 集合 == `harness/<h>/enhancements.yaml` 声明的 id 集合**。少一个就是静默失败（pi 扩展加载抛错、dsh `skipping profile bundle`、profile row 落空）；多一个说明有未声明的增强混入产物（逃过评审）。这条断言把"业务级增强"从"最容易静默失败的地方"变成"必须自证的地方"。

### 6.4 闸门 3：集成探针

| 探针 | 做什么 | 零凭据模式 |
|---|---|---|
| `probe/model` | 一次最小推理，断言"有返回" | 假网关（`tools/fake-gateway`，支持流式与工具调用）。**必须同时断言 `tools=N>0`**——企业网关最常见的故障是吞掉 `tools` 字段或降级流式（pi 实测结论） |
| `probe/skills` | 每个技能进入会话目录 | 需要模型可用 → 用假网关 |
| `probe/connectors` | 每个 MCP 服务器连通 + 工具出现在工具列表 | 需要模型可用 → 用假网关；服务器不可达时**必须失败**（不许静默） |

**假网关是 harness 无关的**（pi §2.3 已确认），只需按 harness 的协议适配。它让闸门 1–3 在**零凭据**下可跑，这是 N14 的实现方式，也是基座自身回归能脱离外部依赖的前提。

> **实现期实测补充（2026-09-25）：`probe/model` 需要链路观测，不能只靠 harness 自报。**
>
> 实测确认：pi 的事件流里**没有** wire 级的 `tools` 计数与 `stream` 标志（见 §8.3 缺口 G1）。而"企业网关最常见的故障是吞掉 `tools` 字段或降级流式"恰恰只有**在链路上**才看得见。
>
> 因此 `probe/model` 的形态是：**把一个记录代理放在智能体与真实端点之间**，由代理观测并断言 `tools=N>0` 与 `stream=true`。这带来两个好处：① 断言针对的是真实发出的请求，不是 harness 的自我描述；② 同一份代理逻辑可以复用假网关的协议适配层（`tools/fake-gateway/protocols/`），假网关退化为"答得确定的代理"。
>
> **反过来说**：只用假网关而不做链路观测，能验证"模型可达"，但验证不了"网关没吞 tools"——那正是最需要验的一条。


### 6.5 闸门 4：端到端冒烟

- 输入：定义里声明的冒烟任务（默认模板给一个确定性任务，不依赖真实外部系统）。
- 断言：**退出码 0 + 输出包含预期标记 + 轨迹文件符合 schema + 未出现未声明工具**。
- 容器内运行，且在加固参数下运行（`--cap-drop ALL`、`no-new-privileges`、非 root）——pi 已实测该组合下 smoke 仍通过。

**冒烟任务定义在中性定义里（harness 无关）**，这是 §6.6 等价性可验证的前提。

### 6.6 跨 harness 等价性（N9，本文新增）

```
HARNESS=pi  render → doctor → smoke ┐
                                    ├─→ 断言集比对 → OK / 差异化
HARNESS=dsh render → doctor → smoke ┘
```

**比对内容（限可移植核心）**：技能集合相等、连接器 `name` 集合相等、`model.route` / `model.name` 相等、冒烟断言集相同且都通过、`effectiveConfigDigest` 各自存在且可复算。

**不比对**：工具命名、提示词文本、工具调用顺序、token 数、耗时。

**豁免机制**：`adapters/<h>/exemptions.yaml`

```yaml
- id: tool-naming
  scope: tools.names
  reason: 工具名 mcp__<server>__<tool> 由 harness 决定，业务不依赖
  reviewBy: 2027-03-31
```

`validate` 检查：豁免条目未过期；豁免涉及的字段确实在比对集中；**没有"沉默的差异"**——比对集里任何不等项若无豁免条目，`verify` 直接失败。

### 6.7 `verify` 的输出契约与退出码

```json
{
  "agent": "contract-review",
  "harness": "pi",
  "harnessVersion": "0.87.1",
  "definitionDigest": "sha256:…",
  "artifactsDigest": "sha256:…",
  "paramNames": ["CORP_GATEWAY_BASE_URL", "JIRA_TOKEN"],
  "effectiveConfigDigest": "sha256:…",
  "gates": [
    { "id": "static",     "ok": true,  "checks": [] },
    { "id": "resolution", "ok": true,  "checks": [] },
    { "id": "probes",     "ok": true,  "checks": [] },
    { "id": "smoke",      "ok": true,  "checks": [] }
  ],
  "usable": true
}
```

**`effectiveConfigDigest`** = `H(harness 版本 + 适配器版本 + artifactsDigest + 参数名集合)`。

- **参数名进 digest，参数值不进**：这既保证了"同一制品 + 同一组参数 = 同一行为"（N19），又不会把密钥写进日志。
- 排障时可以回答"当时生效的到底是什么"（R7 的原始诉求），并且**只要 digest 相同，行为必然相同**——这是 dsh 原设计做不到的（`!!js process.env` 的取值漂移连 golden snapshot 都抓不到，dsh 实验 D）。

**stdout 只放这份 JSON；人读的日志与轨迹走 stderr**（§8.2）。

**退出码**：

| 码 | 含义 |
|---|---|
| 0 | 通过 |
| 2 | 用法/参数错误 |
| 10 | 闸门 1 静态校验失败 |
| 20 | 闸门 2 解析自证失败（含集合不符） |
| 30 | 闸门 3 集成探针失败 |
| 40 | 闸门 4 冒烟失败 |
| 50 | harness 未预期崩溃 / 无法解析其输出 |

### 6.8 "可用"的判定

沿用 dsh §2.2 的口径并保持严格：**"可用" = 四道闸门全过**，不是"能启动"。

**并且验证能力必须在基座里，不能在应用里。** 应用作者既没有能力、也不该自己判断"配置是否真的生效"——§5.5 的静默失败清单正是这类问题的来源。

**"可用"是决策点，不是上线点**（§1.1）：四闸门全绿意味着"这个想法被证明走通了"，产出的是验证证据与可复现制品（§8.1）；之后是否进入生产化是另一个决策，不回头改基座。

## 7. 【不变量】安全与凭据

### 7.1 安全下限的归属（G4，本文新增）

两份上位文档的安全能力不对等（pi 有 R2 且已实现，dsh 只有 Linux landlock + fail-closed 审批），必须明确谁负责什么：

| 层 | 负责 | 理由 |
|---|---|---|
| **容器 / 编排层** | 硬下限：非 root、能力裁剪、无新特权、只读根文件系统、出站网络策略、密钥挂载 | 与 harness 无关，且 harness 换不掉它。这是**唯一**能对两个 harness 一致承诺的下限 |
| **harness 适配器** | 该 harness 能额外提供什么（dsh：landlock 沙箱、权限预设；pi：写保护扩展），**必须如实声明** | 能力不对等，声明后才能被 `conformance/C9` 校验"不夸大" |
| **智能体定义** | 边界内的工具白/黑名单 | 属业务决策（pi 附录 B：`defaultTools` 收窄策略刻意不在基座层解决） |

**硬下限清单在 `conformance/C9` 里逐条断言**：任何 harness 都必须在下限内可运行。

### 7.2 基线下限清单（容器层，两个 harness 一致）

> **本清单的存在理由是"让验证环境足够接近生产、结论才可信"，不是"为生产部署加固"**（§1.1：核心目标是验证走通，不是生产上线）。安全断言只在容器内算数（§9.2）——验证环境若比生产松太多，走通就不可信；但基座不承接生产上线本身的加固责任。

| 项 | 取值 |
|---|---|
| 运行用户 | 非 root（pi 基线用 uid 10001） |
| 能力 | `--cap-drop ALL` |
| 特权提升 | `no-new-privileges` |
| 根文件系统 | 尽量只读；可写卷白名单见 §8.4 |
| 出站网络 | 默认拒绝，按连接器清单显式放行 |
| 离线 | 运行期默认不出网拉依赖（pi 的 `PI_OFFLINE=1` 思路通用化） |
| 密钥 | 只从挂载/环境注入，永不进镜像、永不进定义文件 |
| 调试工具 | **不进生产镜像**；调试走 `agent-base:<h>-debug` 变体（§8.5） |
| 凭据存储文件权限 | **不承诺对 agent 隔离**（dsh §3.10 已知限制：agent 工具进程以同一 OS 用户运行）→ 隔离由编排层负责 |

### 7.3 harness 增强的声明与实测

| harness | 增强 | 已知边界 |
|---|---|---|
| dsh | `dsh-permission-presets` + `dsh-sandbox-policy`；`landlock` **仅 Linux** | **无审批应答者时 fail closed** → 无人值守容器必须显式设为自动放行，否则卡死 |
| pi | `defaultProjectTrust: "never"`；写保护扩展（拦 `.env`/`.git/`/`node_modules/`）；`PI_PROTECTED_PATHS` 可扩展 | 无 OS 级沙箱；未启用只读根文件系统、无出站白名单（由 §7.2 补齐） |

**结论**：安全相关行为**必须在容器内验证**，本地 macOS 上验证通过不构成证据（§9.2）。

### 7.4 凭据模型

- **引用分离**：定义里只写 `credentialRef` / `urlRef` / 路由名，取值来自参数层（N18）。
- **查找优先级**（合并两边，取显式的那个）：`启动环境变量 > 凭据存储文件 > 项目 .env > harness home 的 .env`。**环境变量最高**，与企业环境的 K8s Secret / Vault / CI 变量注入方式一致。
- **校验**：`validate` 检查每个引用在参数层清单里有定义；闸门 3 检查每个引用在运行时**能解析出非空值**（dsh 的 `MISSING_CREDENTIAL` 只在请求时暴露 → 探针必须前置抓到）。
- **轮换**：凭据变更不得需要重建制品（N21）。dsh 原生支持按请求解析（改路由下一请求即生效）；pi 需重启容器。

### 7.5 写保护与不可逆操作

- 基座默认拦截对 `.env`、`.git/`、`node_modules/` 等路径的写入（pi 扩展；dsh 侧用适配器插件实现——**待实测**，属 dsh 适配器交付物）。
- 容器内以非 root + 只读根文件系统兜底：即使 harness 层拦截失效，写入也失败。
- **企业场景的不可逆操作**（推代码、删数据、发消息）不在基座层用"审批流"解决（§1.5 不做审批流），而是：容器层不出网/不出凭据 → 结构上做不到。

## 8. 【不变量】交付契约

### 8.1 镜像契约与派生

```
registry/agent-base:<base-ver>@sha256:<digest>          ← 基座镜像：core + adapters/<h>
        │  FROM
        ▼
registry/<agent-name>:<ver>@sha256:<digest>             ← 智能体镜像：只 COPY 渲染产物
```

- 基座镜像**按 harness 出一个**（`agent-base:pi-<ver>`、`agent-base:dsh-<ver>`），或出一个多 harness 镜像（体积换简单）。**本项目决策：按 harness 分镜像**——pi 与 dsh 的依赖树差异大，合并只会让两边都变重。
- 智能体镜像必须 `FROM <base>@sha256:<digest>`（digest，不是 tag），这是 N19 可复现性的载体。
- **换基座版本 = 改 `FROM` 的 digest**（pi §3.4 的做法，通用化）。
- 容器交付镜像**不接受 `--patch` 等运行期行为覆盖参数**（§2.2 副作用一）；入口脚本遇到这类参数必须失败。

**镜像文件系统结构（业务代码落在哪）**——业务代码是"行为"，只进**智能体镜像的薄层**，绝不进基座镜像（§1.2 基座不含业务）：

```
my-agent:<ver> 镜像文件系统
├── （基座层 · 来自 base:<ver> · 只读）
│   ├── harness 运行时 + 不变量     pi: /opt/pi/agent        dsh: $DSH_HOME
│   └── 基座工具                    entrypoint / doctor / probe / verify
│
├── （智能体层 · COPY 渲染产物 · 行为在此冻结）
│   ├── 声明渲染产物                pi: agent-dir/            dsh: $DSH_HOME/profiles/<name>/
│   ├── 业务技能 + 脚本             skills/<name>/{SKILL.md, scripts/}
│   ├── 自研连接器代码              mcp-servers/<name>/
│   └── 业务级 harness 增强          pi: agent-dir/{extensions,agents,prompts}/   dsh: $DSH_HOME/node_modules/<plugin>/ + profile rows
│
└── /data（可写卷 · 挂载 · 不烤入）  会话/状态、轨迹导出、工作区
```

| 业务代码落点 | 内容 | 谁引用 |
|---|---|---|
| `skills/<name>/scripts/` | 技能的可执行部分（脚本/工具） | SKILL.md 相对路径引用 |
| `mcp-servers/<name>/` | 内部系统无现成 MCP server 时自写的 server | `connectors.yaml` 的 `stdio.command` 相对路径引用 |
| `harness/<h>/` | **业务级 harness 增强**：自定义工具 / 钩子 / 中间件 / 插件 / 子智能体 / 命令 | `enhancements.yaml` 声明 id；harness 按各自机制注册（§4.5） |

**渲染器职责新增**：把业务代码（`scripts/`、`mcp-servers/`、`harness/<h>/`）连同声明一起确定性打包进渲染产物，并把相对引用解析成镜像内固定路径；`harness/<h>/` 的增强还要按 harness 的注册机制挂上（pi：`settings.json` 的 `packages` / extensions 目录；dsh：profile 的 `insert:` row + `node_modules` 插件）。

**镜像语义**：本文的智能体镜像是**验证快照**（同一 digest 可重跑、可交接），**不是生产镜像**（为部署服务）——§1.1 核心目标是验证走通；生产化是走通之后的另一个阶段。

### 8.2 进程契约

| | 约定 |
|---|---|
| **退出码** | §6.7 的表（验证工具与运行时共用同一套语义） |
| **stdout** | **只放结果**：批处理模式下是任务输出；验证模式下是 `verify --json` |
| **stderr** | 人读日志 + 统一轨迹事件（JSONL） |
| **`AGENT_RUN_MODE`** | `interactive`（默认，人用）/ `oneshot`（`-p` 语义，CI 用）/ `rpc`（常驻，平台接入）/ `debug`（交互式调试运行时，**仅 debug 变体镜像**，§8.5） |
| **参数分派** | 无参数 = `interactive`；`-` 开头 = 透传 harness 原生参数；其它 = 命令（pi entrypoint 已实测的做法，通用化） |
| **EPIPE** | 客户端提前关闭 stdout 会让子进程崩溃（pi 实测）→ RPC 客户端必须持续读取；基座侧捕获 EPIPE 并给出明确错误而非崩溃 |

> `rpc` / `oneshot` 在此阶段是**验证入口**（被验证脚本/测试框架调用），不是生产常驻服务；生产化的鉴权、会话归属、并发不在基座范围（§1.5）。

### 8.3 统一轨迹与审计事件（N24，G3）

**为什么必须统一**：企业要回答"这个智能体为什么这么决策"（dsh §4.10），而两个 harness 的原生轨迹形状不同：dsh 是会话轨迹 + 日志插件，pi 是**会话 JSONL 文件 + 结构化事件流**。审计工具不能按 harness 分叉。

> **实现期实测修正（2026-09-25）**：本节原文写"pi 是扩展打 stderr 一行"——**这不准确**。实测 pi 0.87.1 有两套原生轨迹能力：
> ① `--mode json` 输出**结构化 JSONL 事件流**（`session` 头 + `agent_start`/`turn_*`/`message_*`/`tool_execution_*`/`compaction_*`/`auto_retry_*`/`thinking_level_changed` 等），且 stdout 专供 JSONL、诊断走 stderr —— 与 §8.2 的进程契约天然一致；RPC 模式复用同一套事件形状。
> ② 版本化**会话文件**（`~/.pi/agent/sessions/--<path>--/<ts>_<id>.jsonl`，v3，用 `id`/`parentId` 构成树，支持就地分支）。
> 因此 pi 适配器**不需要自建审计扩展**来做基本轨迹 —— 它的职责是**映射**（原生事件 → 统一 schema），见 `adapters/pi/trace-mapping.md`。

**三处必须写清的缺口（否则"统一轨迹"会变成假的安全感）**：

| # | 缺口 | 后果 | 处置 |
|---|---|---|---|
| G1 | 事件流里**没有 wire 级的 `tools` 计数与 `stream` 标志**（实测：19,215 条事件里无顶层 `tools` 字段；`toolsAdded` 只是 harness 侧的工具集合，不是发往端点的那份） | §6.4 门 3 最关键的两条断言（网关吞 `tools`、静默降级流式）**无法**由 harness 事件流支撑 | **必须在链路上观测**：本地记录代理，或网关侧埋点。见 §6.4 的补充 |
| G2 | `tool_execution_end` **没有耗时字段**（实测字段只有 `isError`/`result`/`toolCallId`/`toolName`/`type`） | `tool.result.ms` 只能按事件到达时间推算 | 统一轨迹里该字段必须标注为**推算值**，不许当实测值用于性能结论 |
| G3 | `tool.call.decision`（allow/deny/ask）**没有原生字段** | 审批语义缺失，"谁放行了这次调用"答不上来 | 在补上审批扩展之前，只能记为 `allow`（执行了即放行）——这是**诚实近似，不是等价**，须进 `exemptions.yaml` |

**未被统一 schema 覆盖的原生事件**（`compaction_*` / `auto_retry_*` / `queue_update` / `entry_appended` / `thinking_level_changed`）：按 P1 决策**先全部走 `native.raw` 并带 `reason`**，不急着升格为正式类型 —— 等真的出现"要按类型查询"的需求再提升（P-c 后验统一）。

**约定**：JSONL，一行一个事件，字段如下（`core/trace/schema.json` 为真源）：

```json
{"ts":"2026-09-25T10:00:00Z","seq":12,"run":"<uuid>","agent":"contract-review",
 "harness":"pi","harnessVersion":"0.87.1","effectiveConfigDigest":"sha256:…",
 "type":"tool.call","tool":"mcp__jira__get_issue","inputDigest":"sha256:…","decision":"allow"}
{"type":"tool.result","ok":true,"ms":840,"outputDigest":"sha256:…"}
{"type":"model.request","route":"corp-gateway","model":"corp-think","tools":10,"stream":true}
{"type":"model.error","code":"MISSING_CREDENTIAL","route":"corp-gateway"}
{"type":"gate","name":"connectors","target":"jira","ok":true}
```

| 规则 | 说明 |
|---|---|
| 工具入参只存 digest，不存明文 | 防泄漏；需要时按 digest 去会话目录取 |
| `effectiveConfigDigest` 每条事件都带 | 事后归因不需要再追问"当时生效的是什么" |
| 默认落 stderr | 容器友好（`docker logs`），可通过 `AGENT_TRACE_DEST` 另存文件 |
| 映射失败必须显式 | 适配器的 `trace.mjs` 遇到无法映射的原生事件时，必须输出 `{"type":"native.raw",…}` 而不是丢弃；`conformance/C7` 检查无静默丢弃 |

> **实现期增补：业务层介入轨迹 + 可视化（2026-09-25）**
>
> 轨迹不是只给审计看的黑箱排气口——**业务开发层要能介入**，且**值得可视化**。为此在核心字段之外补三处受控设计（详见 `core/trace/README.md`）：
>
> | 增补 | 内容 | 为什么这样切 |
> |---|---|---|
> | **`biz` 扩展位** | 任何事件都可挂 `biz`：键为小写点分命名空间（`contract.id`），值只允许标量 | 核心字段冻结（`additionalProperties: false`，让上游新字段响亮暴露），业务的需求走受控扩展位。标量约束保证可 diff、可渲染 |
> | **`biz.event`** | 业务可发自己的领域事件（`name` 强制带命名空间，如 `contract.risk_found`） | 让轨迹成为**业务叙事**而非工具调用流水——这正是"为什么这么决策"的答案所在 |
> | **`run.meta.contentMode`** | `digest`（默认）｜`full`（含明文，供可视化与排障） | §8.3 的"只存 digest 防泄漏"与"可视化要看到内容"直接冲突。解法不是选一边，而是**显式标注**：含明文的轨迹是敏感件，不能在下游被当成同一种东西 |
> | **`tool.call` / `tool.result` 的 `callId` 必填** | 调用与结果的关联键 | 没有它就画不出调用配对与耗时，可视化只能线性回放 |
>
> **可视化的定位**：可视化工具是独立产物，不属 `core/`。但**它需要轨迹保证的东西已写进 schema**（UTC 时间戳 + 单调 `seq`、`run` 分组、`callId` 配对、`type` 判别、`effectiveConfigDigest` 归因、`contentMode` 标注）。schema 这边的责任是"让轨迹可被可视化"，不是"提供一个可视化器"。
>
> **取向**：本基座的核心目标是验证走通而非生产上线（§1.1），因此验证/可视化场景默认可取 `contentMode: full`；但必须打标，且生产化阶段要收回来。


### 8.4 日志、可写卷、健康检查

| 项 | 约定 |
|---|---|
| 日志 | 人读日志 → stderr；轨迹 → stderr（默认）或 `AGENT_TRACE_DEST` 文件 |
| 保留策略 | 由编排层定；基座只保证"可导出、可重放" |
| 可写卷 | 会话/状态目录（harness 需要写配置目录：pi 约束 2）、轨迹导出目录、工作区挂载点。**根文件系统只读时，这三个必须显式挂载** |
| 健康检查 | `interactive`/`oneshot`：进程存活即健康；`rpc`：适配器提供一个"零凭据可答"的探针调用（pi 的 `--mode rpc` + `get_state` 已实测无需凭据） |
| 离线自检 | 容器内 `make doctor` 必须可跑（不需网络），供 K8s readiness 使用 |

### 8.5 调试手段

基座镜像本身携带三道**零侵入**调试面，第四道走**调试变体镜像**。原则：**调试面按侵入性递增；生产镜像只含前三道，交互式调试运行时及其工具绝不进生产镜像**——否则违反 §7.2 的最小权限 / 只读根 / 默认离线，并把调试行为与交付行为混进同一制品。

| 道 | 手段 | 何时用 | 侵入性 |
|---|---|---|---|
| ① 自证 | 容器内 `make doctor`（闸门 2 解析自证，零网络） | 先问"harness 实际加载了什么" | 无（已在基座） |
| ② 轨迹 + 退出码 | 统一轨迹 JSONL 到 stderr（`docker logs -f` 即读）+ §6.7 退出码定位失败层 | "它做了什么、在哪一步失败" | 无（已在基座） |
| ③ 诊断重放 | 容器内 `make probe HARNESS=…` 单跑闸门 3 探针 | 把"网络层 vs 配置层"问题分开（§6.4） | 无（已在基座） |
| ④ 交互式调试运行时 | `agent-base:<h>-debug` 变体 + `AGENT_RUN_MODE=debug`：agent 交互会话 + 人在环审批 + 诊断 shell | 前三道只回答"过没过"，④回答"为什么这样、换种做法会怎样" | 有（仅 debug 变体） |

**④ 不是"跑更多测试"，而是一个交互式运行环境**——前三道（① 自证 / ② 轨迹 / ③ 重放）是**验证**，回答"过没过"；④ 是**交互**，回答"为什么这样、我想让它换种做法会怎样"。它由三个能力组成：

| 能力 | 干什么 | 对应机制 |
|---|---|---|
| **交互式 agent 会话** | 发消息 / 派任务，实时看工具调用与结果、已加载技能、模型路由 | harness 原生 `interactive`/tui + 轨迹实时流到 stderr |
| **人在环审批** | 逐条 approve / deny 工具调用，调试危险或不可逆操作 | dsh 权限预设 / pi 审批 |
| **诊断 shell** | 查文件、进程、生效配置 | 调试层工具（shell / curl / ripgrep / jq） |

**调试变体镜像（④）**：

```
registry/agent-base:<h>-<ver>@sha256:<digest>          ← 生产基座镜像
        │  FROM（同 digest）
        ▼
registry/agent-base:<h>-debug                           ← 只加调试层：shell/curl/ripgrep/jq + 交互调试入口
```

| 规则 | 说明 |
|---|---|
| **同 digest 派生** | debug 变体 `FROM base@sha256:<digest>` 只加一层调试工具，**不改渲染产物与行为定义**——保证 debug 时跑的就是生产那套（N19），杜绝"debug 正常、生产崩"的漂移 |
| **显式标记** | debug 态在轨迹首行输出 `{"type":"run.meta","mode":"debug"}`，与交付态可区分（呼应 §11.3 把调试行为与交付行为分开的同一纪律） |
| **临时放开仅限 debug 镜像** | 可写层、出站网络只在 debug 变体里放开（且需显式挂载），生产镜像仍保持只读根 + 默认离线（§7.2） |
| **不进生产镜像** | 调试工具（shell、curl 等）有攻击面（出站、shell 逃逸），**绝不烤进生产基座镜像**；`conformance/C9` 断言生产镜像不含调试工具 |
| **入口脚本拒绝越权** | 生产镜像的 entrypoint 遇到 `AGENT_RUN_MODE=debug` 必须失败（退出码 2）；只有 debug 变体的 entrypoint 接受它 |

**与本地 `run-local` 的关系**：§9.3 的 `run-local` 是**本地开发期**的交互；④ 是**容器里**的同一能力，用来复现"只在容器出现"的问题——Linux 沙箱、隔离 `HOME`、只读根文件系统、默认断网（§9.2 差异表）。同一个 harness `interactive` 能力，两个环境各一个入口，两者跑的是**同一份渲染产物**（本地挂载 / 容器烤入）。

**崩溃取证**：退出码 50（harness 崩溃）时，entrypoint 把轨迹最后 N 行摘要 + `effectiveConfigDigest` 打到 stderr 后退出，保证"连 shell 都进不去"时也有可读线索。

## 9. 【不变量】双入口与差异

### 9.1 两个入口

| | 本地开发入口 | 交付入口 |
|---|---|---|
| 形态 | harness 原生交互模式（dsh tui / pi 交互） | 容器内 `AGENT_RUN_MODE=oneshot` 或 `rpc` |
| 目的 | 调"想法" | 验"契约" |
| 配置来源 | 同一份中性定义（`render` 产物直接挂/软链） | 同一份渲染产物（烤进镜像） |
| 闸门 | 1、2（快，秒级） | 1、2、3、4（含安全断言） |

**Docker 只用于验证交付契约，不用于迭代。** 依据：dsh 的 HMR 只在 tui 上启用，headless/SDK/ACP 在 YAML 中显式禁用（dsh §3.9）；pi 改配置需重启。在容器里迭代等于放弃迭代速度。

### 9.2 本地/容器差异表（必须写进文档，不能靠人踩）

| 差异 | 本地（macOS） | 容器（Linux） | 影响 |
|---|---|---|---|
| OS 沙箱 | 无（dsh landlock 仅 Linux） | 有 | 安全行为**必须**容器内验证 |
| HMR | dsh tui 启用 | 默认禁用 | 迭代只在本地做 |
| 网络 | 通常可出网 | 默认不出网 | 依赖下载类操作本地成功 ≠ 容器成功 |
| 隐式技能源 | 宿主 `$HOME/.agents/skills` 存在 | 固定 `HOME` 且留空 | 本地可能多出技能，闸门 2 会在两边都抓 |
| 路径 | 宿主路径 | 挂载路径 | 定义里禁止绝对路径（schema 拒绝） |
| 参数层来源 | shell 环境 / `.env` | Secret 挂载 | 闸门 3 在两边都跑 |
| 文件权限 | 宿主 uid | uid 10001 | 挂载卷的属主需要对齐 |

**结论**：本地验证通过 ≠ 容器行为一致。安全相关与交付契约相关的断言，只在容器内算数。

### 9.3 本地开发环境与 run-local 挂载契约

§9.1 的本地入口隐含一个前提——"本机已装好 pin 住的 harness"。本节把它从隐含前提变成**一条命令可复现**，否则换台机器或来个新人会被卡在"装哪个版本、挂到哪"上（违背 §1.3 可接手性）。

| 命令 | 作用 |
|---|---|
| `make dev-env` | 按 `adapters/<h>/adapter.yaml` 的 `version` pin 安装/校验两个 harness 到一致版本，输出 `dsh --version` / `pi --version` 供确认 |
| `make run-local HARNESS=<h>` | 用**隔离的临时 HOME/DSH_HOME** 跑原生 harness，`render` 产物挂/软链进去 |

**run-local 挂载契约**（P-b 文件系统隔离：本地也不碰真实 `$HOME`，否则宿主机隐式技能源会混进来——§9.2 差异表第 4 行）：

| harness | render 产物 | 挂/软链到 | 参数层来源 |
|---|---|---|---|
| pi | `agent-dir/` | 临时 `$HOME` 的 agent-dir；其 `.agents/skills` 留空 | shell 环境 / `.env` |
| dsh | `profiles/<name>/` | 临时 `$DSH_HOME/profiles/<name>/` | shell 环境 / `.env` |

**本地环境自检**：`make dev-env` 之后 `make validate && make doctor` 全绿，即证明环境可用（无需网络）。这条自检与容器内的 `doctor`（§8.4 离线自检）是**同一命令、同一判据**——本地与容器共享一个"环境是否就绪"的口径。

## 10. 【harness 专有】pi 适配器

> 本节随 pi 版本变化。pi 升级时只复核本节。**待实测**标记表示该结论尚未在 pi 上验证。

### 10.1 实测约束（沿用 pi §2.1，原文八条）

| # | 实测事实 | 在统一设计里的处置 |
|---|---|---|
| 1 | `models.json` 的 `baseUrl` **不做**环境插值（只有 `apiKey`/`headers` 插值） | 声明 `nativeParamInterpolation: unsupported`；渲染器产出 `.tmpl`，entrypoint 在启动期用参数层渲染（这正是 §2.2 "参数下放"的实现） |
| 2 | 即使只跑 `--list-models` 也会**写**配置目录（`auth.json`、`models-store.json`） | 声明 `runtimeWritableConfig: supported` → 只读种子 + 启动暂存为可写副本 |
| 3 | `$HOME/.agents/skills` 是隐式发现路径，**配置无法排除**（`"!~/.agents/skills"`、`["-…"]`、`[]` 都无效） | 声明 `implicitSkillSources: partial` → **用文件系统隔离**（固定 `HOME`，其 `.agents/skills` 留空），并在 `doctor` 里硬断言集合相等 |
| 4 | 该路径**跟随 `$HOME`**（`HOME` 指向空目录时只剩 agent-dir 技能） | 容器内固定 `HOME=/home/agent`；本地开发时提示该差异（§9.2） |
| 5 | `settings.json` **无 include/extends**，不能多文件拼接 | 声明 `configInclude: unsupported` → 构建期扁平化（§2.2，天然满足） |
| 6 | 普通键"项目覆盖 user"，资源数组"两级并集" | 渲染器必须显式产出完整最终值，不依赖覆盖语义 |
| 7 | `tool_call` 事件的 `input` 无法仅凭 `toolName` 收窄（`CustomToolCallEvent` 把 `input` 定为 `Record<string, unknown>`） | 轨迹映射与写保护扩展必须**运行时收窄**（schema 校验入参），不得断言类型 |

## 11. 【harness 专有】dsh 适配器

### 11.1 实测机制（沿用 dsh §3，摘要）

| 机制 | 结论 | 在统一设计里的处置 |
|---|---|---|
| 四层配置合成 | bundle → profile → **home** → `--patch`，后者覆盖前者 | home 层内容**烤进基座镜像**；`--patch` 仅本地调试 |
| patch 语义 | `config` **整体替换**（非深合并）；`insert` 加 row | 渲染器产出完整 config，不做增量假设 |
| **patch 目标不存在** | **只打警告，exit 0，继续运行** | §5.5 静默失败表第 1 行；闸门 1 注入式检测 |
| bundle 契约 | `dsh.bundle.patch` 可为字符串或路径数组；bundle 之间**不可嵌套** | 渲染器产出扁平列表 |
| 模块解析根 | home 层解析 `$DSH_HOME/node_modules`（实验 E） | 企业插件装一次，烤进基座镜像，全局可见 |
| skills 发现 | 六个 rank 根（project-dsh / project-agents / custom / user-dsh / user-agents / bundled）；不支持嵌套发现 | 用文件系统隔离 + `doctor` 断言集合相等 |
| MCP | 每服务器一条 row；`failOnStartupError` 默认 false（连不上也启动） | §5.5 静默失败表第 3 行 |
| 权限/沙箱 | 预设捆绑沙箱+审批；无应答者时 **fail closed**；landlock 仅 Linux | §7.3：无人值守必须显式自动放行，否则卡死 |
| HMR | tui 启用；headless/SDK/ACP 显式禁用 | §9.1：本地用 tui 迭代，容器只验契约 |
| 凭据 | 环境变量 > 存储文件 > 项目 `.env` > harness home `.env`；**文件权限无法对 agent 隔离** | §7.4、§7.2 |
| 模型路由 | `dsh-llm-pi-ai` 的 `providers` 字典是唯一配置面；`apiKeyEnv` 按请求解析 | §11.4 |
| 已知限制 | `dsh-agent-default-model` **不验证目录成员资格** | 闸门 3 的模型探针即为此存在 |

### 11.2 渲染目标与映射

| 中性定义 | dsh 产物 | 说明 |
|---|---|---|
| `agent.yaml` → `persona.instructions` | profile 内的 agent 提示词 row | |
| `agent.yaml` → `model.route` / `name` | profile 内的默认模型 row + 路由名 | 路由名的**能力**在基座 home 层声明（§11.4） |
| `agent.yaml` → `tools.deny` | profile 内的工具 row（`disabled` / `config`） | |
| `connectors.yaml` | 每服务器一条 `dsh-mcp-client` row | `urlRef`/`credentialRef` 用 `!!js process.env.X`（原生支持） |
| `skills/` | profile 的 `customSkillDirs`（rank 300） | **智能体技能必须进 rank 300**：`$DSH_HOME/skills`（rank 400）是基座不变量技能的位置，放进那里会让所有智能体都带上它，闸门 2 的集合断言会失败（除非该技能确实属于基座不变量） |

| `harness/dsh/`（业务级增强） | `extensions/` 里的插件包 → `$DSH_HOME/node_modules/`；`enhancements.yaml` → profile 里 `insert:` 的新 row | 一等公民（§4.5）；row 落空是静默失败 → 闸门 2 断言扩展 id 集合 |

### 11.3 J2 对 dsh 的具体后果（本节终结 dsh 上位设计 §6.2 决策 1）

dsh 上位设计在"领域差异怎么表达"上二选一：`--patch` 文件（一镜像多智能体）或每个智能体一个 profile。**在"行为烤、参数下放"下这个两难消失了**：

```
registry/agent-base:dsh-<ver>            ← 基座镜像：$DSH_HOME/cordis.patch.yml（不变量）
        │                                    + $DSH_HOME/node_modules（企业插件，一次装）
        │  FROM + COPY 渲染产物
        ▼
registry/contract-review:<ver>           ← 智能体镜像：$DSH_HOME/profiles/contract-review/
                                             （构建期渲染，行为冻结、可评审、可签名）
```

| 规则 | 说明 |
|---|---|
| 每个智能体一个 profile，**构建期生成** | profile 文件是制品的一部分，可 diff、可评审（N1） |
| home 层只放"所有智能体完全一致"的东西 | 强化 dsh 实验 A 的教训：home 层钉住的 row 领域层改不动且失败静默——在新模型下只有"确实不该分叉"的东西才允许进 home |
| 交付镜像**不接受 `--patch`** | 入口脚本遇到该参数即失败（退出码 2）。本地调试允许，但 `doctor` 必须把 `--patch` 的 digest 计入 `effectiveConfigDigest`，使"调试过的行为"不可能被误当交付行为 |
| `!!js process.env` 只允许读参数层清单里的名字 | `validate` 检查 home/profile 里的 `process.env.X` 是否都在 `params.yaml` 里；读了清单外的名字 = 纪律违规 |

**这一条同时解决了 dsh 上位设计的另一个遗留风险**（"重述腐化"：`config` 整体替换导致 home 层重述的 row 随上游结构变化而过期且不报错）——因为渲染器产出完整 config 而不是增量 patch，且渲染产物有 digest。

### 11.4 dsh 模型路由（沿用 dsh 上位决策：能力在基座、选择在智能体）

基座 home 层声明**能力**（有哪些路由可用），智能体定义选择**用哪个**（§4.2 的 `model.route`）：

```yaml
# 基座镜像的 $DSH_HOME/cordis.patch.yml（能力，全企业统一）
- name: '@deepseek-ai/dsh-llm'
- name: '@deepseek-ai/dsh-llm-pi-ai'
  config:
    providers:
      corp-gateway:                       # 内网 OpenAI 兼容网关
        displayName: 企业网关
        apiKeyEnv: CORP_GATEWAY_API_KEY    # 只写引用名
        api: openai-completions
        baseURL: !!js process.env.CORP_GATEWAY_BASE_URL      # 参数层
        models: [{ id: corp-think, contextWindow: 262144 }]
      self-hosted:                        # 自托管
        apiKeyEnv: SELF_HOSTED_KEY
        api: openai-completions
        baseURL: !!js process.env.SELF_HOSTED_BASE_URL
```

| 点 | 说明 |
|---|---|
| 能力/选择分离 | 企业网关换地址 → 只改参数层，**不重建任何制品**（N21） |
| 手工路由键命名 | 必须是小写连字符标识符，否则无法走登录流程 → 这类路由必须用 `apiKeyEnv`（dsh 实测限制）；`validate` 检查路由名正则 |
| 会话级切换 | `/model` 是 harness 原生调试能力，**不算制品的一部分**，不进 `effectiveConfigDigest` |
| 网关新增模型 | 改的是基座层**能力目录**（`providers.<route>.models`），属低频变更 → 重建基座镜像。这与 §2.2"模型名选择属制品"不冲突：**有哪些模型可选**是能力，**这次用哪个**是智能体定义 |

## 12. 【本项目决策】落地设计

### 12.1 基座仓库文件清单与分层纪律

见 §2.4 的拓扑。**每个目录的 `README.md` 必须包含本层纪律**（N6），原话如下（写入文件头注释）：

| 位置 | 纪律原话 |
|---|---|
| `core/` | 放：中性定义规范、能力目录、闸门框架、统一轨迹 schema、基座镜像。**不放**：任何 harness 名字、任何业务概念的具体取值。 |
| `adapters/<h>/` | 放：该 harness 的渲染器、自证、探针、轨迹映射、失败表、种子。**不放**：跨 harness 共享的逻辑（那属于 `core/`）。 |
| 基座镜像的 harness home 层 | 放：所有智能体**完全一致**的东西（模型路由能力、安全姿态、审计、强制校验）。**不放**：任何智能体之间会分叉的东西——home 层钉住的 row 智能体层改不动，且失败静默。 |
| `template/` | 放：开箱可跑的最小定义。**不放**：TODO、占位符、多个示例的杂糅。 |
| `examples/` | 放：完整示例智能体。**不是基座的一部分，可整个删除**；删除后基座仍须能 `validate` + `conformance`。 |

**`core/` 的 harness 名禁令范围（实现期澄清，2026-09-25）**：上表 `core/` 那行的"不放任何 harness 名字"**只覆盖 `core/` 的代码与 schema**（`.mjs` / `.json`）——那里出现 harness 名，意味着把某个 harness 的约束当成了中性契约的一部分，那属于 `adapters/` 或本文。两处**明确豁免**，理由都是本文自身要求它们必须点名 harness：

| 豁免对象 | 依据 |
|---|---|
| `core/catalog/*.yaml` | §4.6 要求能力目录记录"支持该字段的 harness 及降级行为"——不点名就写不出来 |
| Markdown 文档（如 `core/README.md` 的纪律原话） | §12.1 的纪律本身必须点名，否则说不清"不放什么" |

执法方式：`tools/validate.mjs` 的 `core/harness-name` 检查（S0 已交付）。

### 12.2 派生模板（开箱可跑）

### 12.4 验收方式

**基座好不好用，由这两段流程证明。**

**流程甲（便捷启动）** —— 中途不需要理解任何 harness 概念：

```bash
make dev-env                          # ① 首次：按 pin 装两个 harness 到一致版本（§9.3，基座仓库里执行一次）
make new-agent NAME=my-agent          # ② 派生（基座仓库里执行一次）
cd my-agent                           # 之后都在派生目录里操作（Makefile 由模板生成）
$EDITOR agent.yaml connectors.yaml skills/example/SKILL.md    # 只写业务
make validate                         # ③ 静态
make run-local HARNESS=dsh             # ④ 本地调想法（HMR）
make verify HARNESS=dsh                # ⑤ 可用（四闸门）
make image HARNESS=dsh                 # ⑥ 交付镜像
```

**流程乙（换 harness）** —— 只改一个变量：

```bash
make verify HARNESS=pi,dsh     # 同一份定义，两个 harness，四闸门 + 等价性
```

**验收标准**：① 只需要业务知识；② 不出现 harness 术语；③ 给出明确的"可用/不可用"+ JSON 报告；④ 换 harness 不需要改定义（业务级增强除外），且等价性差异全部显式（豁免或失败）。

**走通后的交付（§8.1）**：流程甲的最后一步产出的是**验证证据包**——`verify --json` 结论 + 可复现的 `my-agent:<ver>@sha256` 快照 + 交接文档，支撑"继续投入 / 放弃 / 进入生产化"的决策，**不是生产上线**（§1.1）。

## 14. 风险与已知限制

合并两份上位文档的风险表，并补统一设计新增的风险：

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| 1 | **上游基线不确定** | dsh `0.1.7-rc.1` 是预发布；pi 迭代快（0.85.1 → 0.87.1） | 版本精确 pin；升级时只复核 §10/§11；`conformance` 是升级的回归网 |
| 2 | **静默失败** | dsh：patch target 不存在 / bundle 被 skip / MCP 连不上都不阻断；pi：隐式技能源关不掉 | 闸门 1 注入用例 + 闸门 2 集合硬断言 + §5.5 失败表 |
| 3 | **中性格式的最小公倍数** | 可移植核心只表达两个 harness 的交集，可能损失表达能力 | 业务级增强（§4.5）承接表达力 + 能力目录显式标注"支持该字段的 harness"；增强带来的不可移植性被 `validate` 显式告知 |
| 4 | **渲染层自身成为 bug 源** | 多一层翻译，就多一处可能出错 | `conformance/C2/C3`：渲染确定性与完整性；渲染产物进 git（可 diff、可评审） |
| 5 | **一致性幻觉** | "定义相同"不等于"行为相同" | §1.4 明确承诺边界；§6.6 断言集比对；不允许沉默差异 |
| 6 | **双 harness 维护成本** | 两套适配器 + 两套回归 | `core/` 零 harness 依赖（新增 harness 不改 core）；`conformance` 把成本前置为一次性门槛 |
| 7 | **重述腐化**（dsh 原风险） | `config` 整体替换，重述的 row 随上游结构变化而过期且不报错 | §11.3：渲染器产出完整 config；渲染产物有 digest；升级走复核 |
| 8 | **基座层膨胀** | 便利性诱使把所有东西塞进基座镜像 | §12.1 纪律写入文件注释 + 参数层清单执法（§2.3） |
| 9 | **模型可用性无静态保障** | dsh 默认模型不验证目录成员资格；pi 端点靠启动期渲染 | 闸门 3 模型探针（含 `tools>0` 断言，防网关吞 tools） |
| 10 | **沙箱能力不齐** | macOS 无 OS 级沙箱；landlock 仅 Linux；dsh 审批 fail closed | §7.1 归属划分（容器层承担硬下限）+ §9.2 差异表 + 安全断言只在容器内算数 |
| 11 | **凭据无法对 agent 隔离** | agent 工具进程与 harness 同一 OS 用户 | 容器边界由编排层负责，不依赖 harness 内部隔离 |
| 12 | **上游文档缺失** | npm 包内无 docs 目录，只有包级 README | 两份上位文档的实测结论即为知识资产，沉淀在 §10/§11 |
| 13 | **企业网关保真度**（统一设计新增为重点） | 网关吞 `tools` 字段或降级流式 → 直接让"换端点不改制品"失效 | 闸门 3 强制断言 `tools=N>0`，把网络层问题与配置层问题分开；接真网关前先跑假网关 |
| 14 | **业务级增强侵蚀**（统一设计新增） | 业务团队把所有东西塞进 `harness/*`，可移植性名存实亡 | `validate` 显式输出可移植性等级；`exemptions.yaml` 有复核期限；增强不得与中性定义重复表达同一字段；**且增强是常态而非例外——不能靠"劝人少用"来治理，要靠显式标注与可复现** |

### 15.3 明确否决（保留记录，避免重复讨论）

沿用 pi 附录 A 的全部结论，并补统一设计新增的否决：

| 被否方案 | 否掉的理由 |
|---|---|
| 运行期分层（baseline + 工作区覆盖 + `--approve`） | 行为随 cwd 漂移；工作区配置是可执行代码，不该被任意检出的仓库自动加载 |
| 瘦镜像 + 配置由卷/ConfigMap 下发 | 同一镜像在不同配置下行为不同，违反 N19；把可执行内容的管控从镜像签名挪到平台 RBAC |
| SDK 内嵌（不跑 CLI） | 需自建服务外壳，失去斜杠命令 / MCP 面板 / CLI 生态；`rpc` 模式已满足 N22 |
| 从 harness 源码构建 / fork | 构建链重、升级慢；当前无补丁需求 |
| 把宿主机的扩展与技能全打进基线 | 与宿主工具链耦合；`auto-commit-on-exit` 类扩展与留痕要求冲突；第三方技能体积大且属他人内容 → 改为按需挂载，容器内默认空 |
| 两套并行语义（本地运行期 + 交付构建期） | 两套语义必然漂移（J2 的选项 D） |
| 用业务级增强覆盖中性定义字段 | 造成两个真源，`validate` 直接拒绝 |
| 把"是否支持某能力"交给 harness 自己声明后就相信 | 一定夸大；`conformance/C9` 要求声明与容器内实测一致 |
| 轨迹各自原生、只在导出时适配（P1 的选项 B） | 审计工具按 harness 分叉；且无法保证"不丢事件"——丢的往往正是排障最需要的那条 |
| `conformance` 部分项仅告警（P3 的选项 B） | 会被软化的正是 C5/C8（静默失败检测力、参数层隔离），也就是最危险的两类退化 |
