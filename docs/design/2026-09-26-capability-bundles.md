# 能力包（bundles）：可动态使能的一组能力

> 状态：**设计稿，未实现**。登记处：路线图 §27；本文与 §27 一起看。
> 来源：用户提出 —— 镜像里的 pi/dsh 是"裸的"；`run-local` 进去其实已经具备 AI Coding 条件，
> 希望带上常用的编程 skills / plugins / MCP。并且明确要求：**要有"包"的概念，不能一个一个选**；
> 包要能**动态使能** —— 验证时用简单纯净的环境，需要编程时打开；`/project` 正好是它的发现面。

## 1. 问题与现状

- **能力实体其实已经装了**（`preinstall.yaml` = 基座能力目录 + 锁文件实测 `npm 12 · apt 6`）：
  git / ripgrep / jq / curl / filesystem / repomix / playwright / chrome-devtools / inspector / context7…
- **缺三处**（见 §27）：模板默认子集是空头承诺（D9）· 技能落盘 0（C1）· 没有"插件"类目（C2）。
- 但**把三处补上还不够**：补完之后，每个智能体都会背上同一堆能力（工具描述吃 context、
  验证结论被无关能力污染）。用户要的是**可选择的包**，不是"一律装上"。
- 所以本文要解决的不是"装什么"，而是**"怎么把一组能力打包、并且能在不同场景下切换"**。

## 2. 核心张力：包选择与「行为烤、参数下放」冲突吗

已定原则（统一设计）：改变行为的内容烤进制品并在构建期渲染；运行期只下放端点/凭据/模型名/权限模式/工作区根。

**"运行期打开一个编码包"表面上是改行为** —— 若不加区分，它会破坏"同一份制品 = 同一行为"这条可复现性根基。

**化解办法：把"包"拆成三层，各有归属。**

| 层 | 是什么 | 归属 | 为什么 |
|---|---|---|---|
| **能力实体** | 技能文件、MCP 服务器、插件包（真正的代码/内容） | **构建期烤进基座镜像** | 运行期离线；pin + 存活实测 + 双架构都在这里管 |
| **包定义** | 「`coding` 包 = 这些具名能力 + 默认策略 + 判据」 | **制品/基座能力目录**（`preinstall.yaml` 的 bundles 节或 `bundles.yaml`） | 组合本身要可版本化、可审计、可复算 |
| **包激活** | 本次运行启用哪些包 | **运行期选择** | 从"制品允许的集合"里挑一个子集，**不引入新代码** |

**关键区分：运行期参数分两类，不能混。** 这是本文最重要的一条主张：

| 类别 | 例子 | 规矩 |
|---|---|---|
| **环境型**（已有） | 端点、凭据、模型名、权限模式、工作区根 | 真值在部署期注入；不进制品 |
| **选择型**（新增） | `AGENT_BUNDLES=verify-baseline,coding` | ① **合法取值集合必须烤在制品里**（运行期不许发明包名）② 每次运行的激活集合**必须进证据** ③ 影响 `usable` 结论的适用范围 |

**代价（必须写清）**：同一份定义 + 同一份产物，在**不同包组合**下行为不同。
因此"可用"这个结论**必须绑定"在哪个组合下可用"**，否则证据包会骗人。
这不算破坏可复现性 —— 可复现性变成"**定义 + 包组合** ⇒ 同一行为"。

## 3. 动态使能能到什么粒度（如实，不吹）

| 粒度 | 能否运行期切换 | 依据 |
|---|---|---|
| **工具**（工具的启用/禁用） | ✅ 运行期可改 | 【实测】pi 的 `setActiveTools` 可运行期重开被 `--exclude-tools` 关掉的工具 |
| **扩展 / 插件** | ⚠️ 需要 reload | 【API 存在】pi 扩展 ctx 有 `reload()`；dsh 组合树启动期组装，运行期不可加 row（`--patch` 交付镜像不接受） |
| **技能 / MCP 连接器** | ⚠️ 需要重启会话 | 【实测】两者的加载点都在启动期（`--skill` / `mcp.json` + 扩展） |
| 热插拔（无感切换） | ❌ 两侧都做不到 | 不要在契约里承诺做不到的事 |

⇒ **契约措辞**：包**可切换**，但切换**可能需要重载/重启会话**，且**切换本身必须留痕**。
"动态使能"= 随时能改，不等于"无感热插拔"。

## 4. 两类包（对应用户的两个场景）

| 包 | 场景 | 默认 | 内容取向 |
|---|---|---|---|
| **`verify-baseline`（验证基线）** | 验证：要**简单纯净**、结论可复现 | **开** | 只含基座不变量 + 定义声明的必需项；越少越好 |
| **`coding`（编码辅助）** | 需要真的读改代码、跑命令、查文档 | 关 | 工具描述轻、离线可用、**不需要 Chromium** 的那批：`filesystem` / `git` / `repomix` / `shell-toolchain` + 编码技能 |
| （后续）`browser` | 网页调研 / UI 验证 | 关 | playwright / chrome-devtools：重（带 Chromium），按需开 |

**为什么验证基线要"纯净"**：闸门 2 的断言集只含**当前启用**的连接器/扩展；
默认全开会让断言失去意义（"集合相等"变成"什么都相等"），也会让失败原因被无关能力淹没。

## 5. 与既有机制的关系（一处都不能漏，否则就是"看起来有"）

- **闸门 1（静态校验）**：包定义合法；包里的每条内容都能指到预装清单里的具名条目；
  `refs` 不许出现包名/版本（那是能力目录的事）；包子集与 `connectors.yaml` 声明不重复表达（单一真源）。
- **闸门 2（解析自证）**：期望集合 = **声明 ∩ 当前启用**（不是全量）⇒ "我开了 coding 包，
  里面的 MCP 真的加载了"可断言；没开的不算缺失。
- **闸门 3/4**：启用编码包后，端点侧**工具数必须真的变多**（现成判据 `probe/model.tools`）——
  这是"包里东西真的生效"的取证，而不是"声明了"。
- **轨迹**：每条事件带本次激活集合（或其摘要）；`effectiveConfigDigest` **是否纳入激活集合**
  ⇒ 见 §7 未决项（我倾向纳入，否则"同摘要不同行为"成立，摘要就没意义了）。
- **`verify --json`**：新增 `bundles: { active, available, digest }`；结论标注适用组合。
- **`/project`（已有）**：新增 `bundles` 分类 —— 列出**可用包 + 当前激活 + 包里有什么 + 怎么开**；
  补全项来自包定义与当前产物（与现有实现同一份逻辑），于是"补全即目录"这条继续成立。
- **交付/镜像语义**：包内容进**基座镜像**；`my-agent:<ver>@sha256` 的"验证快照"语义不变 ——
  快照里记的是"在什么包组合下验的"。

## 6. 包的定义形状（示意；字段名实现期定）

```yaml
# 基座能力目录里新增一节（或独立 bundles.yaml）
bundles:
  verify-baseline:
    label: 验证基线（纯净）
    purpose: 让验证结论可复现、失败原因不被无关能力淹没
    refs: []            # 只引用具名能力，不写包名/版本
    skills: []
    default: on

  coding:
    label: 编码辅助
    purpose: 让它能真正读改代码、跑命令、查文档
    refs: [filesystem, git, repomix]        # shell 工具链属 apt 层，用名字引用
    skills: [code-navigation, debugging, verification]
    plugins:                                # harness 专有 ⇒ 必须显式标注差异
      pi:  []
      dsh: []
    default: off
```

**跨 harness**：技能与连接器可共享（可移植内容）；**插件必然专有**。
差异照旧写 `exemptions.yaml`，**不假装等价**（沿用既有纪律）。

## 7. 未决项（需要拍板，我一律给建议）

1. **选择型运行期参数**是否作为 `params.yaml` 的**新类别**记账（以及闸门 1 的对应检查）——
   建议：是。它是"行为选择"，与环境型参数混在一个清单里会掩盖它的证据义务。
2. **`effectiveConfigDigest` 是否纳入激活集合** —— 建议：纳入（理由见 §5）。
3. **默认组合由谁定**：基座给一套、模板可覆盖？—— 建议：基座定义包与默认，
   模板（`new-agent`）决定新智能体的初始组合（并把这行写进 README 的开发循环）。
4. **动态粒度的契约措辞**：接受"切换需 reload/重启 + 留痕"，还是要追求热插拔？—— 建议：前者。
5. **包与"可用"结论的绑定强度**：只在 `verify --json` 记组合，还是要求"每个组合各一份验证结论"？
   —— 建议：先记组合（轻），等真出现"两个组合都要验"的场景再要求多份。

## 8. 与 §27 的关系（谁做什么）

- §27 的 **D9（模板默认子集）** 在本设计里升级为"**默认包组合**"，不再是"默认开几个连接器"。
- §27 的 **C1（3 个编码技能落盘）** 成为 `coding` 包的组成部分；技能"进声明"的机制照旧必须先落（否则闸门 2 全红）。
- §27 的 **C2（插件类目）** 成为 `bundles.*.plugins` 的一个字段来源。
- §27 的 **C6（判据纪律）** 适用于包里的每一条内容，一条都不能少。
