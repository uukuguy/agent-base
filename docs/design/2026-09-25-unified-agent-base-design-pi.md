## 0. 为什么需要这一份（问题的来源）

两份设计各自回答「怎么用 harness X 做企业智能体基座」，且**独立地**发现了同一个结构：

| 设计 | 切分方式 | 老化慢的部分 | 老化快的部分 |
|---|---|---|---|
| pi | 第一部分 / 第二部分 | 十条要求 R1–R10、边界、验收 | §2.1 八条实测约束、三个决定 |
| dsh | 【基座通用】/【dsh 专有】 | §4 的 4.1–4.13 | §3 的 profile/patch/MCP/HMR |

两边都意识到：**「企业智能体基座该有什么能力」与 harness 无关、长期稳定；「harness 逼我怎么做」随上游版本快速老化。** 这就是本设计要形式化的东西。

本设计把它收敛为一句话：

> **一个 harness 无关的统一基座（能力要求 + 边界 + 交付物 + 验证闸门 + 派生契约），加一个可插拔的 harness 运行时适配层（每 harness 一份「约束清单 + 适配决策 + 静默失败清单」）。**

三态标记沿用 dsh 的分法（它是更好的老化模型），改名为：

| 标记 | 含义 | 老化速度 | 换 harness 后 |
|---|---|---|---|
| **【基座通用】** | 任何 agent 框架下企业基座都该有的东西 | 慢 | 保留 |
| **【harness 适配】** | 某个 harness 的机制与约束，全部实测 | 快 | 作废，按新 harness 重测 |
| **【项目决策】** | 跨 harness 的统一取舍 | 中 | 重新决策 |

## 1. 目标与边界

### 1.1 目标【基座通用】

做**企业智能体的基座**，不是最终应用。成功标准：

> 一个新的企业智能体可以从它**便捷地启动**，并且**被验证真的可用**。

「便捷」指**心智负担低**（概念负担、局部性、可发现性、防错性、开箱可用、可接手性），不是「耗时最短」。把便捷定义成工期会砍掉文档与校验。

### 1.2 三级边界【基座通用】（合并 pi §1.1 与 dsh §1.2）

pi 划了「基座 vs 平台」，dsh 划了「基座 vs 应用」，两者是同一根轴的两端。统一为三级：

| 层 | 是什么 | 含什么 | 谁维护 | 变更频率 |
|---|---|---|---|---|
| **平台** | 编排 / 鉴权 / 多租户 / 审批流 / 计费 / 调度 | — | 平台团队 | 低 |
| **基座**（本设计） | 可复用启动底座 | 基础配置、基础镜像、模板、脚手架、校验、文档 | 平台团队 | 低 |
| **应用**（企业智能体） | 某个业务场景的智能体 | 人设与边界、技能、连接器 | 业务团队 | 高 |

两条不变量（分别来自两份设计的核心约束，缺一不可）：

1. **基座不做平台**（pi D1）：权限体系、审批流、多租户、调度不属于基座；基座只提供被平台调用的接口（RPC / headless）。
2. **基座不含应用**（dsh §1.2）：业务智能体必须派生到基座**之外**，且不回头修改基座。参考实现可以放在基座仓库的 `examples/`，但必须在 README 写明「可整个删除」。

判定标准（pi §1.1 原话，沿用）：一条需求若只对某一个智能体成立，就不属于基座。

### 1.3 四个业务概念【基座通用】（dsh §4.2）

业务开发者只需要理解 ≤ 4 个业务语言概念，框架概念由基座吸收：

| 业务开发者说 | 统一语义 |
|---|---|
| 我的智能体 | 一个可版本化、可 diff/review/回滚的目录 |
| 它会哪些技能 | SKILL 目录 bundle |
| 它能连哪些系统 | 连接器（MCP 服务器）配置记录 |
| 它是谁、边界在哪 | 人设 + 工具白名单 + 安全姿态 |

## 2. 统一能力模型【基座通用】

两份能力清单是**互补**的，不是重复的。pi 强在委派 / 可复现 / 供应链；dsh 强在概念收敛 / 能力目录 / 交付契约 / 文档体系 / 纪律显式化。合并去重后得到统一能力模型（`UC1`–`UC16`）。

### 2.1 合并表（UC ↔ pi R ↔ dsh §4）

| 统一编号 | 能力要求 | pi 来源 | dsh 来源 |
|---|---|---|---|
| **UC1** | 模型接入与制品解耦：换端点/换模型不改制品 | R1 | §2.3、§4.7 |
| **UC2** | 默认安全姿态：不信任工作区、写入保护、最小权限、非 root | R2 | §3.8 |

### 2.2 两条跨能力的原则【项目决策】

1. **能力是企业不变量，选择是应用可变**（dsh §2.3）：有哪些 provider / 安全姿态 / 通用技能属于基座（构建期烤入）；这次用哪个 model / 端点 / 密钥属于应用（运行期注入）。
2. **隔离靠文件系统，不靠配置**（pi 约束 3/4）：harness 普遍存在「无法用配置关闭的隐式加载源」（pi 的 `~/.agents/skills`；dsh 的 project `.agents/skills` 六根 rank 扫描）。统一解法是固定并隔离 `HOME` / `DSH_HOME`，而不是逐项关闭配置。

## 3. harness 运行时抽象【harness 适配 → 接口定义】

基座对 harness 运行时提出的契约，共九个轴。每个 harness 适配层必须逐轴回答三件事：

- **实测约束**：在本机/真实环境跑出来的事实，不是从文档推断。
- **适配决策**：由此导出的「基座这一轴怎么做」。
- **静默失败清单**：harness 会「悄悄不做你想做的事」的所有情形（供 UC14 静态校验兜底）。

| 轴 | 基座要什么 | 换 harness 时必查 |
|---|---|---|
| **H1 配置合成模型** | 层与优先级、能否 include/拼接 | 有没有多文件拼接机制 |
| **H2 端点/模型注入** | 端点能否容器外配置、密钥能否引用变量 | baseUrl 是否环境插值 |
| **H3 技能发现与隔离** | 技能从哪加载、有没有隐式加载源 | 隐式路径是否跟 HOME |
| **H4 连接器/MCP** | 外部系统连接、凭据治理、失败时降级还是失败 | 连不上是否静默降级 |
| **H5 安全/沙箱/权限** | 不信任工作区、写入保护、审批、沙箱 | 沙箱是否 Linux-only |
| **H6 可观测钩子** | 每次工具调用可否留痕、轨迹可否导出 | 有无工具调用事件 |
| **H7 委派/子智能体** | 上下文隔离、并行探索 | 有无 subagent 机制 |
| **H8 交付入口/协议** | 交互 / 批处理 / 常驻，同一能力源 | 退出码与 stdout 契约 |
| **H9 静默失败模式** | 所有「改了没生效」的情形 | 逐项实测 |

**方法学（两份设计的共同产物，制度化）**：约束 → 适配决策的「倒推」必须落地为**实测证据**。pi 的 §2.1 八条、dsh 的 §3.11 实验 A–E 都是这个产物。统一设计要求：**每 harness 适配层必须交一份带可复现步骤的约束清单**，否则不视为完成。

## 4. 统一验证闸门【基座通用 + harness 适配】

pi 的「四层闸门」与 dsh 的「六关」是同一阶梯的不同粒度。合并为五层：

| 层 | 命令 | 验什么 | 来源 |
|---|---|---|---|
| **L0 静态** | `validate` | 配置合法 + 无静默失效 + 扩展类型 | dsh 六关① + pi `typecheck` |
| **L1 解析** | `doctor` | harness 实际解析到的配置/技能/扩展/诊断 | pi `doctor`；dsh `--dump-config` |
| **L2 装配** | `verify`（构建后） | 种子暂存、镜像装配、MCP/模型注册 | pi `verify` |
| **L3 运行时验收** | `verify`（运行时六关） | 能启动 → 模型可达 → 技能加载 → 连接器可达 → 能完成任务 | dsh §2.2 六关 |
| **L4 零凭据自证** | `smoke` | 假网关跑通「模型→工具→模型」闭环 | pi `smoke` |

- **L0 是 harness 适配层的专属责任**：框架的失败模式若是静默的（dsh 的 `patch: entry not found` exit 0、`skipping profile bundle`、MCP `failOnStartupError: false`），基座必须补成显式失败。
- **L4 的假网关思路与 harness 无关**，只适配协议：断言 `tools=N>0` 专用于识别企业网关「吞掉 tools 字段 / 降级流式」这类网络层 vs 配置层混叠故障（pi §4.2）。

## 5. 统一交付物结构【基座通用骨架 + harness 子目录】

```
agent-base/                       # 基座仓库（不含任何业务智能体）
├── README.md / CHANGELOG.md      # UC17
├── Makefile                      # new-agent / validate / doctor / verify / smoke / run / image
│
├── base/                         # ★ 基座本体：harness 无关
│   ├── invariants/               # 企业不变量（安全姿态、通用技能、provider 能力）——构建期烤入
│   ├── image/                    # 基础镜像 + entrypoint（每 harness 一版 Dockerfile）
│   ├── template/                 # 新智能体起始骨架：agent 人设/边界、skills、connectors，开箱可跑无 TODO
│   └── docs/                     # UC17 最小文档集（overview/quickstart/concepts/catalog/deploy/troubleshooting/conventions）
│
├── harness/                      # ★ harness 运行时适配层（可插拔，每 harness 一目录）
│   ├── pi/                       #   约束清单（§2.1 八条）+ 适配决策 + 静默失败清单 + doctor/smoke 脚本
│   └── dsh/                      #   约束清单（§3.11 A–E）+ 适配决策 + 静默失败清单 + validate/verify 脚本
│
├── tools/                        # ★ 基座本体：脚手架 + 校验 + 验收
│   ├── new-agent.mjs             # 从 base/template 派生应用（UC9）
│   ├── validate.mjs              # L0 静态校验（UC14）
│   └── verify.mjs                # L3 六关运行时验收（UC14）
│
├── examples/                     # ⚠ 应用示例，非基座本体，可整个删除（UC9/§4.6）
│   ├── pure-skill/               # 纯技能型
│   └── with-connector/           # 带外部系统连接型
│
└── .github/workflows/validate.yml
```

关键点：**`base/` 与 `tools/` 是 harness 无关的；`harness/` 是唯一随 harness 老化的部分。** 换 harness = 新增一个 `harness/<name>/`，`base/` 与 `tools/` 不动。

## 6. 统一派生契约【基座通用】

```
基座 ──派生──▶ 应用 ──验证──▶ 可用（L0→L4 全过）
```

- 派生 = 一条命令（`new-agent my-agent`）+ 只写增量（人设/边界、skills、connectors）。
- 换基座版本 = 改 `FROM` digest（pi §3.4）或升级基座仓库引用（dsh §6.2-3）。
- 新建一个智能体要写/改的文件 ≤ 3；需要理解的框架概念 ≤ 4；读上游源码/文档 = 0。

**配置注入的统一裁决【项目决策】**（合并 pi D2 与 dsh 四层合成）：

> **不变层构建期烤入，可变层运行期注入。** 可复现性（UC7）由「构建层 digest + 运行层生效配置 digest」双记录保证。

| 层 | 内容 | 何时进 |
|---|---|---|
| 不变量 | 安全姿态、通用技能、provider 能力、默认工具开关 | 构建期烤入镜像 |
| 变量 | 端点、模型、密钥 | 运行期注入（环境变量 / 启动渲染 / `--patch`） |

这是对 pi D2 的裁决：pi 因「无 include」被迫全扁平（构建期），dsh 因「四层合成」天然分层。统一原则采用 dsh 的分层——**pi 的 D2 二选一是 harness 约束强加的伪二选一，换到 dsh 后不必再全扁平**；但 pi 的顾虑（同 digest = 同行为）仍成立，用「运行层生效配置 digest」补。

|---|---|---|---|

| H4 MCP | 每服务器一条 row；`reconnect` + `failOnStartupError:false` | 已验证 | 连不上静默降级 |
| H5 安全 | `dsh-permission-presets` + `dsh-sandbox-policy`；landlock 仅 Linux | 已验证 | macOS 无沙箱 |

## 8. 统一决策点【项目决策】

合并 pi D1–D5 + 外部输入 I1–I3 + dsh §6.2：

| # | 决策点 | 备选 | 倾向 |
|---|---|---|---|
| D1 | 三级边界：接受「不做平台 + 不含应用」？ | 接受 / 扩大 | 接受 |
| D2 | 配置注入：不变层构建期 + 可变层运行期（§6） | 采纳 / 全构建期（pi 式）/ 全运行期 | 采纳 §6 分层 |
| D3 | 交付形态优先级：一次性 vs 常驻 | 一次性（建议） | 一次性；常驻需单独一张编排设计 |
| D4 | 安全下限缺口（只读根文件系统、出站白名单、MCP 凭据） | 本期 / 下一期 / 环境承担 | 本期至少把缺口写进验收标注 |
| D5 | 供应链：SBOM / 镜像签名 / 私仓 | 需要 / 部分 | 部分，接入 CI 时定 |
| D6 | 领域差异表达：`--patch` vs 独立 profile（dsh §6.2-1） | A / B | A（一镜像多智能体） |
| D7 | 参考实现场景：纯技能型 + 带连接器型 | 待定 | 覆盖两者各一 |
| D8 | 基座与应用是否分仓（dsh §6.2-3） | A 独立 / B 单仓 | A |

## 9. 统一风险清单【合并】

| 风险 | 说明 | 缓解 |
|---|---|---|
| harness 上游快速迭代 | pi 0.85.1→0.87.1、dsh 是 RC | 版本精确 pin；升级只复核 `harness/<name>/` |
| 静默失败 | 两个 harness 都有「改了没生效」的情形 | L0 `validate` + 每 harness 静默失败清单 |
| 配置重述腐化 | dsh `config` 整体替换，home 层 row 过期不报错 | validate + 定期复核 |
| 模型可用性无静态保障 | provider 路由写错/凭据缺失只在请求时暴露 | L3 模型可达探针 |
| 沙箱能力不齐 | macOS 无 landlock；pi 未做只读根 | 安全行为必须在容器内验证 |
| 凭据无法对 agent 隔离 | 工具进程以同一 OS 用户运行 | 容器边界由编排层负责 |
| 隐式加载源泄漏 | 宿主机技能混进容器 | 文件系统隔离（固定 HOME/DSH_HOME） |
