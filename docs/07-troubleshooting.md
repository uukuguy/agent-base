# 07 · 排障：失败模式清单

> **这篇是文档里最该先看的一篇。** 其余篇章讲"怎么用"，这一篇讲"用错了会怎么坏、怎么看出来"。
> 本项目大量精力花在一件事上：**让失败可见** —— 因为这里的失败大多是**静默**的
> （退出码 0、照常启动、看起来一切正常，只是能力悄悄没了）。

## 一、先看退出码

| 退出码 | 含义 | 你要做什么 |
|---|---|---|
| `0` | 通过 / 可用 | — |
| `2` | **用法错误**（参数不对、或在生产镜像里请求调试模式） | 看 stderr 的用法提示；这不是产品缺陷 |
| `10` | **闸门 1 静态校验失败** | 定义本身有问题。按报错改 `agent.yaml` / `connectors.yaml` / `skills/` |
| `20` | **闸门 2 解析自证失败** | 运行时实际加载的东西 ≠ 你声明的。这是最需要认真看的一类 |
| `30` | **闸门 3 集成探针失败** | 某个组成部件**不可达**（模型端点、技能、连接器） |
| `40` | **闸门 4 端到端冒烟失败** | 能连上但**干不成活**（退出码、输出、轨迹、工具越界） |
| `50` | **未预期崩溃** | 基座自己的 bug 或环境异常。容器内崩溃会把轨迹末 N 行 + 生效配置摘要打到 stderr |

> 闸门 1 失败时后续闸门**不会跑** —— 定义都不合法，后面的结论没有意义。

## 二、四道闸门各自在防什么

| 闸门 | 命令 | 它回答的问题 | 它**不**回答 |
|---|---|---|---|
| 1 静态校验 | `make validate` | 定义合法吗？引用存在吗？凭据引用在允许清单里吗？ | 运行时会不会真加载 |
| 2 解析自证 | `make doctor RENDER_DIR=…` | 运行时**实际**加载了哪些技能/连接器/扩展？生效的是哪份配置？ | 这些东西**可达吗** |
| 3 集成探针 | `make probe RENDER_DIR=…` | 模型端点、技能、连接器**真的可达吗**？ | 它**能不能干活** |
| 4 端到端冒烟 | `make smoke RENDER_DIR=…` | 真跑一个任务：退出码、输出、轨迹合规、**有没有越界用工具** | 业务结论对不对 |

一次跑全：`make verify AGENT_DIR=<目录>`，最后给出**可用 / 不可用**。
`usable` 的定义是**四道全过**，不是"能启动"。

## 三、静默失败清单（本篇的核心）

这些失败**不会**让你看到报错。按"最危险"排序。

### 3.1 两个 harness 共同的形态

| 症状 | 真实原因 | 怎么检测 |
|---|---|---|
| 配置改了没生效，退出码 0 | **dsh D1**：patch 指向不存在的 row 时**只打警告、继续运行** | `doctor` 断言「每个 patch target 都命中组合树」——这条断言是**基座在替 harness 报它不报的错** |
| 技能比声明的多 | 两个 harness 都有**隐式技能源**（pi 有两个，其中之一沿 cwd 祖先发现；dsh 有六个 rank 根） | 闸门 2 断言「实际加载集合 == 声明集合」；本地运行必须用**临时 HOME + 中立 cwd** |
| 端点配了没生效 | pi 的 `models.json` **不对 `baseUrl` 做环境插值**（只对 apiKey/headers 插值） | 渲染器产出 `.tmpl`，**启动期**渲染；`doctor` 断言生效配置来自本次产物 |
| 推理强度配了没生效 | pi 把 thinking level **钳到模型声明支持的档位**，模型无该元数据时**静默降为 `off`** | 闸门 2 断言「声明的档位 == 实际档位」，不一致即失败 |
| 工具黑名单没生效 | pi 的 `tools.deny` 靠**运行参数**生效 —— 手工直接启动 harness 会绕过它 | 闸门 4 断言调用到的工具都没触碰禁用清单；闸门 2 断言 row/settings 级边界 |
| 增强/扩展没加载 | 扩展加载抛错可能被忽略 | 闸门 2 断言「已加载扩展 id 集合 == 声明集合」 |
| 配置目录不是本次产物 | pi 从 `PI_CODING_AGENT_DIR` 取目录，**环境变量缺失时回落到真实 `~/.pi`**，带着宿主机配置照常启动 | 闸门 2 断言 `definitionPath` == 本次渲染产物 |
| 连接器被静默忽略 | pi **原生没有 MCP 客户端**（靠基座种子扩展补上） | 闸门 2 断言「声明了连接器 ⇒ 产物必须声明客户端扩展」；本地运行未提供扩展路径时运行器**拒绝运行** |
| 无人值守时"卡死" | **dsh D4**：审批在**无应答者时 fail closed** —— 它不是失败退出，而是**等** | 冒烟用例超时即判失败；运行入口必须显式给放行策略 |
| 工具没出现但照常启动 | **dsh D3**：MCP `failOnStartupError` 默认 `false`，连不上也启动 | 连接器探针**必须让闸门 3 失败** |
| 升级后行为漂移 | **dsh D6 重述腐化**：上游 `config` 是**整体替换**而非深合并，重述的 row 会随上游变化而过期且不报错 | 渲染器产出**完整** config（不做增量假设）+ 产物 digest 可复算；升级时靠 `conformance` 回归 |

### 3.2 完整清单在哪

每个适配器目录下都有一份逐条的失败表，含"检测方式"与"归属闸门"：

- `adapters/pi/failures.md` —— F1–F10（隐式技能双源、端点不插值、推理强度钳位、扩展没加载、工具黑名单语义、运行期写配置、配置目录回落、连接器静默忽略 …）
- `adapters/dsh/failures.md` —— D1–D8（patch 静默失效、增强没加载、MCP 静默降级、审批 fail closed 卡死、六个技能根、重述腐化、`--patch` 逃生舱、调试态未标记）

**每条都配了一个可执行的检测用例**（`failure-cases.yaml`），由 `make conformance` 的 C5 逐条注入验证 ——
"写了检测方式但没有用例"不算数。

## 四、基座自身的坑（实测踩过，写下来省你时间）

| 坑 | 现象 | 结论 |
|---|---|---|
| 起的 harness 进程**没关 stdin** | 子进程零输出、零事件，看起来像"扩展没加载" | 非交互模式也必须 `stdin.end()`，否则它可能在等输入 |
| 同进程起假网关 + 子进程 harness | 网关收不到任何请求 | 用独立进程；这条曾被误判为"必须独立进程"，真因其实是上一条 |
| 手写"跳过旗标值"的参数解析 | `--out` 缺失时 `indexOf()+1 === 0`，**吞掉第一个位置参数** | 统一用 `core/gates/cli.mjs` 的 `parseArgs`；闸门 1 有静态检查拦这种写法（它错过三次） |
| 算相对路径前没 `realpath` | 符号链接导致"算式正确、实际指错"（`/tmp`→`/private/tmp`） | 双方都 realpath 后再算；生成的 Makefile 有 `check-base` 给明确报错 |
| 构建产物落在定义目录内 | 渲染一次，产物摘要就变（自漂移） | `.render/`、`dist/` 已排除出定义摘要 |
| 手写 YAML 时表达式含 `: ` | 被当成嵌套映射，配置静默变成 `{'[object Object]': ask}` | 含 YAML 敏感字符时给表达式加引号（标签在引号**外面**） |
| 用 YAML 库的自定义标签输出 `!!js` | 出来是 `!!js [object Object]`，harness 不当作表达式求值 | 自己输出这套简单结构的 YAML |
| **检查写在错误的方向上** | 检查测了一条系统**从不执行**的命令，于是必然失败 ⇒ 报出**假缺陷** | 判据必须打在**系统真正执行的命令**上。这类错比漏检更糟：它会让你去修本来正确的东西 |

## 五、出问题时，证据在哪

| 证据 | 位置 | 用途 |
|---|---|---|
| §6.7 报告 | `make verify AGENT_DIR=… JSON=1` | 四道闸门的逐条结论 + `usable` |
| 渲染清单 | `<render>/render-manifest.json` | 产物摘要、声明的技能/连接器/增强、**`expresses`（每个定义字段落在产物哪里）** |
| 自证输出 | `make doctor RENDER_DIR=… JSON=1` | 七个字段：harness/version、definitionPath、skills、connectors、enhancements、modelProviders、effectiveConfigDigest |
| 统一轨迹 | 运行期轨迹文件（JSONL） | 8 类事件；未映射的原生事件进 `native.raw`（**不许丢弃**） |
| 业务可读时间轴 | `node tools/trace-view/labels.mjs <AGENT_DIR> --timeline <轨迹>` | 按业务标签表把机械轨迹渲染成业务语言 |
| 容器内诊断 shell | `make debug RENDER_DIR=…` | 复现"只在容器里出现"的问题（生产镜像会明确拒绝调试模式） |

## 六、诚实说明：现在还不知道的

| 项 | 状态 |
|---|---|
| pi 的推理强度在**有 thinking 元数据的真实 provider** 上是否被尊重 | 离线环境无内建模型目录，**需真实 provider 才能实测**。检测用例不依赖该结论（它断言"声明档位 == 实际档位"，两种情况都成立） |
| dsh 的 `model.reasoningEffort` 映射 | **尚未映射**（provider 条目的 `reasoningEfforts` 取值形状未实测）。渲染器把它声明为**豁免并写明理由**，不猜形状、也不静默丢弃 |
| 网关吞 `tools` / 降级流式 | 已记录为**将来风险**，不进准入门槛（当前无企业网关，直连 API） |
| 连接器"已被发现"（而非"已配置且就位"） | dsh 侧没有零凭据原语能列出已发现技能，口径较弱 —— 已进 `exemptions.yaml`，不许当作与 pi 等价 |
| `enhancements[]` 的口径 | pi 侧目前是「**已进入产物**」而非「**已加载**」，离真正的加载还差一步（pi 约束 7）。缺口记在 `adapters/pi/failures.md` 的 F6 |
