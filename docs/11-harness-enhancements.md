# 11 · 业务级增强怎么写

## 一、先分清三种东西

| 类型 | 放哪 | 可移植吗 | 例子 |
|---|---|---|---|
| **中性定义** | `agent.yaml` / `skills/` / `connectors.yaml` | ✅ 两个运行时都懂 | 人设、技能、连接器 |
| **业务级增强** | `harness/<运行时>/` | ❌ 必然专有 | 自定义工具、钩子、拦截器 |
| **基座不变量** | `adapters/<h>/seed/` | ❌（但由**基座**提供，业务只声明） | 安全姿态、轨迹扩展 |

**为什么必然专有**：两个运行时的扩展机制根本不同 —— pi 是 TypeScript 扩展文件，
dsh 是 cordis 插件 npm 包。指望"一份增强两边跑"是不现实的，所以设计上就把它排除在
可移植性承诺之外（但**必须显式声明**，不能沉默地不一样）。

## 二、三层结构

```
harness/
  shared/          纯业务算法：无运行时依赖、无 I/O 副作用（技能脚本也可以挂这里）
  pi/              pi 的薄外壳：协议适配 + 注册
  dsh/             dsh 的薄外壳：同上
```

- **`shared/`**：真正可复用的业务逻辑（算规则、评分、解析）。**不许**依赖任何一个运行时的 API
- **`<运行时>/`**：薄薄一层，负责"把 shared 里的算法注册成这个运行时认的扩展"
- 两边都薄 ⇒ 换运行时只重写外壳

## 三、声明与实体必须成对

`harness/<运行时>/enhancements.yaml` 是**声明清单**：

```yaml
apiVersion: agent-base/v1
harness: pi
enhancements:
  - kind: hook              # 扩展种类（该运行时自己的说法）
    id: risk-score          # 唯一 id —— 闸门 2 用它做集合断言
    entry: extensions/risk-score.ts    # pi：产物里的扩展文件
```

dsh 的形态不同（增强是 npm 包）：

```yaml
apiVersion: agent-base/v1
harness: dsh
enhancements:
  - kind: plugin
    id: risk-score
    package: "@your-org/agent-risk-score"    # 包名
    config: { threshold: 0.7 }               # 可选
```

**形态由适配器决定**（`adapter.yaml` 的 `enhancementShape: file | package`）——
用例助手与检查都照它来，所以你不必去猜哪种写法对。

## 四、三条硬约束（违反会被机器拦）

| 约束 | 为什么 | 谁拦 |
|---|---|---|
| **声明的必须有实体** | 声明了却找不到文件 = 你以为增强了、其实没有 | `resolution/enhancement-entries` |
| **加载的必须等于声明的** | 扩展可能**静默没加载**（抛错被忽略） | 闸门 2 第三条硬断言 |
| **增强不得重复表达中性定义已表达的字段** | 否则同一件事有两个真源，改一处漏一处 | `enhance/single-source` |

第三条最容易踩：你要改人设、改工具边界、改模型选择，**改中性定义**，不要在增强里再写一遍。

## 五、现成的参考实现：基座自己的轨迹扩展

**基座不变量增强**的最好例子就是它自己 —— `adapters/pi/seed/extensions/trace.ts`：

- 它是**基座不变量**（每个智能体都有），但**同样走声明清单**（`seed/enhancements.yaml`）——
  **基座不给自己开后门**，闸门 2 的集合断言一样覆盖它
- 它的纪律写得明明白白，**直接可以照抄**：

| 纪律 | 为什么 |
|---|---|
| **只订阅，绝不返回值** | 事件分通知/变换/替换/取消四类；一旦返回值就可能覆盖或取消**业务扩展**的意图 |
| **绝不抛异常** | 运行时的 `tool_call` 回调里抛异常会**阻断工具调用** —— 一个写日志的回调把业务工具搞挂，是不可接受的反向依赖 |
| **幂等** | 退出/reload/会话替换会汇聚到同一清理路径 |
| **观测不到就不写** | 拿不到判定就写 `unobserved`，**不写 `allow`** —— 那会让审计把「没记录」误读成「放行了」 |

业务增强与它**叠在同一批回调上**，按注册顺序执行；运行时的 `tool_result` 处理器是**显式 compose** 的。
所以：**基座不占用扩展点**，你直接注册自己的即可。

## 六、晋升通道（什么时候该把它搬进基座）

同一个增强在**多个智能体重复出现**时，就是它该晋升为**基座不变量**的信号：

1. 基座在 `adapters/<h>/seed/` 提供实现
2. 业务侧只剩下**声明**（`enhancements.yaml` 里写一行）
3. 这样升级局部化：改一次，所有智能体一起受益

反过来，**不要**因为"就一个智能体用"就把东西塞进基座 —— 基座不含业务。

## 七、怎么确认它真的加载了

```bash
make validate            # 声明与实体成对、不重复表达中性字段
make render && make doctor RENDER_DIR=.render/pi
#   → doctor 的 enhancements[] 与声明集合做断言
make verify              # 四道闸门一起看
```

⚠️ **诚实说明当前口径**：pi 侧 `enhancements[]` 目前验到的是「**已进入产物**」
（实体已打包 + 已登记到运行时的扩展入口），**不是**「已被运行时成功加载」——
后一步需要扩展自己上报，目前还差这一步（缺口记在 `adapters/pi/failures.md` 的 F6）。
dsh 侧反而是**真观测**：它的组合树列出全部 row，"插入的增强行在不在、是否被禁用"可直接判定。

**所以：如果你在 pi 上写了增强，别只看 `make validate` 过了 —— 跑一次真实任务，
确认它的行为真的出现了。** 这一条是当前已知的能力边界，不是"应该没事"。
