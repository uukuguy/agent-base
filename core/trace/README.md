# core/trace —— 统一轨迹（基座不变量）

> **本层纪律（统一设计 §12.1 原话）**
>
> 放：中性定义规范、能力目录、闸门框架、统一轨迹 schema、基座镜像。
> **不放**：任何 harness 名字、任何业务概念的具体取值。

`schema.json` 是**唯一真源**。本文件说明三件事：三层分工、业务层怎么介入、可视化需要它保证什么。pi 侧的原生映射规格在 `adapters/pi/trace-mapping.md`。

## 一、三层分工（各自的老化速度不同，所以分层）

| 层 | 谁写 | 能不能改 | 审计工具怎么用 |
|---|---|---|---|
| **核心字段** | 基座 / 适配器 | **冻结**：增删字段要走设计评审 | 只读核心字段即可工作，**不必懂任何业务语义** |
| **`biz` 扩展位** | 业务层 | 自由加，但受形状约束 | 忽略它也能审计；要业务洞察时才读 |
| **`native.raw`** | 适配器 | 兜底，任何未映射的原生事件都进这里 | 用来发现「上游出了新事件」——所以 `reason` 必填 |

核心事件 8 类：`run.meta` / `model.request` / `model.error` / `tool.call` / `tool.result` / `gate` / `biz.event` / `native.raw`。

**为什么核心字段用 `additionalProperties: false`**：未知顶层字段一律拒绝，是为了让「上游出新东西了」**响亮地暴露**，而不是悄悄混进审计数据。业务要加东西，唯一的正路是下面第二节的受控扩展位——**不是**往顶层塞字段。

## 二、业务开发层怎么介入轨迹

三种方式，按侵入性递增：

### ① 给核心事件附业务上下文 —— `biz` 容器

任何事件都能挂 `biz`：

```json
{"ts":"2026-09-25T10:00:00Z","seq":12,"run":"…","type":"tool.call",
 "callId":"call_abc","tool":"mcp__jira__get_issue","inputDigest":"sha256:…","decision":"allow",
 "biz":{"contract.id":"C-1024","risk.level":3}}
```

约束（基座只校验**形状**，不解释语义）：

- 键必须是小写点分命名空间（`contract.id`）→ 防止业务字段与核心字段撞名
- 值只允许标量（string / number / boolean），最多 20 个键、字符串最长 500
- **标量约束不是洁癖**：它保证轨迹可序列化、可 diff、可视化时能直接渲染成表格；一旦允许嵌套，每个业务团队会长出一棵自己的树

### ② 把自己的领域事件写进同一条轨迹 —— `biz.event`

```json
{"ts":"…","seq":31,"run":"…","type":"biz.event",
 "name":"contract.risk_found","data":{"clause":"7.2","level":3}}
```

`name` **强制带命名空间**（至少一个点）。这样一眼能看出「这是业务语义，不是核心事件」，审计方不会被业务词汇淹没。

有了它，轨迹读起来是**业务叙事**（「找到风险条款 → 查询历史工单 → 判定高风险 → 拒绝」），而不只是工具调用流水。这正是 §8.3「回答这个智能体为什么这么决策」的落点。

### ③ 订阅与消费 —— 由业务侧实现，基座只保证可消费

轨迹是 JSONL 流（默认 stderr，`AGENT_TRACE_DEST` 可改文件），业务侧可以：

- `tail -f` / 管道订阅，边跑边看
- 承载业务级增强（`harness/<h>/`）里读同一份流，做自己的反应（告警、埋点、审批）
- 落库做回放与对比

基座不提供订阅 API —— 提供 API 就把「可消费」与「必须用我们的 SDK」混为一谈了；JSONL 已经是最低耦合的接口。

## 三、可视化：schema 这边的承诺

可视化工具是独立产物（不属本目录），但它需要轨迹保证几件事，这几件已写进 schema：

| 可视化需要 | schema 提供的保障 |
|---|---|
| 按时间轴回放 | `ts`（强制 UTC + `Z`）+ `seq`（同 run 单调递增，可检测丢行） |
| 按运行/会话分组 | `run` 必填 |
| **画出调用嵌套与耗时** | `tool.call` / `tool.result` 的 `callId` **必填** —— 没有它只能线性回放，画不出配对 |
| 分层展开（核心 / 原生 / 业务） | `type` 判别 + `biz` 命名空间 + `native.raw` 的 `reason` |
| 失败点定位 | `gate` 事件的 `ok` + §6.7 退出码（退出码定位「失败在哪一层」） |
| 归因「当时生效的是什么」 | 每条都带 `effectiveConfigDigest` |
| 看出「这份轨迹能不能外发」 | `run.meta.contentMode`（见下） |

### 内容 vs 摘要：一个必须显式化的取舍

§8.3 规定「工具入参只存 digest，不存明文」以防泄漏 —— 但**可视化需要内容**：拿着 `inputDigest` 画不出一次调用的真实样子。

处置：`run.meta.contentMode`

| 取值 | 含义 | 用在哪 |
|---|---|---|
| `digest`（默认） | 只留摘要；明文按 digest 去会话文件/工件存储取 | 审计件、可能外发的轨迹 |
| `full` | 轨迹里含明文 | 本地验证、容器内排障、**可视化** |

**关键不在默认值，而在「必须显式标注」**：一份含明文的轨迹与一份纯摘要的轨迹**性质不同**，绝不能被下游当成同一种东西 —— 否则可视化要的明文与审计要的脱敏会互相污染。含明文的轨迹本身就是一份敏感件，`contentMode` 就是它的标签。

> 取向说明：本基座的核心目标是**验证走通**而非生产上线（§1.1），所以验证/可视化场景默认可以取 `full` —— 但**必须打标**，且生产化阶段要把它收回来。

## 四、自检

```bash
make trace-selftest
```

覆盖：8 类合法事件通过 + 17 类必拒写法（含 `biz` 键未命名空间、`biz` 值嵌套、`biz.event` 名未命名空间、`tool.call` 缺 `callId`、`contentMode` 取值非法）。
